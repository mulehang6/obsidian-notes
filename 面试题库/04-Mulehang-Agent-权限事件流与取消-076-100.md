# Mulehang Agent：权限、事件流与取消（076-100）

## 076. Agent 的安全边界由什么组成？

### 面试时可以这样答

> 安全不能只写在 system prompt 里。项目把边界分散在几个可执行位置：注册表限制模型能看到哪些工具；工作区限制文件作用域；权限档位决定读、写、执行的默认策略；硬规则拒绝明显危险命令；Hook 可以在工具前阻断或要求确认；交互桥负责人工审批；审计日志记录决定来源。任何一层都可能漏判，所以不能把其中一层描述成完整沙箱。
>
> 当前实现主要降低误操作风险，还不能等同于操作系统级隔离。若要执行不受信任代码，应增加低权限进程、容器或虚拟机、网络限制和资源配额。

## 077. `PLAN` 模式为什么仍允许读取？

### 面试时可以这样答

> 规划需要理解项目。若连文件、目录和代码搜索都禁止，Agent 只能凭猜测生成方案。`PLAN` 因此允许只读工具，但 `isWriteDenied` 和 `isExecuteDenied` 都返回 true，补丁和命令在执行入口被拒绝。
>
> 只读也不是全盘读取。工作区外文件仍要审批，因为内容可能包含隐私或密钥。PLAN 的含义是“不改变环境”，不是“可以读取电脑上的一切”。

## 078. `EDIT_ALLOW` 与 `BRAVE` 的差别是什么？

### 面试时可以这样答

> `EDIT_ALLOW` 自动批准工作区内写入，但不会自动执行命令。它适合用户愿意让 Agent 改代码，却仍想在运行脚本前确认的场景。`BRAVE` 同时自动批准写入和执行，交互更少，风险更高。
>
> 两者都不能绕过硬规则、PLAN 之外的路径判断和 Hook。工作区外写入也不会因为 `EDIT_ALLOW` 就自动放行。权限档位是默认决策，不是关闭所有检查的总开关。

## 079. 为什么 `DEFAULT` 不能简单理解为只读？

### 面试时可以这样答

> `DEFAULT` 允许提出写入和执行请求，只是不自动批准。系统会生成 diff、操作意图和风险信息，再等待用户确认。只读模式是 `PLAN`，两者的能力不同。
>
> 这个区别影响用户体验。DEFAULT 仍能完成完整任务，只是关键动作有人在环；PLAN 在工具入口就禁止改变环境，适合分析和方案阶段。面试时若把二者混为一谈，就无法解释审批流程存在的意义。

## 080. Hook、权限档位和人工审批的顺序是什么？

### 面试时可以这样答

> 以工具调用为例，Hook 先获得拦截机会。`BLOCK` 直接拒绝，`ALLOW` 可以按当前规则放行，`ASK` 强制人工确认，`CONTINUE` 才进入普通权限判断。随后检查档位是否硬性禁止，再决定自动批准、自动审核或人工审批。
>
> 顺序必须稳定。若先自动批准再执行 Hook，组织策略就来不及阻止动作；若 `ASK` 还能被后面的自动策略覆盖，强制确认就失效。项目把 Hook 决定显式映射，避免用多个布尔值拼出含糊优先级。

## 081. 为什么网关返回 `Flow<AgentStreamEvent>`？

### 面试时可以这样答

> Agent 一次运行可能持续几分钟，中间有文本、工具、审批和命令输出。若接口只返回最终字符串，UI 无法显示进度，也无法在等待审批时交互。Kotlin Flow 可以顺序传递这些异步事件，并把收集取消向上游传播。
>
> Flow 还让网关与 Compose 解耦。测试可以直接收集事件，命令行界面也能复用同一接口。需要注意的是，Flow 只提供通信模型，事件顺序、缓冲和资源关闭仍由实现保证。

## 082. 为什么这里使用 `channelFlow`？

### 面试时可以这样答

> 事件来自多个并发来源。Agent 主任务产生文本和终态，工具子进程线程产生 stdout、stderr 和 diff，审批桥也会发事件。普通 `flow` 的 emit 要求同一协程上下文，不适合多个生产者直接发送。`channelFlow` 提供可并发发送的通道，并与收集方生命周期绑定。
>
> 网关内部再用一个容量为 64 的事件队列统一转发，避免阻塞式工具回调直接操作下游 Flow。代价是必须认真处理队列关闭、转发任务退出和背压。

## 083. 事件队列容量为什么不是无限？

### 面试时可以这样答

> 无限缓冲会在命令疯狂输出、UI 消费变慢时持续占用内存。容量 64 给生产者和消费者留出短暂速度差，又会在积压时施加背压。这个数字是当前工程参数，不是理论最优值。
>
> 若工具回调所在环境不能挂起，代码使用受控桥接把事件送入队列。后续应通过队列占用、丢弃情况和 UI 延迟校准容量。真正的大量日志还需要采样或落盘，不能靠调大内存队列解决。

## 084. `Started`、`Completed`、`Failed` 为什么必须是明确事件？

### 面试时可以这样答

> UI 不能用“有没有文本”推断生命周期。工具型任务可能很久没有正文，失败前也可能已经输出部分内容。`Started` 建立运行边界，`Completed` 携带成功结果，`Failed` 携带运行级原因。
>
> 它们也方便持久化和测试。一次运行应只有一个终态，单次 `ToolCallFailed` 不能被误当成运行失败。若收集被取消，UI 还要有单独的取消状态，不能伪造 Completed。

## 085. 网关结束时为什么要按顺序关闭资源？

### 面试时可以这样答

> `finally` 中先释放本轮 MCP 视图，再按会话情况关闭 Hook dispatcher，然后关闭事件队列，等待转发任务排空，最后关闭 channelFlow。若先关闭下游，末尾的失败或完成事件可能丢失；若不等待转发任务，已经入队的事件可能来不及送达。
>
> 清理必须覆盖成功、异常和取消。只在正常分支释放资源，会让失败任务留下连接、协程或子进程。

## 086. 为什么 `CancellationException` 要单独抛出？

### 面试时可以这样答

> Kotlin 协程用 `CancellationException` 表示结构化取消，它不是普通业务失败。若被宽泛的 `catch (Exception)` 转成 `AgentStreamEvent.Failed`，上游会认为任务出错，协程也可能无法及时停止子任务。
>
> 网关因此捕获后直接重新抛出，其他异常才转换为 Failed。这个习惯对所有 suspend 代码都重要：可以做 finally 清理，但不能吞掉取消后继续工作。

## 087. 用户点击停止后，取消如何传到工具？

### 面试时可以这样答

> Flow 收集取消后，`channelFlow` 作用域不再 active。网关在创建 `DesktopToolSet` 时注入 `isCancelled = { !isActive }`。命令工具再把这个函数传给 `DesktopProcessRunner`，运行器每 50 毫秒轮询一次。
>
> 检测到取消后，运行器终止主进程及已观察到的后代进程，并返回 `CANCELLED`。这条链说明取消不是 UI 隐藏按钮，而是从收集生命周期一路传播到操作系统进程。

## 088. 为什么取消时要处理子进程树？

### 面试时可以这样答

> Windows 下常见的 `cmd`、Gradle 或脚本解释器会再启动子进程。只结束最外层包装进程，编译器或测试进程可能继续运行，并继续持有 stdout 管道。用户以为任务停了，CPU 和文件仍在变化。
>
> 运行器在等待期间持续收集 descendants，终止时先处理后代，再结束主进程。先尝试正常 destroy，500 毫秒后仍未退出就强制终止，并再次清理存活后代。

## 089. 为什么不能无限等待进程输出 EOF？

### 面试时可以这样答

> Windows 上被终止的包装进程可能留下继承的管道句柄，输出读取线程一直等不到 EOF。如果主线程无限 `get()`，任务虽然已经取消，应用仍卡住。
>
> 项目给输出排空设置 1 秒上限。超时后取消读取任务，并把输出标记为 truncated。这样牺牲末尾一小段日志，换取确定的退出。界面必须显示截断状态，不能把不完整输出当成完整结果。

## 090. 为什么 stdout 与 stderr 要并发排空？

### 面试时可以这样答

> 子进程的两个管道都有有限缓冲。如果程序大量写 stderr，而父进程只同步读取 stdout，stderr 缓冲写满后子进程会阻塞，父进程又等 stdout 或进程结束，最终死锁。
>
> `DesktopProcessRunner` 使用独立任务同时读取 stdout、stderr，并另开任务写 stdin。进程结束后再等待这些任务完成。这个细节比“调用 ProcessBuilder”本身更能体现进程执行是否可靠。

## 091. 输出为什么同时要流式发送和有限保存？

### 面试时可以这样答

> 流式回调用于实时界面，保存的文本用于最终工具结果和模型观察。二者不能互相替代。只流式不保存，模型拿不到完整结果；只保存不流式，长命令没有反馈。
>
> 项目每个流最多保存 1 MiB，超过后继续排空管道但不再写入内存，并设置 truncated 标志。继续排空很关键，否则即使不保存，子进程仍可能因管道写满而阻塞。

## 092. UTF-8 流式解码为什么不能直接对每个字节块转字符串？

### 面试时可以这样答

> 一个中文字符的 UTF-8 字节可能被拆在两个读取块中。若每块直接构造字符串，边界处会出现替换字符，流式 UI 与最终文本也可能不一致。
>
> 运行器保留未完成字节，用 `CharsetDecoder` 增量解码，只把完整字符交给回调，结束时再 flush。遇到非法字节使用替换策略，避免整个读取线程崩溃。这是流式 I/O 常被忽略的正确性问题。

## 093. 文件 diff 为什么在工具完成前发事件？

### 面试时可以这样答

> `apply_patch` 在真正写入前就生成结构化 diff。系统此时发 `ToolFileDiffPreviewed`，审批界面可以展示；即使 AUTO 自动放行，时间线也能保留同一份预览。工具完成后再发结果事件。
>
> 如果只在工具完成后从文本结果反推 diff，可能丢失多文件结构，也无法用于事前审批。预览事件与完成事件职责不同，前者描述将要或已经展示的变化，后者说明执行结果。

## 094. 为什么自动批准时也要展示 diff？

### 面试时可以这样答

> 自动批准减少点击，不等于隐藏动作。用户仍需要知道 Agent 改了哪些文件，出错时也要能沿时间线定位具体补丁。项目注释明确要求 AUTO 放行的补丁也显示同一份预览。
>
> 安全设计既要控制动作，也要让动作可见。没有可见记录的自动化，出了问题只能依赖磁盘最终状态，很难判断是哪一步造成的。

## 095. 工具失败与运行失败在 UI 上应如何区分？

### 面试时可以这样答

> `ToolCallFailed` 属于时间线中的一步，应显示工具名、callId 和原因，并允许后续事件继续出现。`Failed` 是整次运行终态，出现后不应再期待正常 Completed。颜色和文案也应不同，避免用户看到一次路径不存在就误以为任务结束。
>
> 数据模型已经区分两者，UI reducer 仍可能写错。测试应覆盖“工具失败后模型换方法并最终完成”的事件序列。

## 096. 达到迭代上限后如何给出可行动的错误？

### 面试时可以这样答

> 网关识别 Koog 的 `AIAgentMaxNumberOfIterationsReachedException`，不会只显示类名。普通上限会告诉用户本次配置值，并建议提高上限或缩小任务范围；无限模式达到框架极限时使用另一条说明。
>
> 好的错误消息要说明发生了什么、当前会话是否还能继续、用户下一步能做什么。它不能伪装成模型最终回答，也不应丢掉已完成的工具轨迹。

## 097. 为什么异常消息不能全部原样展示？

### 面试时可以这样答

> 原始异常适合诊断，但可能包含本地路径、请求地址或敏感参数。用户界面需要稳定、可理解的原因，详细堆栈应进入受控日志。当前 `agentFailureReason` 对迭代异常做了专门转换，其他异常暂时使用 message，这仍有改进空间。
>
> 更完整的方案会为错误建立类型和安全展示文本，同时保留 traceId 关联内部日志。不能简单把整个 stack trace 发回模型或界面。

## 098. 如何处理慢 UI 带来的背压？

### 面试时可以这样答

> 有界 Channel 会在容量耗尽后阻止继续发送，这能限制内存，却也可能拖慢 Agent。文本 token、命令日志和终态的重要性不同，可以分别采用合并、采样和绝不丢弃的策略。
>
> 当前容量 64 是基础保护。后续可把连续 TextDelta 合并成帧，对高频 stdout 批量刷新，但 Completed、Failed、审批和 diff 不能丢。优化前要测 UI 消费延迟，不应凭感觉把容量改大。

## 099. 怎样保证一次运行只产生一个终态？

### 面试时可以这样答

> 正常分支在 `agentRunner` 返回后发送 Completed；异常分支发送 Failed；取消则重新抛出，由上层标记取消。事件队列在 finally 中关闭，防止后台继续写入。这个结构在代码层把终态集中在网关边界。
>
> 仍应写事件序列测试，覆盖完成时 Hook 继续、MCP 连接诊断、工具失败和取消竞态。尤其要防止下游取消后 finally 又试图发送 Failed，造成“取消后失败”的双重状态。

## 100. 你会如何测试流式、取消和权限这条链？

### 面试时可以这样答

> 我会分层测试。纯单元测试覆盖权限矩阵、危险命令识别、UTF-8 分块和截断。进程测试启动可控的短命令，验证 stdout、stderr、超时、取消以及后代进程终止。网关测试使用假的 Agent runner 和交互桥，断言事件顺序、审批等待和唯一终态。
>
> 最后做少量端到端测试，从 UI 发起命令再点击停止，确认进程确实退出，而不是按钮变灰。失败用例比成功用例更重要，因为资源泄漏和历史不完整通常只出现在异常路径。
