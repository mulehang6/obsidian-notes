# Spring、Spring Boot 与 MyBatis（401-425）

## 401. IoC 和 DI 分别是什么？

### 面试时可以这样答

> IoC 是把对象创建、依赖装配和生命周期控制交给容器；DI 是实现 IoC 的主要方式，由容器把依赖通过构造器、工厂方法或属性注入对象。业务类因此面向抽象协作，不需要自己查找和创建依赖。
>
> 我优先使用构造器注入，因为依赖明确、可设为 final，也便于单元测试。依赖过多通常不是改成字段注入的理由，而是类职责需要拆分的信号。

## 402. BeanFactory 和 ApplicationContext 有什么区别？

### 面试时可以这样答

> BeanFactory 是 IoC 容器的基础接口，提供 Bean 获取和依赖装配；ApplicationContext 在其上增加事件、国际化、资源加载、环境配置及企业级集成。Spring 应用日常使用的通常是 ApplicationContext。
>
> 默认情况下，ApplicationContext 会在启动阶段预实例化非懒加载单例，因此配置错误较早暴露；懒加载 Bean 则可能到首次获取时才失败。这是启动速度与提前校验之间的取舍。

## 403. Spring Bean 的生命周期是什么？

### 面试时可以这样答

> 典型过程是实例化、属性填充、Aware 回调、BeanPostProcessor 初始化前处理、`@PostConstruct` 或初始化方法、初始化后处理，最后 Bean 可用；容器关闭时执行 `@PreDestroy` 或销毁方法。代理通常在后置处理阶段产生。
>
> 实际排查要区分原始对象与最终暴露对象，尤其是事务和异步代理。不要在构造器里做依赖尚未就绪的重操作，也不要假设 prototype Bean 的销毁由容器完整管理。

## 404. BeanPostProcessor 和 BeanFactoryPostProcessor 的区别是什么？

### 面试时可以这样答

> BeanFactoryPostProcessor 在普通 Bean 创建前修改 BeanDefinition 等容器元数据；BeanPostProcessor 围绕每个 Bean 的初始化执行，可包装或替换实例，AOP 自动代理就依赖这一扩展点。
>
> 前者处理“如何定义 Bean”，后者处理“最终交付哪个对象”。实现时要避免在容器后处理阶段过早获取普通 Bean，否则可能打乱后处理器注册和代理创建顺序。

## 405. Spring Bean 有哪些常见作用域？

### 面试时可以这样答

> singleton 是每个容器一个实例，prototype 是每次获取创建新实例；Web 环境还有 request、session、application 和 websocket 等作用域。单例只描述容器中的实例数量，不自动保证线程安全。
>
> 将短生命周期 Bean 注入单例时通常需要作用域代理或 ObjectProvider，使每次调用解析当前对象。直接注入一个已创建实例会丢失预期的作用域语义。

## 406. Spring 如何解决循环依赖？

### 面试时可以这样答

> 构造器相互依赖没有可用的半成品对象，容器会报 `BeanCurrentlyInCreationException`。经典单例 setter/字段循环依赖可通过提前暴露对象引用解决，涉及早期引用和代理一致性；这不是所有作用域和所有配置都支持。
>
> 工程上应先拆职责、引入中介服务或领域事件消除环，而不是依赖容器技巧。循环依赖常意味着边界不清，也会让初始化和测试更脆弱。

## 407. Spring AOP 的实现原理是什么？

### 面试时可以这样答

> Spring AOP 主要在运行期用代理拦截方法调用：有接口时可用 JDK 动态代理，也可使用基于子类的 CGLIB 代理。Advisor 把切点和通知组合起来，代理调用链依次执行事务、日志等拦截器后再进入目标方法。
>
> 它主要针对 Spring Bean 的方法执行，不等同于完整 AspectJ 字节码织入。final 类、final 方法、对象自行 new 出来以及代理内部自调用都可能绕开预期拦截。

## 408. 为什么同类内部调用会导致 @Transactional 失效？

### 面试时可以这样答

> 声明式事务通常由代理在方法入口开启。外部调用先经过代理，但 `this.inner()` 是目标对象内部直接调用，没有再次穿过代理，因此 inner 上的事务注解不会独立生效。
>
> 更好的修复是按事务边界拆到另一个 Bean，或让外部入口承载事务。通过暴露代理再自调会增加耦合，只适合明确理解其代价的场景。

## 409. Spring 事务的传播行为如何理解？

### 面试时可以这样答

> REQUIRED 有事务就加入、没有就新建；REQUIRES_NEW 总是挂起外层并新建；NESTED 在支持时用保存点嵌套；SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER分别表达可选、暂停、必须有和必须没有事务。
>
> 传播行为要从失败语义选，而不是背枚举。例如审计记录若必须独立提交可考虑 REQUIRES_NEW，但它会额外占连接，外层回滚后还留下记录也必须符合业务预期。

## 410. @Transactional 默认在什么情况下回滚？

### 面试时可以这样答

> 默认对 RuntimeException 和 Error 回滚，对受检异常通常不回滚，可用 `rollbackFor` 调整。异常若在方法内部被捕获后正常返回，代理看不到失败，也不会自动回滚。
>
> 事务边界还受代理调用方式影响。排查“不回滚”时依次检查是否经代理、方法可否被代理、异常是否被吞、回滚规则、传播行为和数据库引擎是否支持事务。

## 411. 事务隔离级别和传播行为有什么区别？

### 面试时可以这样答

> 隔离级别约束并发事务彼此能看到什么，解决脏读、不可重复读和幻读等问题；传播行为决定一个业务方法进入时如何加入或创建事务。前者主要由数据库实现，后者由 Spring 事务拦截器编排。
>
> 两者会共同影响结果，但不能互相替代。开一个 REQUIRES_NEW 不会自动提升隔离性，提高隔离级别也不能修复代理自调用导致的事务缺失。

## 412. Spring MVC 一次请求的主流程是什么？

### 面试时可以这样答

> 请求先到 DispatcherServlet，它通过 HandlerMapping 找到处理器与拦截器链，再由 HandlerAdapter 完成参数解析并调用控制器。返回值由 ReturnValueHandler 处理，可能经消息转换器写成 JSON，或交给视图解析器渲染。
>
> 异常会进入 HandlerExceptionResolver 链。排查 400、415、406 等问题时，要分别看参数绑定、请求 Content-Type、可用消息转换器和客户端 Accept，而不是都归因于 Controller 未命中。

## 413. Filter、Interceptor 和 AOP 怎么选？

### 面试时可以这样答

> Filter 属于 Servlet 层，可处理所有进入容器的请求与响应，适合编码、CORS、基础安全；Interceptor 位于 Spring MVC 处理器链，能拿到 Handler，适合鉴权和请求上下文；AOP 围绕 Bean 方法，适合服务层事务、审计和通用耗时。
>
> 选择依据是需要拦截的边界。技术交流平台的接口耗时若要关联用户和控制器信息，可由拦截器建立 MDC，上层 AOP记录服务方法，但必须在 finally 清理线程本地上下文。

## 414. @Autowired 按什么规则注入？

### 面试时可以这样答

> 首先按类型寻找候选；多个候选时可结合 `@Primary`、`@Qualifier`、名称和优先级消歧。构造器只有一个时可省略 `@Autowired`。集合注入会得到匹配类型的多个 Bean。
>
> 候选不唯一不应靠碰巧匹配字段名维持。应通过清晰的接口、限定符或配置类表达选择规则，让重构名称时不会悄悄改变依赖。

## 415. Spring Boot 自动配置的核心思路是什么？

### 面试时可以这样答

> 自动配置根据 classpath、已有 Bean、配置属性和应用类型等条件，选择性注册一组默认 Bean。它遵循“用户配置优先”：常见自动配置带 `@ConditionalOnMissingBean`，开发者声明同类型 Bean 后默认实现退让。
>
> 排查时应查看条件评估报告，确认某配置为什么匹配或未匹配，而不是盲目排除整个自动配置。自动配置减少样板代码，但仍是可检查、可覆盖的普通配置。

## 416. @SpringBootApplication 包含哪些能力？

### 面试时可以这样答

> 它组合了配置类声明、自动配置启用和组件扫描。默认扫描从启动类所在包向下，因此启动类位置不当会导致组件漏扫，扫描范围过大也可能引入不期望的 Bean。
>
> 多模块项目应明确包边界，必要时用显式扫描或 `@Import` 组合配置。不要把启动类移动后出现的注入失败误认为自动配置失效。

## 417. Spring Boot 配置的优先级应如何处理？

### 面试时可以这样答

> 配置可来自默认文件、profile 文件、环境变量、系统属性和命令行等，后加载或更高优先级来源可以覆盖低优先级值。相比大量 `@Value`，结构化配置更适合用 `@ConfigurationProperties` 做类型绑定和校验。
>
> 运维上要能追踪最终值来自哪里，并避免把密钥提交进仓库。对关键配置在启动时校验，缺失就快速失败，比运行到业务路径才出现空值更可靠。

## 418. Spring Boot Starter 的价值是什么？

### 面试时可以这样答

> Starter 是一组有意组合的依赖入口，配合依赖管理和自动配置，让使用者不必逐项寻找兼容版本。它本身往往几乎没有代码，真正行为来自被引入的库与自动配置模块。
>
> 自定义 starter 应把依赖入口、配置属性和自动配置职责分清，提供条件化默认 Bean，并写上下文加载测试验证“有依赖启用、用户覆盖退让、缺依赖不生效”。

## 419. 如何设计统一异常处理？

### 面试时可以这样答

> 用 `@RestControllerAdvice` 和分层的 `@ExceptionHandler` 把领域异常、参数错误和未知异常映射为稳定错误码与 HTTP 状态。响应给调用方的信息要可行动，但不能泄露堆栈、SQL 或内部路径。
>
> 日志端保留 traceId、异常链和关键业务标识；同一异常只在有处理责任的边界记录一次，避免每层重复打印。未知异常返回通用提示，同时告警并保留完整证据。

## 420. MyBatis 的 `#{}` 和 `${}` 有什么区别？

### 面试时可以这样答

> `#{}` 生成预编译参数占位符，由 JDBC 绑定值，能正确处理类型并降低注入风险；`${}` 是字符串直接替换，常用于无法参数化的表名或排序字段，但输入若可控就可能形成 SQL 注入。
>
> 动态排序应把客户端值映射到服务端白名单列名，不能把原始字符串塞进 `${}`。普通条件和值一律优先 `#{}`。

## 421. MyBatis 一级缓存和二级缓存是什么？

### 面试时可以这样答

> 一级缓存属于 SqlSession，同一会话内相同查询可复用结果，更新会使相关缓存失效；二级缓存属于 mapper namespace，可跨 SqlSession，但需要显式配置并面对序列化、一致性和多节点问题。
>
> 在 Spring 事务外每次调用可能使用不同会话，一级缓存效果不能想当然。复杂系统通常把一致性策略放到明确的业务缓存层，而不是依赖不易观察的二级缓存。

## 422. MyBatis 的 Mapper 接口为什么不需要实现类？

### 面试时可以这样答

> 启动时 MapperScanner 找到接口并注册 FactoryBean，最终生成代理对象。调用接口方法时，代理根据“接口全名加方法名”定位 MappedStatement，构造参数、执行 SQL，再通过结果映射返回对象。
>
> 因此接口方法与 XML statement id、参数名和返回类型必须一致。所谓“没有实现类”并非没有实现，而是运行时代理把调用转换成了持久化执行。

## 423. MyBatis 如何处理动态 SQL？

### 面试时可以这样答

> XML 的 if、choose、where、set、foreach 等节点会根据参数生成最终 SQL；where/set 能智能处理多余 AND 和逗号，foreach 常用于批量条件。动态性越强，越要关注最终生成 SQL 而不是只看模板。
>
> 我会为关键分支写集成测试，覆盖空集合、全部条件为空和批量上限，并在开发环境观察 SQL 与执行计划，避免条件缺失导致全表更新或超长 IN 列表。

## 424. MyBatis 如何避免 N+1 查询？

### 面试时可以这样答

> N+1 是先查一批主记录，再为每条记录单独查询关联数据，往返次数随结果数增长。可根据数据规模选择 join 一次查出、分两次批量 IN 查询后内存组装，或专门的聚合查询。
>
> 不能简单把所有关联都 join，因为一对多会放大行数并干扰分页。应记录 SQL 次数和总耗时，用真实基数决定批量加载策略。

## 425. MyBatis-Plus 提高效率时有哪些边界？

### 面试时可以这样答

> 它提供通用 CRUD、条件构造器、分页和代码生成，减少样板代码，但不会替代索引设计、事务边界和 SQL 审查。复杂查询仍应写清晰 SQL，并用执行计划验证。
>
> Wrapper 条件要防止空参数漏掉约束，分页插件要确认方言与 count SQL，逻辑删除和自动填充也应有数据库约束兜底。便利 API 不能成为隐藏业务规则的地方。
