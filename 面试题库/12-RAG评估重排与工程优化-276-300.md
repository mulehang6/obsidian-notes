# RAG：评估、重排与工程优化（276-300）

## 276. 如何判断 RAG 系统效果好不好？

### 面试时可以这样答

> 要把检索和生成分开评估。检索看 recall@k、precision@k、MRR、NDCG 和证据覆盖率；生成看答案正确性、是否忠于证据、引用是否准确和拒答是否合理。线上再看首 token 延迟、总耗时、失败率、成本和用户反馈。
>
> 只凭几次人工聊天觉得“回答不错”无法比较版本。需要固定问题集、期望证据和评分规则。

## 277. 如何构建 RAG 评测集？

### 面试时可以这样答

> 从真实文档和用户问题抽样，标注问题、可接受答案、支持答案的 chunk 或文档，以及无答案问题。覆盖精确名词、语义改写、多文档归纳、时间敏感和权限隔离场景。
>
> 训练调参集与最终测试集分开，防止针对少量题过拟合。线上失败案例定期回流，但加入前要人工清洗。

## 278. Recall@k 和 Precision@k 怎么理解？

### 面试时可以这样答

> Recall@k 看所有相关证据中有多少进入前 k，适合衡量漏召回；Precision@k 看前 k 中有多少真正相关，反映噪声。RAG 常先保证召回，再用重排提高精度，但过多噪声会干扰模型。
>
> 指标依赖相关性标注。若一个问题有多段互补证据，只标一段会低估系统。

## 279. 如何区分是检索错还是模型生成错？

### 面试时可以这样答

> 先检查正确证据是否进入候选和最终 prompt。没召回是检索问题；候选有但重排丢掉是排序问题；prompt 已有清楚证据，模型仍答错或编造，才是生成和提示问题。
>
> 每次请求应记录 query、各路候选、融合排名、最终上下文和引用映射。没有这条链，只看最终答案很难定位。

## 280. 什么是 reranker？

### 面试时可以这样答

> 首阶段检索追求快速召回，reranker 用更精细模型对 query 与候选逐对评分，再选少量结果。Cross-encoder 同时编码问题和文档，相关性通常优于向量点积，但计算更贵。
>
> 常见做法是先召回几十条，再重排到 5 到 10 条。候选太少救不回漏召回，太多则增加延迟和费用。

## 281. MMR 解决什么问题？

### 面试时可以这样答

> 最大边际相关性在相关度与结果多样性之间取舍。若 topK 都来自同一段的重叠 chunk，模型得到大量重复信息。MMR 会惩罚与已选内容过于相似的候选。
>
> 多样性权重过大又会选入不相关文档。它适合去重复，不替代相关性阈值。实现时还要决定用 embedding 相似度还是文档来源重合衡量冗余，并在同一评测集上调节权重。

## 282. Query Rewrite 有什么价值和风险？

### 面试时可以这样答

> 多轮对话中的“它怎么配置”缺少实体，先结合历史改写成独立问题，检索更准确。还可以统一缩写、补充同义词和纠正拼写。
>
> 改写模型可能改变用户意图。应保留原 query，同时检索原始与改写版本，日志中展示改写结果，敏感过滤不能只依赖改写文本。代词指代不明确时，宁可向用户澄清也不要强行补全实体。

## 283. Multi-query 检索怎么做？

### 面试时可以这样答

> 让模型生成几个不同表达或子问题，各自检索，再用 RRF 合并。它能提高复杂问题和词汇不匹配场景的召回。
>
> 查询数会线性增加 embedding 与 ES 请求，也可能扩散错误意图。只对低置信或复合问题启用，并限制并发和候选总量。融合前应对同一文档片段去重，避免多次命中被错误当成多份证据。

## 284. HyDE 是什么？

### 面试时可以这样答

> HyDE 先让模型生成一段假设答案，再对假设文本做 embedding，用它去检索真实文档。答案式文本有时比短问题更接近文档表达。
>
> 假设答案可能带偏检索，尤其是专有事实。可以与原 query 向量并行召回，不要把假设内容当真实证据交给最终模型。是否启用应以困难查询子集的召回提升能否覆盖额外模型成本为依据。

## 285. 对话历史为什么不能全部塞进 Prompt？

### 面试时可以这样答

> 历史越长，token 成本和延迟越高，早期无关内容还会稀释当前问题。项目笔记中的基础方案是 Redis 保存全部或近期消息，实际请求取最近 20 条，再控制检索 chunk 和输出上限。
>
> 仅按条数截断不精确。更好的是按 token 预算保留最近轮次、长期摘要和被当前问题命中的重要记忆。

## 286. 为什么对话历史使用 Redis List？

### 面试时可以这样答

> 消息天然有顺序，List 可以 RPUSH 追加，用 LRANGE 读取末尾若干条，实现简单。key 由用户和会话组成，消息序列化为带 role、content 和时间的 JSON。
>
> 并发写入时还要保证一轮用户消息与助手消息的顺序，设置 TTL 和最大长度。持久历史仍应落数据库，Redis 更适合快速上下文窗口。

## 287. 字符数估算 token 靠谱吗？

### 面试时可以这样答

> 笔记中的 `UsageQuotaService` 按 ASCII、CJK 和其他 Unicode 乘经验系数，再加固定开销。它计算快，适合粗略预算，但不同 tokenizer、代码、标点和模型会产生明显误差。
>
> 临近上下文上限时应使用目标模型 tokenizer 或保留足够安全余量。经验估算可以做预警，不能作为精确计费依据。

## 288. 上下文压缩有哪些方案？

### 面试时可以这样答

> 可以保留最近轮次并总结较早内容，给消息做重要性评分，把长期事实写入外部记忆，或针对当前 query 重新检索历史。摘要应保留用户约束、已做决定和未完成事项。
>
> 摘要会丢信息，最好保存原历史和摘要覆盖范围。达到阈值后异步生成新摘要，比每轮全量总结更省成本。

## 289. 如何减少 RAG 幻觉？

### 面试时可以这样答

> 先提高证据质量，再在 prompt 中要求基于编号资料回答、缺少证据就说明不知道，并让每个关键结论带引用。生成后可以检查引用编号是否存在，或用第二阶段验证结论是否被证据支持。
>
> temperature 降低只能减少随机性，不能补回没召到的事实。幻觉治理首先是检索和证据约束问题。

## 290. 如何设计“无法回答”？

### 面试时可以这样答

> 当候选低于相关度阈值、证据互相冲突或缺少回答所需字段时，系统应返回资料不足，并给出缺失内容或建议用户补充问题。不要为了完整句子让模型猜。
>
> 阈值要用无答案问题集校准。过高会大量拒答，过低会编造，不能凭一个固定分数跨索引使用。回答层还应区分“完全无证据”和“只缺少部分条件”，给用户可执行的补充方向。

## 291. 引用如何做到可验证？

### 面试时可以这样答

> Prompt 中为每个 chunk 分配稳定引用 ID，并携带 documentId、页码或章节。模型输出引用后，后端只接受本轮上下文中存在的 ID，再映射成可点击来源。
>
> 不能让模型自己生成 URL 或页码。引用存在也不代表结论被支持，还要检查句子与引用内容的一致性。

## 292. 文档更新后如何保证索引一致？

### 面试时可以这样答

> 为文档建立版本。新版本在独立状态下解析和写入，全部 chunk 成功后原子切换 activeVersion，再异步删除旧版本。查询只过滤 active 版本。
>
> 直接先删旧索引再写新数据会出现不可检索窗口；覆盖写又可能留下旧版多余 chunk。版本切换更容易回滚。

## 293. 删除文档要处理哪些数据？

### 面试时可以这样答

> 要删除或标记原文件、文档记录、ES chunks、embedding 缓存和权限关联，并考虑 Redis 中已缓存的检索结果。异步删除应有任务状态和重试。
>
> 用户要求立即不可见时，先在权限或 active 标志上同步屏蔽，物理清理可以稍后完成。仅删 MinIO 文件会让向量内容继续被检索。

## 294. 如何做检索缓存？

### 面试时可以这样答

> 可缓存 query embedding，key 包含模型版本和规范化文本；也可缓存检索结果，但 key 必须包含用户权限、索引版本和检索参数。否则 A 用户的结果可能泄露给 B 用户。
>
> 文档更新和权限变化会让缓存失效。RAG 缓存最危险的不是命中率低，而是返回过期或越权证据。

## 295. 断点续传如何使用 Redis Bitmap？

### 面试时可以这样答

> 上传任务把分片序号作为 offset，成功后 SETBIT 为 1。重连时读取缺失位，只传失败分片；服务端确认全部位为 1 后调用 MinIO 合并。Bitmap 底层利用 String 的位操作，空间开销小。
>
> 仍需校验分片摘要、总数、文件 ID 和过期时间。只看 bit 为 1 无法证明分片内容正确。

## 296. Bitmap 方案如何处理并发和过期？

### 面试时可以这样答

> SETBIT 本身原子，但“检查全部完成再合并”是组合操作，多个请求可能同时触发。可用状态机加条件更新或短锁保证只合并一次。任务 key 要设置 TTL，成功后清理。
>
> 分片总数和文件摘要应存独立元数据，防止复用旧 key 或客户端改变上传计划。合并成功应通过数据库唯一状态或版本号成为最终事实，Redis bitmap 只承担加速协调而不是唯一凭据。

## 297. Kafka 消息积压怎么办？

### 面试时可以这样答

> 先看生产速率、消费延迟和具体耗时阶段。可增加分区与消费者，但 embedding 服务限流可能才是真正瓶颈，盲目扩消费者只会放大重试。大文件任务还可能造成分区头阻塞。
>
> 需要监控 lag、单任务耗时、失败类型和下游配额。必要时按文件大小分队列或限制上传并发。

## 298. WebSocket 与 SSE 怎么选？

### 面试时可以这样答

> 只需要服务端把模型 token 推给浏览器时，SSE 基于 HTTP，重连和代理兼容通常更简单。WebSocket 是全双工，适合客户端在同一连接中发送停止、反馈或交互事件。
>
> 项目选 WebSocket 支持流式对话，但不能说 SSE 无法由客户端发请求，客户端仍可用普通 HTTP。比较的是持续连接方向和工程复杂度。

## 299. RAG 链路应记录哪些可观测数据？

### 面试时可以这样答

> 每次请求记录 traceId、query 改写、embedding 延迟、各路候选 ID 与分数、过滤数量、融合排名、最终上下文 token、模型首 token 与总延迟、引用和错误类型。敏感正文只在受控采样中保留。
>
> 指标要能把慢拆到解析、检索、重排和生成，而不是只有一个总耗时。

## 300. 如何防止检索内容中的提示注入？

### 面试时可以这样答

> 文档是数据，不是可信指令。系统 prompt 明确标记引用块，告诉模型忽略其中要求改变规则、调用工具或泄露信息的文本。高风险工具仍由程序权限控制，绝不因检索文档说“已获授权”就放行。
>
> 还可扫描明显注入模式、限制文档来源、对生成结果做敏感信息检查。单靠一句 prompt 不能构成安全边界。
