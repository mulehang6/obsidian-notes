# MySQL、事务、索引与优化（426-450）

## 426. 为什么 InnoDB 通常比 MyISAM 更适合业务系统？

### 面试时可以这样答

> InnoDB 支持事务、行级锁、崩溃恢复、MVCC 和外键，适合并发读写与强一致业务；MyISAM 不支持事务，主要使用表级锁。现代 MySQL 的默认引擎也是 InnoDB。
>
> 选择不能只看“查询快”。订单、用户和内容状态更新更需要故障恢复与并发控制，性能要通过索引、SQL 和架构优化，而不是用放弃事务换取未经验证的速度。

## 427. 事务的 ACID 如何落到 InnoDB？

### 面试时可以这样答

> 原子性依靠 undo log 回滚未完成修改；一致性是约束、事务逻辑与恢复机制共同维持的结果；隔离性由锁和 MVCC 提供；持久性主要依靠 redo log、刷盘策略和崩溃恢复。
>
> ACID 不是应用无需负责一致性。数据库只能保证声明的约束和事务内操作，跨服务副作用、错误事务边界或遗漏唯一约束仍会破坏业务不变量。

## 428. redo log、undo log 和 binlog 的区别是什么？

### 面试时可以这样答

> redo log 是 InnoDB 物理层面的重做信息，用于崩溃恢复；undo log 保存旧版本，用于回滚和 MVCC；binlog 是 Server 层逻辑变更日志，用于复制和时间点恢复。
>
> 提交时 InnoDB 与 binlog 需要协调，避免一个持久化而另一个缺失。排障应先明确目标是实例恢复、事务可见性还是复制，而不是把三种日志混为一谈。

## 429. MVCC 是什么？

### 面试时可以这样答

> MVCC 让一致性读基于事务可见性读取某个版本，而不是和写操作普遍互斥。InnoDB 聚簇记录包含事务相关隐藏信息，并通过 undo 链重建旧版本，Read View 决定哪些版本可见。
>
> MVCC 主要服务快照读；`SELECT ... FOR UPDATE` 等锁定读仍会加锁。长事务会阻碍旧版本清理并放大 undo，因此要监控事务时长而不只是连接数。

## 430. READ COMMITTED 和 REPEATABLE READ 有何差异？

### 面试时可以这样答

> READ COMMITTED 通常每条一致性读生成新的 Read View，同一事务两次查询可能看到不同已提交结果；REPEATABLE READ 通常在事务内复用快照，使重复读保持一致。InnoDB 默认常为 RR。
>
> 隔离级别还影响锁范围，例如 RR 下范围锁定读常用 next-key lock 防止插入。选择应兼顾一致性语义与冲突成本，不能认为级别越高总越好。

## 431. 快照读和当前读有什么区别？

### 面试时可以这样答

> 普通 SELECT 在合适隔离级别下通常是快照读，按 Read View 读取可见版本；UPDATE、DELETE、INSERT 以及 `FOR UPDATE`、`FOR SHARE` 是当前读，要读取最新可锁定记录并参与锁竞争。
>
> 如果业务要“查库存后扣减”，只做快照读再更新可能产生竞态。可用条件更新 `UPDATE ... SET stock=stock-1 WHERE stock>0`，或在明确事务中锁定读。

## 432. 脏读、不可重复读和幻读是什么？

### 面试时可以这样答

> 脏读是读到尚未提交的数据；不可重复读是同一行前后值变化；幻读是按同一条件再次查询，结果集合出现或消失了行。它们描述的是不同并发异常，不应只背隔离级别表格。
>
> InnoDB 的 RR 通过 MVCC 让快照读保持一致，并通过 next-key lock 约束锁定范围。混用快照读和当前读时仍要分析具体语句，不能笼统说“RR 完全没有幻读”。

## 433. InnoDB 有哪些常见锁？

### 面试时可以这样答

> 有表级意向锁、记录锁、间隙锁和 next-key lock 等。意向锁表达事务准备在表内行上加何种锁，便于表级冲突判断；next-key lock 是记录锁与前方间隙锁组合。
>
> InnoDB 的“行锁”依赖索引记录。范围扫描或缺少合适索引时可能锁住大量记录和间隙，所以锁冲突问题也常是索引与 SQL 问题。

## 434. 什么是间隙锁和 next-key lock？

### 面试时可以这样答

> 间隙锁锁住索引记录之间的区间，主要阻止其他事务在范围内插入；next-key lock 同时覆盖某条索引记录和它之前的间隙。RR 下范围锁定读常借此防止结果集合出现新行。
>
> 精确命中唯一索引时通常只需锁具体记录，非唯一或范围条件更可能扩大锁范围。优化死锁时应检查查询到底扫描了哪些索引区间。

## 435. MySQL 死锁为什么无法完全避免？

### 面试时可以这样答

> 并发事务以不同顺序持有并等待资源就可能成环。InnoDB 检测到死锁后会选择一个事务回滚，让其他事务继续；即使代码看似顺序一致，扫描计划与索引范围变化也可能改变实际加锁顺序。
>
> 应统一资源访问顺序、缩短事务、建立合适索引并对死锁错误做有限重试。重试必须保证操作幂等，并记录死锁日志分析根因，不能无限循环掩盖设计问题。

## 436. 为什么 B+ 树适合数据库索引？

### 面试时可以这样答

> B+ 树分支多、树高低，可减少磁盘或页访问；数据或主键指针集中在叶子层，叶子按序连接，既支持等值查找也支持范围扫描。相比普通二叉树，它更匹配页式存储。
>
> 性能仍取决于键宽度、选择性和访问模式。过宽索引降低单页扇出并增加缓存与写放大，因此索引不是越多越好。

## 437. 聚簇索引和二级索引有什么区别？

### 面试时可以这样答

> InnoDB 聚簇索引叶子存整行数据，通常由主键组织；二级索引叶子存索引列和主键值。用二级索引查询非覆盖列时，通常先得到主键再回聚簇索引取行，也就是回表。
>
> 因此主键过大会膨胀所有二级索引。设计主键时通常偏好短、稳定且递增，但是否使用业务主键仍要结合分布式生成和查询模式。

## 438. 什么是覆盖索引？

### 面试时可以这样答

> 若查询所需的过滤、排序和返回列都能从一个索引获得，就不必回表，这个索引对该查询是覆盖索引。EXPLAIN 的 Extra 里常见 `Using index`，但仍要结合扫描行数判断成本。
>
> 不能为了覆盖所有查询不断堆列。应优先覆盖高频且性能敏感的访问，并评估索引体积、写入开销和缓存命中率。

## 439. 联合索引的最左前缀原则是什么？

### 面试时可以这样答

> 联合索引按列顺序形成有序键，可有效利用从最左列开始的连续前缀。跳过首列通常无法直接定位后续列的连续范围；遇到范围条件后，后续列用于继续缩小扫描范围的能力也可能受限。
>
> 列顺序要同时考虑等值条件、范围、排序、选择性和覆盖需求。不能只按“区分度最高放最左”这一条口诀决定。

## 440. 哪些写法容易让索引失效？

### 面试时可以这样答

> 常见情况包括对索引列做无法改写的函数或计算、隐式类型转换、前导通配符、联合索引缺失左前缀，以及选择性太差导致优化器主动全表扫描。`OR` 是否失效也取决于可用索引和代价。
>
> “失效”不等于语法禁止，而是访问路径不再高效。最终以 EXPLAIN 和实际执行统计为准，不靠固定清单猜测。

## 441. 如何理解索引下推？

### 面试时可以这样答

> 索引下推让存储引擎在遍历二级索引时就检查可由索引列判断的条件，先过滤不符合的记录，再决定是否回表，减少回表次数。
>
> 它不能替代合理的联合索引，也不保证扫描索引项变少。分析时要区分扫描了多少索引记录、回表多少次以及最终返回多少行，并用执行计划确认 Extra 中的下推信息。

## 442. EXPLAIN 重点看哪些字段？

### 面试时可以这样答

> 重点看访问类型、实际选择的 key、使用的 key_len、估算 rows、filtered 和 Extra，再结合表连接顺序。全表扫描不一定错误，小表或返回比例很高时可能是合理选择。
>
> 估算计划只能说明优化器判断，条件允许时还应看 EXPLAIN ANALYZE 的实际行数与耗时。估算和实际差距很大时，要检查统计信息、数据倾斜和谓词相关性。

## 443. count(*)、count(1) 和 count(列) 有什么区别？

### 面试时可以这样答

> `count(*)` 统计行数，`count(1)` 语义上也是对每行非空常量计数，现代优化器通常能等价处理；`count(列)` 不统计该列为 NULL 的行。性能不能用“星号会取整行”解释。
>
> 大表实时精确计数可能代价高，应根据一致性要求选择索引扫描、汇总表或近似指标，并处理并发更新下的误差边界。

## 444. 深分页为什么慢？如何优化？

### 面试时可以这样答

> `LIMIT offset, size` 仍要定位并跳过前 offset 行，若还伴随回表和排序，offset 越大成本越高。可采用基于稳定排序键的游标翻页，例如记录上一页的 `(created_at,id)` 后继续范围查询。
>
> 游标必须能唯一确定顺序，否则同时间值会漏行或重复。若产品必须跳任意页，可先用覆盖索引取主键再关联回表，并限制最大可访问页数。

## 445. 慢 SQL 应如何排查？

### 面试时可以这样答

> 先从慢日志和链路定位具体 SQL、参数分布与频率，再看执行计划、实际扫描行数、锁等待和返回数据量。随后检查索引、统计信息、隐式转换、排序临时表及上游 N+1。
>
> 优化后要用同分布数据压测，并观察 P95/P99 和写入代价。只在测试库跑一次快查询，或只看到“用了索引”，都不足以证明优化有效。

## 446. 为什么不建议长事务？

### 面试时可以这样答

> 长事务会长期持锁，扩大冲突与死锁窗口；其 Read View 还可能阻碍旧版本清理，使 undo 膨胀。连接被长时间占用也会压缩系统并发容量。
>
> 应把远程调用、用户交互和大批量计算移出数据库事务，批处理分段提交并设计幂等恢复。缩短事务时仍要确保业务不变量没有被拆坏。

## 447. 乐观锁和悲观锁怎么选？

### 面试时可以这样答

> 悲观锁在操作前锁定记录，适合冲突概率高且失败重试代价大的场景；乐观锁用版本号或条件更新，提交时检测冲突，适合读多写少、重试可接受的场景。
>
> 乐观锁更新后必须检查受影响行数，失败后重新读取并有限重试。悲观锁则要控制事务时长、访问顺序和超时，不能在持锁期间调用不可靠的外部服务。

## 448. 唯一索引为什么仍然需要应用层幂等？

### 面试时可以这样答

> 唯一索引是并发条件下可靠的最终防线，可原子拒绝重复业务键；应用层预检查只能改善提示，检查与插入之间仍有竞争窗口。
>
> 接口应把幂等键落到唯一约束，并将重复键异常映射为“已处理”或冲突。若请求还会产生消息和外部副作用，需要事务消息或 outbox 等更完整方案。

## 449. 主从复制延迟会造成什么问题？

### 面试时可以这样答

> 写入主库后立即读从库可能读不到新数据，导致用户看到回退状态，甚至基于旧值重复操作。延迟还会受大事务、慢 SQL 和从库资源影响，不是固定毫秒数。
>
> 需要读己之写的路径可短期读主库、携带位点等待追平，或在业务层保持新状态；普通列表可接受最终一致。策略应按接口语义区分，而不是全量强制读主。

## 450. 如何设计数据库表和索引的评审清单？

### 面试时可以这样答

> 我会检查主键与业务唯一键、字段类型和 NULL 语义、金额精度、时间与时区、状态约束、预期数据量和保留策略；再从真实查询反推联合索引、排序与覆盖关系。
>
> 还要评估写放大、冷热数据、迁移兼容、回滚方案和监控。上线前用接近生产的数据分布验证执行计划，而不是只在几十行样例数据上确认“能跑”。
