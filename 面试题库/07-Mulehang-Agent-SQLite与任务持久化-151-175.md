# Mulehang Agent：SQLite 与任务持久化（151-175）

## 151. 为什么桌面 Agent 选择 SQLite？

### 面试时可以这样答

> 项目数据属于单机用户，任务、时间线和模型历史需要结构化查询，但没必要部署独立数据库。SQLite 是单文件、事务完整，JDBC 接入简单，适合随桌面应用分发。它比散落 JSON 文件更容易保证任务元数据与子项一起提交，也能按工作区和更新时间查询。
>
> 代价是并发写能力有限，schema 迁移需要自己管理。当前写入由协调器串行化，符合单窗口桌面应用的负载。

## 152. 数据库为什么拆成四张业务表？

### 面试时可以这样答

> `task` 保存标题、工作区、Profile、权限、执行状态以及会话树元数据；`task_timeline_item` 保存 UI 时间线；`task_history_item` 保存下一轮模型需要的历史；`task_entry` 保存会话内条目图的 id、parentId、类型和 JSON 负载。前三张有序子表用 taskId 加 sequence 作为联合主键，条目图用 taskId 加 entryId 标识节点。
>
> 时间线与模型历史看起来相似，但用途不同。UI 可以保存 diff、状态和展示文本，模型历史必须满足消息协议。若只存一份再互相推导，任何展示调整都可能破坏重放语义。

## 153. 为什么 timeline 和 history 都要保存 sequence？

### 面试时可以这样答

> Agent 事件的意义依赖顺序。工具调用必须先于结果，推理和正文也有先后。数据库不能依赖默认行顺序，因此保存显式 sequence，加载时 `ORDER BY sequence`。
>
> 联合主键还能阻止同一任务出现重复序号。Session Tree 不能只依赖线性 sequence：当前实现用 `task_entry(id, parent_id, created_at, type, payload_json)` 保存完整条目图，并在 `task` 上保存 `active_entry_id` 与 `head_entry_id`，因此兄弟分支可以共存，活动路径再投影成时间线和模型历史。

## 154. `saveAll` 为什么在一个事务里先删再重建？

### 面试时可以这样答

> 当前仓库保存的是整个 UI 任务集合快照。事务内先清空 task，再逐个插入任务、时间线、模型历史和 `task_entry` 条目图，能让删除、新增、更新与分支元数据同时生效。任一步失败就 rollback，不会留下只写了一半的任务。
>
> 这种实现简单，但任务很多时写放大会明显。后续可按 updatedAt 做 upsert，并单独删除缺失任务。不过增量方案要更认真地处理子项替换和并发版本。

## 155. 为什么删除任务能自动清理时间线和历史？

### 面试时可以这样答

> 时间线、模型历史和 `task_entry` 都通过外键引用 task，并配置 `ON DELETE CASCADE`。每次连接还执行 `PRAGMA foreign_keys = ON`，否则 SQLite 默认可能不启用外键约束。删除主任务后，时间线、历史和完整条目图由数据库原子清理。
>
> 测试专门验证级联删除，原因不只是整洁。时间线可能包含工具输出和敏感路径，留下不可见孤儿数据属于隐私问题。

## 156. 为什么启用 WAL？

### 面试时可以这样答

> `PRAGMA journal_mode = WAL` 让读者和写者更少互相阻塞，适合 UI 可能读取历史、后台同时保存快照的桌面场景。提交记录先进入 WAL，之后再 checkpoint 到主文件。
>
> WAL 不是无需管理。备份主库前必须先 checkpoint，否则最新事务可能仍在 WAL 文件中。项目迁移备份前执行 `wal_checkpoint(FULL)` 正是为了得到完整副本。

## 157. 为什么数据库操作放到 `Dispatchers.IO`？

### 面试时可以这样答

> JDBC 是阻塞 API，连接、查询和磁盘写入都可能卡住线程。仓库方法用 `withContext(Dispatchers.IO)`，避免阻塞 Compose UI 或 Agent 协程的默认线程。
>
> 切到 IO 不会自动解决并发覆盖，所以协调器还用 Mutex 串行保存。线程调度和数据一致性是两个问题，不能混在一起回答。

## 158. 为什么每次打开连接都执行迁移？

### 面试时可以这样答

> 仓库通过 `schema_migration` 记录已应用版本，打开连接时计算待执行迁移。操作必须幂等，已经记录的版本不会重复执行。这样应用升级后首次访问数据库即可完成 schema 对齐。
>
> 当前项目频繁打开连接，重复检查有少量成本但逻辑直接。若改成长连接，可在仓库初始化阶段迁移一次，同时处理多进程竞争。

## 159. 为什么迁移前要备份数据库？

### 面试时可以这样答

> `ALTER TABLE` 或迁移代码出错可能让用户历史无法恢复。项目只在已有 task 表且存在待迁移版本时备份，避免全新数据库产生无意义副本。备份前先做 WAL checkpoint，再复制主库。
>
> 备份只保留最近三份，防止每次升级无限占用磁盘。文件备份是最后保险，仍不能替代事务和迁移测试。

## 160. 迁移为什么也必须放在事务里？

### 面试时可以这样答

> 一个版本可能执行多条 DDL 和数据修复。若第三条失败而前两条已生效，迁移日志与实际 schema 会分叉。项目在事务内执行待迁移步骤，完成后再写版本记录；异常时 rollback。
>
> SQLite 对多数 DDL 支持事务，但具体操作仍要验证。复杂重建表迁移应在真实旧库副本上测试，不只测空数据库。

## 161. 当前有哪些 schema 版本？

### 面试时可以这样答

> v1 创建 task、timeline、history 和工作区更新时间索引；v2 增加 profileId 与 permissionPreset；v3 增加 workspaceName；v4 增加 detached workspace 的路径和名称；v5 增加外层会话树字段、`task_entry` 条目图和父指针索引；v6 增加 `head_entry_id`，并把已有树会话的 active leaf 回填为 head。旧库缺失字段时按顺序补齐。
>
> 默认权限写成 `DEFAULT`，老数据因此能安全恢复。迁移测试会手工建立 v1 数据库，再验证字段、原行和备份保留。

## 162. 为什么要给旧数据设置安全默认值？

### 面试时可以这样答

> 新版本增加 permissionPreset 后，旧任务没有该字段。若默认成 BRAVE，恢复后可能获得比原来更高的权限。迁移选择 DEFAULT，Mapper 遇到未知枚举也回退 DEFAULT。
>
> 推理档位的未知值回退 MEDIUM。兼容默认值要分别从安全和用户预期判断，不能统一取枚举第一项。

## 163. 为什么保存完整工具输出和原始 reasoning？

### 面试时可以这样答

> 完整快照能在重启后还原时间线，并为下一轮模型构造合法历史。只保存 UI 截断预览，会丢失工具结果或 callId，继续对话时可能改变语义。测试明确验证原始 reasoning 和完整工具输出可以往返。
>
> 这也带来隐私压力。原始输出可能含密钥或文件内容，需要明确存储位置、删除语义和未来的脱敏策略。

## 164. 为什么附件信息存成 JSON？

### 面试时可以这样答

> 附件结构包含类型、路径、媒体 ID、MIME 和标签，字段可能继续演进。当前把附件列表作为 JSON 放在 task 行中，省去额外表和 join，适合每个任务附件数量不大的情况。
>
> JSON 字段不适合按附件属性查询，也缺少数据库级字段约束。若以后需要全局媒体清理、去重或搜索，应拆成独立表。

## 165. Snapshot Mapper 为什么单独存在？

### 面试时可以这样答

> UI 状态包含 Compose 需要的类型，数据库模型强调稳定存储格式。`ChatTaskSnapshotMapper` 负责双向转换，把变化隔离在边界。仓库不需要依赖 UI，UI 也不直接拼 SQL。
>
> Mapper 还是兼容策略所在，例如未知权限回退、运行中状态在重启后转成中断错误。把这些规则散落在页面初始化里很难测试。

## 166. 为什么未知 JSON 类型选择拒绝恢复？

### 面试时可以这样答

> 对历史消息和输入片段，未知 type 可能意味着数据库损坏或新版本格式被旧程序读取。若静默跳过，工具调用与结果可能失配，恢复出来的对话看似正常但语义已经改变。
>
> 当前做法是抛出明确错误。更友好的版本可以隔离损坏任务并继续加载其他任务，但不能偷偷丢字段后当成成功。

## 167. 应用重启后为什么不继续此前正在运行的 Agent？

### 面试时可以这样答

> 数据库保存了时间线、模型历史、会话条目图以及 active/head leaf，但没有保存 Koog 图节点、在途网络请求、工具进程和审批 continuation。仅凭 UI 快照无法安全地从原位置继续。因此 Mapper 把 RUNNING、等待输入和等待审批统一恢复为“执行已中断”的 Failed；树路径和内容可以恢复，不等于运行可以续接。
>
> 真正的断点续跑需要持久化执行状态机、幂等工具信息和外部副作用确认，不能只把状态字符串改回 Running。

## 168. 为什么保存要做 300ms debounce？

### 面试时可以这样答

> 流式文本可能每几十毫秒更新一次，若每个 token 都重写完整任务集合，SQLite 写入和 JSON 编码会拖慢 UI。协调器取消前一个延迟任务，静默 300ms 后保存最新快照。
>
> debounce 会形成短暂未落盘窗口，所以应用关闭或关键动作需要 `flush`。300ms 是体验与写放大的折中，应以真实事件频率评估。

## 169. 为什么持久化要在历史加载完成后才激活？

### 面试时可以这样答

> 应用启动时 UI 可能先有一个空状态，再异步读取数据库。如果此时自动保存，空快照会先执行 `DELETE FROM task`，把历史覆盖掉。协调器只有在旧任务成功恢复到窗口状态后才把 `persistenceEnabled` 设为 true。
>
> 这是典型初始化竞态。不能靠“读取通常更快”解决，必须让状态机显式区分未加载和已加载。

## 170. 为什么使用 Mutex 串行保存？

### 面试时可以这样答

> debounce 任务可能在开始写入后又收到新状态。取消协程不一定能中断已经进入 JDBC 的阻塞操作。若两个完整快照并发写，较旧任务可能后提交并覆盖新内容。
>
> `writeMutex.withLock` 保证保存顺序串行。要进一步防旧快照覆盖，还可以给快照增加单调版本，写入前比较版本。

## 171. 为什么取消旧的保存任务不报错？

### 面试时可以这样答

> 连续状态更新时，协调器主动取消前一个 debounce Job，这是正常调度，不是用户数据保存失败。`shouldReportTaskPersistenceError` 因此排除 `CancellationException`，其他异常才提示“任务保存失败”。
>
> 仍然要重新抛出取消或正确结束协程，不能为了不弹错误把所有 Throwable 都吞掉。

## 172. `flush` 应该在什么时候用？

### 面试时可以这样答

> 窗口关闭、应用退出或需要立即确认持久化的动作前，应取消延迟任务并保存当前快照，完成后再执行关闭回调。未激活持久化时可以直接回调，避免启动阶段误写。
>
> flush 也可能失败，关闭流程要决定是否提示、重试或仍然退出。当前回调模型需要保证异常不会让窗口永远无法关闭。

## 173. 为什么任务按 `updated_at DESC, id` 排序？

### 面试时可以这样答

> 主排序把最近活动任务放在前面，符合侧边栏预期。相同时间戳时再按 id，结果稳定，测试和 UI 不会因数据库返回顺序变化而抖动。
>
> schema 还建立 workspacePath 与 updatedAt 的联合索引，为按工作区筛选和最近更新时间查询预留效率。若时间精度可能相同，稳定的次排序键也能保证游标分页不漏项、不重复。

## 174. SQLite 持久化最需要关注哪些故障？

### 面试时可以这样答

> 包括磁盘满、数据库锁、迁移失败、文件损坏、旧版本读取新格式、应用被强制结束和敏感内容长期残留。事务只能处理部分一致性问题，不能解决磁盘与版本兼容。
>
> 我会保留迁移前备份、显示保存失败、测试旧库升级，并提供导出与重建入口。不要在读取失败后自动用空库覆盖原文件。

## 175. 如何测试这套持久化？

### 面试时可以这样答

> 仓库测试用临时目录和真实 SQLite 文件，验证完整往返、排序、级联删除、非默认 Profile 与权限，以及条目图字段。迁移测试手工创建 v1、v4、v5 旧 schema，打开新仓库后检查数据、树格式默认值、v6 head 回填和备份数量。
>
> Mapper 测试还应覆盖每种时间线、消息 part、附件和未知枚举。协调器用虚假仓库验证 debounce、激活门槛、串行写和 flush，而不是靠 UI 手测。
