# Mulehang Agent：架构与执行循环（026-050）

这一卷回答“你究竟做了一个什么 Agent，以及它为什么不是普通聊天界面”。答案以当前本地源码为准。口述时不需要背类的完整包名，但必须能解释关键数据如何流动。

## 026. 请你完整介绍一下 Mulehang Agent 项目

### 面试时可以这样答

> Mulehang Agent 是我用 Kotlin 做的本地桌面 Agent。我想解决的不是单轮聊天，而是让模型围绕一个任务持续规划、调用工具、观察结果，再决定下一步。一次运行会接收用户提示词、模型配置、推理配置、历史消息、工作区、权限预设和运行时资源，然后由 Koog 的图执行策略驱动模型与工具交替运行。执行过程中，底层不会直接操作界面，而是持续产出文本增量、工具开始与完成、文件差异预览、审批请求、状态和失败等统一事件，UI 再消费这些事件。
>
> 我在这个项目中重点处理了三个问题。第一，如何把 Agent 循环写成可理解、可测试的状态图，而不是把所有逻辑塞进一个循环。第二，如何保证工具成功或失败后，消息历史仍满足模型 API 对工具调用配对的要求。第三，如何划清权限和运行资源的边界，例如一次运行开始后冻结其 prompt、MCP 服务和版本信息，避免热更新让同一条执行链前后语义不一致。
>
> 所以这个项目的价值不只是“接了大模型接口”，而是把模型、工具、权限、事件流和桌面交互组织成一个能持续演进的运行时。当前我会把已经落地的能力和设计中的能力分开介绍，不会把尚未核实的 Session Tree 等功能说成已经完成。

### 面试官继续追问

- **它最核心的类是什么？** 当前执行主线可以从 `KoogStreamingStrategy` 看起，它负责创建 `AIAgent`、装配事件处理器和图策略。
- **你个人做了什么？** 不要泛答“负责后端”。按自己真实工作选择图策略、流式事件、工具历史、权限或持久化中的具体部分，并说明一次实际问题和验证方式。

## 027. 你为什么要做这个项目？普通聊天客户端不够吗？

### 面试时可以这样答

> 普通聊天客户端的核心是“输入一段文本，输出一段文本”，但代码任务或桌面任务往往需要多步操作。例如先搜索文件，再读源码，再修改，最后运行测试。模型每一步都必须看到上一步工具返回的结果，还要在写文件或执行高风险命令前遵守权限策略。只做聊天 UI，难点会被掩盖在一堆回调里，无法清楚回答运行状态、失败恢复和权限控制。
>
> 我做这个项目，是想把 Agent 的工程问题拆开：模型只负责给出下一步意图，工具层负责执行受控动作，图策略负责决定状态如何迁移，事件层负责把过程暴露给 UI，持久化层负责保存任务和快照。这样即使以后更换模型提供商、增加 MCP 工具或改变界面，核心执行语义也不必一起推倒重来。
>
> 这也带来代价。系统比聊天客户端复杂得多，需要处理工具调用与结果的配对、长任务取消、迭代上限、敏感配置和部分失败。因此我不会把“Agent”当成营销标签，而是把它定义为一个能基于环境反馈多步行动、并受运行时约束的系统。

### 面试官继续追问

- **如果只调用一次检索工具算不算 Agent？** 名字不重要。若流程由业务代码固定编排，它更接近带工具的工作流；若模型根据观察结果动态决定后续动作，才更接近这里讨论的 Agent。
- **什么时候不该用 Agent？** 步骤固定、强确定性、可直接写成事务或工作流的场景，优先用普通程序，成本和可测试性都更好。

## 028. 这个项目为什么算 Agent，而不只是带函数调用的聊天应用？

### 面试时可以这样答

> 判断标准不在于有没有 `tools` 参数，而在于系统是否形成“决策、行动、观察、再决策”的闭环。Mulehang Agent 中，模型节点先生成普通回复或工具调用。如果产生工具调用，图会进入执行工具节点；工具结果随后作为新的上下文送回模型，模型可以结束，也可以继续请求另一个工具。下一步不是业务代码预先写死的，而是由模型结合历史和工具结果决定，同时又受到图边、权限和最大迭代次数约束。
>
> 函数调用只是模型表达行动意图的协议。真正让它成为 Agent 运行时的，是外围的执行循环、状态管理、工具注册、错误结果回填、审批机制和可观察事件。如果没有这些，模型即使生成了函数名和参数，也没有可靠的机制去执行、反馈或终止。
>
> 我也不会把自主性说得过头。它不是无限自主的系统，能做什么由注册工具决定，是否允许执行由权限策略决定，运行多久由迭代限制、取消和异常共同决定。更准确的说法是“受约束的多步 Agent”。

### 面试官继续追问

- **自主性越高越好吗？** 不是。生产系统通常要限制工具集合、参数、工作目录和审批点，让模型只在明确边界内选择步骤。
- **如何证明存在闭环？** 直接画出 `LLM -> Tool -> Tool Result -> LLM` 的状态迁移，并说明工具失败时也必须产生可回放的结果。

## 029. 请你画一下 Mulehang Agent 的核心架构

### 面试时可以这样答

> 我会把它分成五层。第一层是输入与配置，`AgentRunRequest` 聚合提示词、Profile、推理级别、历史、工作区、权限预设、会话 ID 和运行时资源。第二层是模型与 Agent 执行器，当前由 Koog 的 `AIAgent` 和自定义图策略承担。第三层是工具层，`ToolRegistry` 统一提供内置工具和扩展工具，MCP 资源也在运行开始前解析进来。第四层是运行时策略，包括权限判断、最大迭代次数、失败处理和资源快照。第五层是呈现与持久化，统一的 `AgentStreamEvent` 被 UI 消费，任务与快照再写入本地存储。
>
> 依赖方向上，我希望上层界面依赖稳定的事件和请求模型，而不是直接依赖 Koog 内部事件。这样框架升级或替换时，变化可以被限制在适配层。工具也不应该知道 Compose UI 如何显示结果，它只返回结构化执行结果。权限判断则要放在真正执行动作之前，不能只靠 prompt 告诉模型“请不要做危险操作”。

### 可以顺手画出的数据流

```text
AgentRunRequest
      ↓
运行资源快照 + ToolRegistry + 权限策略
      ↓
Koog AIAgent / Graph Strategy
      ↓
LLM 调用 ⇄ 工具执行
      ↓
AgentStreamEvent
      ↓
Compose UI / 持久化 / 日志
```

### 面试官继续追问

- **为什么事件模型单独一层？** 它隔离框架事件与产品语义，也让 UI、测试和日志观察同一套状态变化。
- **哪一层最容易失控？** 工具执行层，因为它真正触碰文件、进程和网络，需要同时处理权限、超时、输出截断和失败回填。

## 030. 一次 Agent 运行从开始到结束经历什么？

### 面试时可以这样答

> 入口拿到 `AgentRunRequest` 后，先解析当前 Profile 的迭代次数和本次固定的运行资源，再准备模型执行器、工具注册表以及连接界面的桥接对象。随后创建 Koog `AIAgent`，把 system prompt、用户 prompt、历史、模型和自定义 graph strategy 装进去，并注册事件处理器。
>
> 图从开始节点进入流式 LLM 节点。这里一边收集模型输出，一边把文本增量发给界面。如果最终只得到普通文本，就进入结束节点；如果得到一个或多个工具调用，就转到工具执行节点。工具开始、完成或失败都会映射为内部事件。执行结果进入“发送工具结果”节点，再交给模型判断是结束还是继续调用工具。这个循环受最大迭代次数约束，也可能被用户取消或不可恢复异常中断。
>
> 结束时不能只关心最终文本。系统还要确保已产生的消息历史完整、UI 收到完成或失败事件、需要持久化的状态被保存，并释放本次运行持有的资源。面试时我会特别说明：工具失败不一定等于整个 Agent 失败，它可以作为一条观察结果反馈给模型，但前提是协议历史仍然完整。

### 面试官继续追问

- **用户中途修改配置会怎样？** 当前运行使用启动时的资源快照，不应被热更新改变；新配置作用于下一次运行。
- **多个工具调用怎么处理？** 需要看图节点和工具执行器的具体语义，不能未经源码确认就宣称一定并行。

## 031. 什么是 ReAct？你的项目是怎么体现的？

### 面试时可以这样答

> ReAct 的核心不是固定格式的“Thought、Action、Observation”三行文本，而是让推理与行动交替发生。模型根据当前上下文决定行动，环境返回观察结果，模型再基于新信息继续判断。它解决的是模型不能仅靠参数知识完成外部世界任务的问题。
>
> 在我的项目里，`call_llm_streaming` 节点承担决策，工具执行节点承担行动，工具结果消息就是观察，`send_tool_results_streaming` 再把观察交回模型。图边把这几步连成循环。普通文本响应会结束本轮，工具调用会进入执行分支，工具结果之后既可能结束，也可能再次进入工具分支。
>
> 不过我不会声称能看到模型完整的内部思维链。系统能记录的是模型公开输出、结构化工具调用、工具结果以及部分提供商支持的 reasoning 事件。工程上真正需要的是可验证的行动轨迹，而不是要求模型暴露私有推理过程。

### 面试官继续追问

- **ReAct 的问题是什么？** 循环可能过长、重复调用、被错误观察带偏，也可能产生高成本，需要迭代上限、工具描述、错误反馈和终止条件。
- **能否不用 ReAct？** 可以。固定流程适合工作流，复杂规划也可用 plan-and-execute；选择取决于任务不确定性。

## 032. ReAct 和 Function Calling 有什么区别？

### 面试时可以这样答

> 两者不在同一层。Function Calling 是模型与程序之间的结构化通信协议，模型输出工具名和参数，程序执行后再回传工具结果。ReAct 是一种让推理与行动交替进行的任务策略。Function Calling 可以作为 ReAct 中“行动”的实现方式，但单次 Function Calling 并不自动形成 ReAct 循环。
>
> 举例来说，用户问天气，模型调用一次天气工具并直接总结，这只是很短的工具增强问答。用户要求修改项目并验证时，模型可能先搜索文件、读取实现、修改文件、运行测试，根据失败信息再次修改，这才明显体现多步行动和观察。我的项目通过 graph strategy 让 Function Calling 的结果能够重新进入模型节点，因此协议能力被组织成了执行循环。
>
> 工程风险也不同。Function Calling 主要关注 schema、参数校验和调用结果配对；ReAct 还需要处理循环终止、上下文膨胀、重复动作、错误恢复和权限升级。

### 面试官继续追问

- **JSON 格式正确就能直接执行吗？** 不能。还要做 schema 校验、业务校验、路径与权限检查，危险动作可能需要人工批准。
- **工具描述重要吗？** 很重要。名称、用途、参数边界和返回语义会直接影响模型的工具选择质量。

## 033. 只要模型会调用工具，就能称为 Agent 吗？

### 面试时可以这样答

> 我不会用一个绝对定义去争论名称，而会看系统具备哪些能力。最低限度要有目标、环境行动、观察反馈和下一步决策。再往工程化走，还需要状态、终止条件、权限和错误处理。如果程序无论输入是什么都固定调用同一个工具，再把结果交给模型总结，它本质上是确定性工作流，不需要强调 Agent。
>
> Mulehang Agent 中，模型可以依据工具结果选择继续或结束，工具集合和权限构成行动边界，图保存控制流，事件模型暴露运行过程。因此它满足“受约束的多步 Agent”这个更具体的描述。但它不是通用自主智能体，也没有必要把每一个检索或函数调用都包装成 Agent。
>
> 这个区分对架构选择有实际意义。固定工作流更可预测、便宜、容易测试；只有当步骤确实取决于中间结果、分支难以提前穷举时，引入 Agent 循环才有收益。

### 面试官继续追问

- **工作流和 Agent 能混合吗？** 可以。常见做法是在确定性工作流的某个节点内使用 Agent，或让 Agent 只能选择经过审核的工作流。
- **如何衡量是否值得？** 比较成功率、调用成本、耗时、人工介入率和不可预测失败，而不是只看演示效果。

## 034. 为什么选择 JetBrains Koog？

### 面试时可以这样答

> 这个项目本身使用 Kotlin，并且是桌面端工程，所以我优先考虑对 Kotlin 类型系统、协程和多平台生态更自然的框架。Koog 提供 `AIAgent`、工具注册、事件处理以及图式 Agent 等抽象，我可以把精力放在运行语义、权限和 UI 事件上，而不是自己从 HTTP 协议开始拼一个循环。
>
> 我最看重的是它允许显式定义 graph strategy。节点表示具体动作，边表达控制流和数据流，工具调用、工具结果和结束条件可以直接映射到状态图。它也提供 Agent persistence 的概念，可以在节点之后创建检查点。这些能力与桌面 Agent 需要的可观察、可恢复方向契合。
>
> 选择框架不代表把核心逻辑全部交给框架。我仍然定义了自己的 `AgentRunRequest`、`AgentStreamEvent` 和资源快照，并为流式消息历史做了自定义节点。这样既利用 Koog 的执行能力，又避免产品层被它的内部类型完全绑死。

### 面试官继续追问

- **Koog 的风险是什么？** 生态和 API 仍可能变化，需要适配层、回归测试和版本锁定；不能只因它是 Kotlin 框架就忽略成熟度。
- **为什么不自己写？** 简单循环可以自己写，但工具协议、图状态、事件与持久化细节会快速膨胀。自研应当针对差异化部分，而不是重复所有底层能力。

## 035. 为什么不用 LangChain 或 LangGraph？

### 面试时可以这样答

> LangChain 和 LangGraph 并不是能力不足，它们在 Python 生态、组件数量和资料积累上更成熟。我的选择主要受项目边界影响：桌面应用主体是 Kotlin，如果把 Agent 核心放到 Python，就要额外维护进程通信、部署、类型协议和生命周期；如果为了框架改变整个技术栈，收益未必覆盖复杂度。
>
> Koog 让我在同一个 Kotlin 工程里共享请求模型、协程、工具接口和事件类型，调试链路也更短。对这个项目来说，这是比“插件数量最多”更重要的约束。另一方面，LangGraph 的显式状态图、检查点和人工介入能力仍然值得对比学习，我会把它作为设计参照，而不是为了证明自己的选择就贬低替代方案。
>
> 如果团队已有稳定的 Python Agent 服务、需要大量成熟集成，或者 Agent 要独立扩缩容，我会重新评估 LangGraph。技术选择应跟组织能力和部署形态一起决定。

### 面试官继续追问

- **这是技术偏好还是工程选择？** 应回答可量化约束：语言边界、部署单元、团队栈、调试成本和需要的框架能力。
- **将来如何替换框架？** 保持请求、事件、工具和权限模型属于项目自身，在 Koog 外围建立适配边界。

## 036. 为什么不用 Spring AI？

### 面试时可以这样答

> Spring AI 很适合已经以 Spring Boot 为核心的服务端应用，尤其是统一模型客户端、向量库、检索增强和企业配置管理。Mulehang Agent 的主体是 Kotlin 桌面应用，我更需要的是本地长任务、流式界面事件、图式工具循环和桌面生命周期，而不是把它部署成一个 Spring 容器里的后端服务。
>
> 如果强行引入 Spring AI，可能会获得熟悉的依赖注入和模型抽象，但也会增加容器启动、依赖体积以及桌面端与服务端模型之间的摩擦。Koog 与 Kotlin 协程和图 Agent 的结合对当前目标更直接。
>
> 这不意味着两者只能二选一。若以后把 RAG、用户管理或集中式模型网关拆成服务端，Spring AI 可以承担服务层能力，桌面端仍通过明确协议调用。选择依据是模块职责，而不是对框架站队。

### 面试官继续追问

- **什么情况下会换到 Spring AI？** 当核心形态变成 Spring 服务，且企业集成、可观测、向量库或模型网关能力比桌面内嵌更重要时。
- **能同时使用吗？** 可以，但要避免两套抽象同时管理同一条 Agent 状态，边界应当清晰。

## 037. 什么是 Graph Agent？它解决了什么问题？

### 面试时可以这样答

> Graph Agent 把执行过程表示为节点和边。节点执行模型请求、工具调用或业务动作，边根据节点结果决定下一步，并传递需要的数据。它把原本藏在回调和条件分支中的控制流显式化。
>
> 对多步 Agent 来说，这至少有三个好处。第一，可读，看到图就能知道模型、工具和结束之间如何迁移。第二，可测试，可以针对某个节点、某条边和特定结果编写用例。第三，可扩展，未来加入审批、压缩上下文或检查点时，可以增加节点和边，而不是不断加深一个巨大循环的嵌套。
>
> 但图不是免费的。节点数据类型、错误传播和状态一致性都需要设计，小任务如果只有一次模型调用，图反而是过度工程。我的项目使用图，是因为核心流程天然存在重复工具调用、失败反馈和多种结束路径。

### 面试官继续追问

- **图一定是 DAG 吗？** 不是。Agent 需要循环，`LLM -> Tool -> LLM` 本身就包含环。
- **图和有限状态机一样吗？** 很接近，但图节点还可以携带并转换业务数据，框架通常也提供更丰富的执行上下文。

## 038. 你项目里的执行图具体有哪些节点和边？

### 面试时可以这样答

> 当前主线可以概括为三个业务节点。`call_llm_streaming` 负责流式请求模型并收集助手消息；工具执行节点负责执行模型给出的工具调用；`send_tool_results_streaming` 把工具结果写回上下文并再次流式请求模型。
>
> 从开始节点先进入 LLM 节点。若 LLM 返回最终文本，就转到结束；若包含工具调用，就进入工具节点。工具完成后进入发送工具结果节点。模型收到工具结果后，如果给出最终答案就结束，如果又产生工具调用则再次进入工具节点。由此形成受控循环。
>
> 这里最值得讲的不是节点名称，而是边的条件代表业务语义：普通回答和工具调用必须分流，工具结果之后也必须再次判断。若把所有输出无条件送到工具节点，普通文本会被误处理；若工具结果直接结束，Agent 就失去了多步能力。

### 面试官继续追问

- **工具失败走哪条边？** 失败也要形成结构化工具结果或失败事件，并保持调用与结果配对，再由上层决定能否继续；不能把异常直接吞掉。
- **多个工具调用如何表示？** 要以实际节点返回的数据结构为准，回答时不要假定框架一定串行或并行。

## 039. 为什么不直接写一个 `while` 循环？

### 面试时可以这样答

> 最小版本确实可以用 `while`：调用模型，发现工具请求就执行，再把结果加入历史，直到模型返回文本。问题是功能增加后，循环会同时承担状态迁移、流式输出、审批、失败恢复、取消、持久化和 UI 通知，很快变成难以验证的控制中心。
>
> 图策略让每个节点只处理一类动作，边负责表达迁移条件。例如审批可以插在工具执行前，消息压缩可以放在模型调用前，检查点可以放在节点完成后。这些变化不必全部挤进同一组嵌套判断。
>
> 不过我不会把图说成天然更高性能。它主要改善结构、可观察性和扩展性，也会增加抽象和学习成本。如果任务只有两步且不会增长，一个清晰的循环反而更合适。

### 面试官继续追问

- **循环版本最容易出什么 bug？** 工具结果漏写、异常后状态不完整、取消只停 UI 不停后台、结束条件互相覆盖。
- **图就不会出这些问题吗？** 仍会。图只是让状态和路径更显式，还需要不变量和回归测试。

## 040. 你为什么要自定义 Koog 的 Graph Strategy？

### 面试时可以这样答

> 默认能力可以快速跑通，但产品需要的流式事件和消息历史语义更具体。我的策略需要在模型生成过程中向 UI 发文本增量，还要把工具开始、完成、失败等 Koog 事件映射为项目自己的事件类型。更关键的是，当前 Koog 的流式请求不会自动把最终 assistant message 写回 prompt，因此自定义 LLM 节点在流结束后显式更新历史。
>
> 如果忽略这一步，界面可能已经显示了模型说过的话，但下一次工具调用后的模型上下文里缺少这条 assistant message，UI 状态和模型状态就分叉。对于要求工具调用与结果严格配对的模型接口，这还可能直接导致请求被拒绝。
>
> 所以自定义策略不是为了重复框架代码，而是把项目必须保证的不变量放到一个可控位置：流式输出可见、历史完整、边的终止条件明确。对应行为需要用回归测试锁住，因为框架升级后默认行为可能变化。

### 面试官继续追问

- **升级 Koog 后怎么办？** 先检查相关 API 和默认历史行为，再运行工具历史与流式回归测试，不能只看能否编译。
- **为什么不在 UI 层补历史？** UI 不是 Agent 状态的权威来源，后台运行或无界面测试也必须得到同样的历史语义。

## 041. 你如何理解 Agent 的“状态”？

### 面试时可以这样答

> Agent 状态不只是聊天消息。至少包括会影响下一步决策的消息历史、当前节点和节点输出、已注册工具、本次运行配置、权限上下文、迭代计数，以及需要持久化或展示的任务状态。不同状态的生命周期也不同：消息随会话演进，运行资源在一次 run 内固定，UI 的临时加载状态则不应成为业务真相。
>
> 我会区分三类。第一是模型状态，也就是 prompt 和工具调用结果，它直接影响下一次生成。第二是控制状态，例如当前图节点、是否取消、还剩多少迭代。第三是产品状态，例如任务记录、文件差异预览和审批请求。把三者混在一个可变对象里，很容易让 UI 操作意外改变模型行为。
>
> 设计上的关键是不变量。例如每个 `function_call` 必须有对应的 `function_call_output`；一次运行读取到的资源版本保持不变；结束事件只能表示真正的终态。这些不变量比“用了状态机”这个术语更重要。

### 面试官继续追问

- **哪些状态必须持久化？** 取决于恢复目标。若只恢复对话，保存消息即可；若要从节点继续，还要保存图位置、节点输入输出和兼容版本。
- **UI 状态能否直接作为 Agent 状态？** 不建议。UI 可以投影运行状态，但不应成为执行语义的唯一来源。

## 042. Agent 在什么情况下结束？

### 面试时可以这样答

> 正常结束是模型在 LLM 节点或收到工具结果后给出最终消息，并且没有新的工具调用，图于是进入结束节点。除此之外还有多种非正常终止：达到最大迭代次数、用户取消、模型请求失败、工具或框架抛出不可恢复异常、进程退出等。
>
> 工具单次失败不应该自动等同于整个任务失败。系统可以把失败原因作为工具结果反馈给模型，让它修改参数、换工具或向用户说明。但如果失败来自权限拒绝、资源不可用或连续重复动作，继续循环可能没有意义，需要由策略终止或请求人工介入。
>
> 完成状态也必须区分“成功完成”“取消”“达到上限”和“异常失败”。如果 UI 都显示成“结束”，用户无法判断结果是否可信，持久化恢复也会失去语义。

### 面试官继续追问

- **如何防止模型说完答案后仍继续？** 边条件必须以结构化输出是否包含工具调用为准，而不是用自然语言关键词猜测。
- **达到上限后给用户什么？** 保留已产生的事件和中间结果，明确说明因迭代限制停止，不应伪装成正常完成。

## 043. 为什么需要 `maxIterations`？

### 面试时可以这样答

> 大模型可能因为工具描述不清、错误结果、目标不可达或自身判断偏差而重复调用。没有迭代上限时，一个简单任务可能持续消耗 token、网络请求和本地资源，甚至反复修改文件。`maxIterations` 是运行时保险丝，不是任务质量优化本身。
>
> 当前创建 `AIAgent` 时，会把 Profile 中配置的次数解析后传入 `.maxIterations(...)`。合理的上限应结合任务类型、工具平均步骤和成本来定。只把上限设得很小，会让正常的多步代码任务被截断；设得很大又无法及时阻止死循环，因此还应结合重复调用检测、超时、取消和成本预算。
>
> 达到上限后，系统应留下可诊断信息，例如最后节点、最近几次工具调用和停止原因。否则用户只会看到“失败”，开发者无法区分任务确实复杂还是 Agent 卡在循环中。

### 面试官继续追问

- **上限能防住所有失控吗？** 不能。单次工具也可能长时间阻塞，还需要超时和取消；高成本模型也可能在少量迭代内产生高费用。
- **如何动态设置？** 可以按 Profile、任务类型或风险级别设置，但应有全局硬上限和可观测指标。

## 044. 项目里的 `-1` 无限迭代是真正无限吗？

### 面试时可以这样答

> 不是数学意义上的无限。项目把配置值 `-1` 解释为“不主动使用普通次数限制”，传给 Koog 时转换为 `Int.MAX_VALUE`。这是一个方便用户理解的配置语义，底层仍然是有限整数。
>
> 即使迭代计数几乎不会触顶，运行仍可能因为用户取消、模型上下文上限、进程关闭、网络异常、工具超时或不可恢复错误而结束。因此面试时我会说“无限模式取消了常规迭代限制”，不会说“保证永远运行”。
>
> 这个模式也不适合作为默认安全策略。若允许无人值守长时间运行，还应增加总耗时、token 或费用预算，检测连续相同工具调用，并对写文件、执行命令等高风险动作保留审批。

### 面试官继续追问

- **为什么不用 nullable 表示无限？** `-1` 便于配置文件和 UI 表达，但需要集中解析，避免业务代码到处判断魔法数字。
- **`Int.MAX_VALUE` 会溢出吗？** 正常运行几乎到不了，但计数实现仍应由框架保证；业务不能把它当永不溢出的证明。

## 045. 为什么项目规定最小迭代次数为 50？

### 面试时可以这样答

> 当前 `AgentIterationLimit` 把最小值和默认值都设为 50，低于 50 的正数配置会被判为无效。这反映出项目更偏向多步编码或桌面任务，避免用户误把上限设成很小，导致正常流程刚完成搜索和读取就被截断。
>
> 但“50”不是通用理论值，也不等于每个任务都会执行 50 次。它是当前产品策略，需要结合真实任务分布验证。如果多数任务 5 到 10 步就完成，那么强制最小 50 主要是在约束配置，而不是节省资源；如果要面向轻量问答，允许更小的 Profile 可能更合理。
>
> 我会通过迭代次数分位数、达到上限的任务比例、成功率和平均成本来重新评估这个值。面试中承认它是经验参数，并说明如何用数据校准，比硬说“50 最合理”更可信。

### 面试官继续追问

- **限制太小和太大各有什么表现？** 太小会出现大量可恢复任务被截断，太大则让错误循环持续更久。
- **默认值与硬上限一样吗？** 不一样。默认值是用户未配置时的选择，硬上限是系统不允许超过的安全边界。

## 046. 默认 `AIAgent` 与自定义 Graph Strategy 如何分工？

### 面试时可以这样答

> `AIAgent` 提供运行容器，负责接收模型、工具注册表、prompt、最大迭代次数和策略等依赖；Graph Strategy 则描述这次运行具体如何在节点之间流转。可以把前者理解为执行引擎，后者理解为可执行流程定义。
>
> 我的代码没有重写整个 Agent 框架，而是在创建 `AIAgent` 时注入自定义策略，并通过 `handleEvents` 订阅框架事件。这样模型调用、工具机制等基础能力仍由 Koog 提供，项目只定制流式节点、消息写回、边条件和产品事件映射。
>
> 这种分工比直接 fork 框架更容易升级，但适配层仍然依赖 Koog API。需要通过小范围封装和回归测试控制依赖面，尤其关注消息历史、事件顺序和失败工具调用这些语义，而不仅是接口是否改名。

### 面试官继续追问

- **为什么不继承一个大类覆写方法？** 组合策略能让执行流程更显式，也减少对框架内部继承层次的耦合。
- **哪些能力属于项目自身？** 请求、事件、权限和资源快照应由项目定义；底层模型与图执行可以由框架承载。

## 047. 流式输出是怎么实现的？

### 面试时可以这样答

> 流式输出不是把最终字符串切成几段，而是在模型提供商返回增量时就逐步消费。自定义 LLM 节点发起 streaming 请求，收集返回片段，并把可展示的文本转换为 `TextDelta` 等项目事件交给 UI。节点同时要累积出完整的 assistant message，因为后续消息历史和图边判断不能只依赖界面已经显示的碎片。
>
> 代码里还设置了约 300 毫秒的状态提示时机，用来处理模型尚未产生正文时的等待感。这类提示只能是呈现层状态，不能伪造模型内容。流结束后，节点显式把完整 assistant message 写回 prompt，再返回给图继续判断是结束还是执行工具。
>
> 实现时要关注取消和背压。用户取消后，不能只停止 UI 更新而让网络请求继续；UI 消费较慢时，也不能无限积压事件。错误发生时还要保留已经收到的部分输出，并明确标记最终状态不是正常完成。

### 面试官继续追问

- **为什么既发增量又保存完整消息？** 增量服务交互体验，完整消息服务下一轮模型上下文和持久化，两者职责不同。
- **如何处理 Markdown 被拆开？** UI 应支持增量缓冲和重新解析，不能假设每个 chunk 都是完整语法单元。

## 048. 为什么要定义自己的 `AgentStreamEvent`？

### 面试时可以这样答

> 框架事件反映 Koog 的内部生命周期，产品事件反映 UI 和业务真正关心的语义，两者不应直接等同。项目定义的 `AgentStreamEvent` 包括开始、文本增量、工具开始与完成、文件差异预览、工具失败、标准输出与错误输出、提问、审批、状态、推理片段、完成和失败等。UI 只需要依赖这些稳定事件，不必知道 Koog 的具体类型。
>
> 这层适配有三个价值。第一，降低框架耦合，Koog 事件变化时只改映射。第二，统一不同来源，例如内置工具、MCP 工具和模型流都能投影到同一条时间线。第三，便于测试，可以给定底层事件后断言产品层产生什么，而不用启动完整界面。
>
> 事件模型也要避免歧义。`ToolCallFailed` 表示单次工具失败，注释明确它不必立即终止整次运行；`Failed` 才表示运行级失败。若 UI 把两者都显示为任务结束，就破坏了领域语义。

### 面试官继续追问

- **事件和状态有什么区别？** 事件描述已经发生的变化，状态是事件处理后的当前投影；事件不应被随意覆盖。
- **会不会丢事件？** 要根据流实现决定缓冲和持久化策略，关键终态不能只依赖临时 UI 订阅。

## 049. 为什么流式请求后还要手动把 assistant message 写回历史？

### 面试时可以这样答

> 因为“界面收到文本”不代表“模型上下文已经更新”。当前实现的注释明确指出，Koog 的 `requestLLMStreaming` 不会自动把 assistant message 写入 prompt。自定义节点因此一边收集流，一边构造完整消息，流结束后显式更新 prompt。
>
> 如果漏掉这一步，下一轮只看到用户消息和工具结果，却看不到模型此前发出的工具调用或文字。对于 Function Calling 协议，更严重的问题是 `function_call` 与 `function_call_output` 可能不再成对。有些模型服务会直接返回类似“找不到某个 tool call 的输出”的 400 错误。
>
> 项目里的失败工具历史回归测试就是在保护这个不变量：即使连续多个工具都失败，每个调用也必须有对应输出，重放历史时仍是合法序列。这说明错误路径不能简单抛异常后跳过历史写入。

### 面试官继续追问

- **为什么工具失败也要写 output？** 对模型来说，失败也是环境观察；协议上它还负责闭合前一个工具调用。
- **可以只在数据库里修复吗？** 不行。下一次模型请求前内存中的 prompt 就必须合法，持久化只能记录，不能代替运行时不变量。

## 050. 为什么一次运行开始后要冻结运行时资源？

### 面试时可以这样答

> `AgentRuntimeResources` 保存版本、system prompt 附加内容和 MCP 服务配置，并明确把它定义为一次运行固定的资源集合。原因是 Agent 可能执行很久，如果中途热更新 prompt 或工具服务器，同一条轨迹前半段和后半段会使用不同规则，之后很难解释、复现或回放。
>
> 冻结的是这次运行看到的快照，不是禁止应用更新配置。用户修改配置后，新运行读取新版本，已经开始的运行继续使用旧快照。这样日志可以记录资源版本，出问题时能够回答“这次任务究竟使用了哪份 prompt 和哪些 MCP 连接”。
>
> MCP 配置还可能包含命令、URL、环境变量和请求头，其中环境变量与请求头可能承载密钥。资源快照需要控制日志与序列化边界，不能为了可复现就把 secret 原样写入事件或数据库。理想做法是保存非敏感配置和引用，敏感值从安全存储按需解析。

### 面试官继续追问

- **热更新为什么危险？** 除了行为不一致，还可能让正在执行的图突然失去工具，或让审批基于旧描述、执行却使用新配置。
- **如何实现可复现？** 记录资源版本、模型与 Profile、必要的非敏感配置和事件轨迹；外部服务本身仍可能变化，因此只能提高而非保证完全复现。
