# 自我介绍与项目边界

这一组题解决一个问题：面试官还没有决定深挖哪个项目时，怎样让他听见你的主线，同时不给自己埋下无法解释的坑。

## 001. 请做一个一分钟自我介绍

### 面试时先这样答

> 我是湖北工业大学软件工程专业本科生，方向偏 Java 后端，也在用 Kotlin 做桌面 Agent。我的项目经历主要有两条线：一条是技术交流平台，使用 Spring Boot、MySQL、Redis、Elasticsearch 和 RabbitMQ，重点处理热点数据、文章搜索、请求日志和异步通知；另一条是 Mulehang Agent，使用 Kotlin、Compose Desktop 和 Koog，重点处理 ReAct 执行循环、工具调用、Hook、SQLite 任务持久化和树状会话。
>
> 我比较关注系统在出错时还能不能解释清楚。比如平台项目里要区分 MySQL、Redis 和 ES 各自负责什么，Agent 项目里要区分模型失败、工具失败、用户取消和持久化恢复。我希望应聘后端或 AI 应用工程岗位，把这两类项目里的工程问题继续做深。

### 展开结构

学校和方向只说一句。两个项目各说一个问题，不要把所有依赖逐个念完。结尾说明目标岗位，并留一个可追问的入口，例如“如果您更关注后端，我可以先展开平台项目的缓存和搜索链路”。

### 继续追问

- 为什么同时做 Java 和 Kotlin？
- 你在两个项目中分别负责什么？
- 哪个项目你能讲得更深？

### 边界

不要开场说“熟悉所有中间件”或“精通 Agent”。简历上出现过的技术名词，只代表你准备接受追问，不代表每个组件都由你从零实现。

## 002. 请用三分钟介绍两个项目

### 面试时先这样答

> 技术交流平台的主链路是 MySQL 保存业务事实，Redis 保存热点计数和排行榜等派生数据，Elasticsearch 提供文章搜索，RabbitMQ 把部分通知流程从用户请求中移开。我的重点是理解数据一致性的边界：文章详情不能因为 ES 延迟就变成空数据，Redis 统计也要能定期和数据库校准。
>
> Mulehang Agent 是桌面端任务执行系统。一次运行会把用户输入、历史、模型配置、工具注册表、权限和运行时资源交给 Koog。模型输出工具调用后进入工具节点，工具结果再回到模型，直到模型给出纯文本结果或达到迭代上限。执行过程以事件流展示给 UI，SQLite 保存任务快照，Session Tree 保存可回溯的历史分支。
>
> 两个项目的共同点是把外部系统当作有失败可能的协作者。数据库、缓存、搜索引擎、消息队列和模型都不能简单当成永远可用的函数。

### 展开结构

三分钟版本只讲两条主链路：请求链路和任务链路。每条链路都回答“谁是权威数据、哪里允许最终一致、失败后怎么退化”。技术交流平台侧重数据系统，Agent 侧重状态机和运行时约束。

### 继续追问

- 为什么搜索结果不直接返回 ES 中的完整文章？
- Agent 重启后能不能从模型中断的位置继续？
- Redis 统计和 MySQL 不一致时谁说了算？

### 边界

“两个项目都做过”不等于两个项目每个模块都由你负责。回答中要把“我实现”“我参与”“我阅读并能解释”分开。

## 003. 如果只能选一个项目深挖，你会选哪个？

### 面试时先这样答

> 如果岗位偏 Java 后端，我会选技术交流平台，因为它能从请求进入、业务写库、缓存统计、ES 搜索和异步通知一路展开。如果岗位偏 AI 应用或 Kotlin，我会选 Mulehang Agent，因为它的执行循环、工具结果回写、Hook 决策和任务恢复更贴近岗位。
>
> 我会先讲一条完整链路，再根据您的问题切到某个组件。这样能证明我理解系统之间的关系，不会只背 Redis、ES 或 Koog 的独立知识点。

### 展开结构

先判断岗位关注点，再选择项目。选择后不要重复项目简介，直接画出一条请求或任务的时序：入口、核心决策、外部依赖、成功结果、失败结果。

### 继续追问

- 你觉得哪个项目更接近生产系统？
- 两个项目中最像后端工程的问题是什么？
- 如果让你删掉一个中间件，删谁？

### 边界

不要为了显得全面而两个项目各讲一半。面试官通常会沿着你主动提到的第一个技术点继续问。

## 004. 你在技术交流平台里具体做了什么？

### 面试时先这样答

> 我会按功能链路说，不按依赖清单说。业务数据通过 Spring Boot 的分层结构进入 MySQL；文章阅读、点赞、收藏等统计有 Redis Hash 计数；热点排序使用 Sorted Set；文章搜索由 ES 根据关键词和结构化条件召回；点赞通知等非关键同步动作可以通过 RabbitMQ 异步处理；请求入口和业务方法用过滤器、AOP 和 MDC记录 traceId、业务标识和耗时。
>
> 我能重点展开的是缓存统计、搜索条件组合、请求日志和异步通知。对于没有亲自负责的模块，我会说明参与范围，不把整个项目的代码都算成个人贡献。

### 展开结构

用“事实数据、派生数据、异步副作用、排查信息”四个角度组织。事实数据落 MySQL，派生数据可重建，异步副作用允许延迟，可观测信息帮助定位哪一段慢或失败。

### 继续追问

- 文章发布后什么时候能搜到？
- Redis 的统计丢了怎么办？
- RabbitMQ 消费失败会不会重复通知？

### 边界

当前代码中 ES 搜索明确包含关键词、标题、正文、作者和栏目等条件。标签与文章的关联查询还有 MySQL 路径，回答时不要把它们无条件归为一条 ES 查询。

## 005. Mulehang Agent 的一次运行是怎样走完的？

### 面试时先这样答

> UI 先提交用户输入、历史、模型配置、工作区、权限预设和运行时资源。Gateway 创建工具注册表和 MCP 资源，执行启动与提交 Hook，然后交给 Koog Agent。图中先调用模型，模型如果产生工具调用就进入工具执行节点，工具结果回到下一次模型调用；模型只返回文本且没有工具调用时才结束。过程中各类增量、工具状态、审批和失败会转成统一事件给 UI，最终结果和任务状态再交给持久化层保存。

### 展开结构

抓住四个状态：模型决策、工具执行、工具结果、结束或失败。模型负责下一步意图，工具负责受控执行，Gateway 负责生命周期和事件，UI 不直接参与模型协议。

### 继续追问

- 为什么不能把它写成一个 `while` 循环？
- 工具失败后是 Gateway 重试还是模型决定下一步？
- UI 关闭后后台任务怎样处理？

### 边界

当前实现是可恢复的任务状态和会话分支，不等于所有外部工具都能在进程重启后从原地续跑。

## 006. 你如何区分“自己做的”和“项目已有的”？

### 面试时先这样答

> 我会把贡献分三层说。第一层是我亲自设计和实现的链路，例如某个缓存统计或 Agent 状态流；第二层是我在已有框架上接入并改造的部分，例如 Koog 的流式节点和 RabbitMQ 的业务流程；第三层是我阅读过、能解释其工作方式但没有主导修改的模块。我不会把第三层说成从零实现。

### 展开结构

每项贡献准备一个可验证事实：改动解决了什么问题，异常路径怎么走，测试或日志怎样证明。不要用“负责后端开发”这种无法核对的总括句。

### 继续追问

- 你能给出一次具体故障吗？
- 你的代码如何被验证？
- 如果删掉你负责的部分，系统会失去什么能力？

### 边界

如果某个模块主要来自开源项目或已有模板，要说“在项目中接入和改造”，不要说“我实现了这个中间件”。

## 007. 两个项目中最难的问题分别是什么？

### 面试时先这样答

> 平台项目最难的是多个存储的职责和一致性边界。MySQL、Redis、ES 和 MQ 各自适合不同读写模式，难点不是把它们连起来，而是明确何时可以延迟、何时必须回源、失败后怎样重建。
>
> Agent 项目最难的是状态流转。模型输出可能同时有文本和工具调用，工具可能失败，Hook 可能阻止结束，用户也可能取消。系统要让模型协议、UI 事件、权限判断和持久化快照对同一个运行保持一致。

### 展开结构

回答“难”时必须跟着约束和处理方法。不要只说代码量大或依赖复杂。

### 继续追问

- 哪个问题最容易产生隐蔽 bug？
- 你怎么测试这些状态？
- 如果重新做一次会改什么？

### 边界

没有线上流量数据时，不要虚构“性能提升了多少”。可以说验证方式，例如单元测试、故障注入、日志字段或恢复演练。

## 008. 你如何回答一个自己还没有完全解决的问题？

### 面试时先这样答

> 我会先把已验证的部分说清楚，再明确未知项。例如当前项目能恢复 SQLite 中保存的任务状态，但不能恢复已经消失的 JVM 协程和模型请求。我可以继续分析如何把运行中的请求拆成可恢复步骤，但不会把它说成已经完成。

### 展开结构

使用“事实、推断、待验证”三层。事实给出代码或测试依据，推断说明理由，待验证项说出下一步实验，不用一段模糊话掩盖。

### 继续追问

- 你准备怎样验证？
- 这个缺口会影响哪些用户操作？
- 为什么当时没有继续做？

### 边界

诚实的边界不是减分项。把未实现能力说成已实现，面试官通常会在第二个追问中发现。

## 009. 面试官连续追问时，你怎样避免把答案说散？

### 面试时先这样答

> 我会把每次追问收敛到当前层次。先用一句话回答，再补一条项目证据，最后停下来等下一问。比如问“为什么用 Redis 计数”，先回答“为了把高频自增从同步数据库写入中移开”，再补“当前通过 Hash 和 pipeline 更新，定时任务回写数据库”。如果继续问一致性，再讨论丢失、重复和补偿，不把所有 Redis 知识一次讲完。

### 展开结构

把回答分成概念层、项目层、异常层和取舍层。面试官问哪一层，就答哪一层。

### 继续追问

- 你如何判断面试官还想听什么？
- 面试官质疑你的方案时怎么办？
- 什么时候应该主动承认限制？

### 边界

不要用背好的长段落压过问题。回答越长，越容易主动引出没有准备的技术点。

## 010. 简历上没有性能数字，面试官问“效果怎么样”怎么办？

### 面试时先这样答

> 如果没有稳定压测或线上指标，我不会报一个看起来很精确的数字。我会说优化改变了什么：阅读计数从每次请求直接写数据库改为 Redis Hash 自增，再由定时任务同步；搜索查询用 ES 的倒排索引和结构化 filter；Agent 侧用事件流和快照避免 UI 直接阻塞在模型调用上。然后说明可以怎样验证，例如压测命中率、P95、数据库写入量、队列积压和恢复耗时。

### 展开结构

先给已有事实，再给指标设计。缓存看命中率、数据库写压力和同步延迟；搜索看查询延迟、召回准确性和索引可用率；消息看消费延迟、失败数和重复率；Agent 看首帧时间、工具失败率和快照成功率。

### 继续追问

- 如果让你现在补压测，怎么设计？
- 哪个指标最能证明方案有效？
- 优化有没有新增成本？

### 边界

“更快”“高性能”“显著提升”都需要证据。没有数据时改用可测量的行为描述。
