# 技术交流平台：Redis 与查询链路

这一组题集中回答缓存、统计、排行榜和全文搜索。先记住一个原则：中间件是数据链路的一部分，不是性能结论本身。

## 031. 简历写“热点文章缓存”，代码里具体是什么？

### 面试时先这样答

> 这句话需要校准。当前代码能明确证明的是 Redis Hash 承载文章和用户的实时统计，Redis Sorted Set 承载日/月活跃度排行榜；文章热点推荐接口本身仍通过数据库按阅读量查询。更准确的说法是“使用 Redis 处理热点统计与排行榜”，而不是把热点文章列表整体说成已经缓存到 Redis。

### 展开结构

文章详情查询统计时从 Redis Hash 读取点赞、收藏、评论和阅读数。阅读请求通过 `HINCRBY` 更新文章和作者两个 Hash。热点文章列表走 MySQL 查询按阅读量排序。三者都是“热点”相关，但存储职责不同。

### 继续追问

- 如果要把热点文章列表也缓存到 Redis，怎么设计？
- 为什么当前实现没有直接缓存列表？
- Redis 缓存和 Redis 计数有什么区别？

### 边界

不要为了迎合简历把数据库查询说成 Redis 缓存。面试前可以修改简历，也可以在面试中主动把实现范围讲准。

## 032. 为什么文章统计使用 Hash，而不是每个字段一个 String？

### 面试时先这样答

> 一个文章的点赞、收藏、评论和阅读数属于同一组统计，Hash 可以用文章 ID 作为 key、统计类型作为 field，读取和更新的语义都比较集中。`HINCRBY` 适合阅读量这种原子递增操作，查询时一次读取多个 field，再组装 DTO。这样 key 数量和业务映射都比四个独立 String 更清楚。

### 展开结构

用户统计也采用类似结构。阅读一次时需要同时更新文章统计和作者统计，项目用 Redis pipeline 把两条命令放在同一个网络批次中，主要减少网络往返，不要把 pipeline 说成跨 key 事务。

### 继续追问

- Hash 的两个 field 更新能否保证同时成功？
- pipeline 和 Lua、事务有什么区别？
- Hash 变成大 key 时怎么办？

### 边界

pipeline 不是原子性保证。Redis 进程在两条命令之间故障时，文章和作者统计仍可能短暂不一致。

## 033. Redis 计数为什么还要定时同步 MySQL？

### 面试时先这样答

> Redis 适合高频自增和实时读取，但它不是文章统计的长期唯一存储。项目每 5 分钟扫描文章统计 key，把 Redis 中的阅读数覆盖写入 MySQL，数据库用 `insertOrUpdate` 接收结果。这样把高频写和持久化写分开，详情读取快，数据库也保留可重建的最终数据。

### 展开结构

同步任务要关注三个问题：扫描不能用阻塞性的全量 `KEYS`，代码采用 `SCAN`；写入要可重复，当前按文章 ID 覆盖写；Redis 在同步前丢失会产生丢计数窗口，需要持久化、备份或消息补偿才能进一步缩小风险。

### 继续追问

- 定时任务执行两次会不会把阅读数加两次？
- Redis 数值比 MySQL 小时应该覆盖还是取最大值？
- 多个应用实例同时跑定时任务怎么办？

### 边界

当前实现能支撑“定时同步具备幂等写入”的说法，不能直接支撑“零丢失”。没有看到分布式锁、消息补偿或同步前快照时，要把风险说清楚。

## 034. Redis Sorted Set 怎样实现排行榜，怎样避免重复计分？

### 面试时先这样答

> Sorted Set 用用户 ID 做 member、活跃度做 score，查询时按 score 取 Top N。项目另外用按用户和日期组织的 Hash 记录已经计过分的行为，只有当天该行为还没有记录时才增加日榜和月榜分数，并给统计 key 设置过期时间。查询 Top N 后再批量查用户资料，避免把完整用户对象塞进排行榜。

### 展开结构

日榜和月榜是两个不同 key。更新分数和设置 TTL 是不同操作，需要考虑中途失败。并列排序、取消行为是否扣分、跨天 key 如何生成，都要先定义业务规则再选命令。

### 继续追问

- 为什么不把用户信息直接存到 ZSet？
- 取消点赞会不会扣分？
- 热点排行榜 key 过热怎么办？

### 边界

排行榜是派生数据，用户资料和行为事实仍来自数据库或业务事件。Redis 丢失后可以重算，但需要保留足够的事实数据。

## 035. Redis 失效、缓存穿透、击穿和雪崩分别怎么处理？

### 面试时先这样答

> 穿透是大量请求查询本来不存在的数据，需要参数校验、空值短缓存或布隆过滤器；击穿是某个热点 key 过期时并发回源，需要互斥重建、逻辑过期或热点续期；雪崩是大量 key 同时失效，需要 TTL 抖动、分批刷新和限流降级。Redis 故障本身还要让非核心统计回源或返回可接受的旧值，不能把所有接口一起拖垮。

### 展开结构

先区分数据类型。文章详情、统计、排行榜的容忍度不同。统计允许延迟时可以异步修复，权限和文章状态不能因为缓存故障而放行。锁的超时、回源并发和降级结果也要有上限。

### 继续追问

- 空值缓存多久？
- 分布式锁拿不到时返回什么？
- Redis 恢复后如何重建排行榜？

### 边界

项目当前主要展示 Redis 计数和排行榜，不能把所有缓存防护策略都说成已经落地。回答“当前实现”与“生产上会补什么”要分开。

## 036. Elasticsearch 在平台中负责什么，为什么不让 MySQL 做全文搜索？

### 面试时先这样答

> ES 负责文章内容的全文召回、相关性排序和高亮，MySQL 仍保存文章事实和最终展示数据。文章标题、短标题、摘要和正文在 ES 中建立倒排索引，查询时根据关键词召回文章 ID 和片段，再回源 MySQL 取需要展示的内容。MySQL 适合事务和权威数据，ES 更适合分词、相关性和全文查询。

### 展开结构

搜索服务的职责是返回候选和解释信息，不负责替代文章主表。这样 ES 缺失、延迟或重建时，文章详情仍有数据库路径；代价是搜索结果与数据库之间存在短暂延迟。

### 继续追问

- 为什么搜索服务返回文章 ID 而不是完整 DTO？
- ES 不可用时搜索接口如何退化？
- 删除文章后索引如何处理？

### 边界

ES 不是强一致缓存，也不是主业务数据库。索引缺失时不能直接认为文章不存在。

## 037. ES 的 `text`、`keyword` 和 analyzer 怎样选择？

### 面试时先这样答

> 标题、摘要和正文需要分词和相关性，使用 `text`；文章 ID、状态、URL slug 等精确筛选字段使用 `keyword` 或数值类型。当前文本字段使用 `ik_max_word` 建索引、`ik_smart` 查询，并提供 keyword 子字段和 exact 字段，兼顾全文匹配、精确条件和高亮。

### 展开结构

索引 analyzer 决定词怎样进入倒排索引，search analyzer 决定查询词怎样拆分。二者不匹配可能出现“写入了但搜不到”。字段类型应由查询模式反推，不能只把所有字符串都设成 text。

### 继续追问

- 为什么索引和查询使用不同 IK analyzer？
- `keyword` 能不能做正文全文检索？
- mapping 改了为什么经常要重建索引？

### 边界

字段映射能提高可控性，但不能保证中文搜索质量。仍要用真实关键词集测试召回、排序和高亮。

## 038. 关键词、作者、栏目和状态条件如何组合？标签条件要怎么说？

### 面试时先这样答

> 关键词属于全文匹配条件，放在 `bool.must`；删除标记、发布状态、文章 ID、作者 ID、栏目 ID 等结构化条件放在 `bool.filter`。作者名称可以作为 must 中的短语匹配，标题还可以设置更高权重。当前代码能直接证明这些条件会组合成 ES 查询。标签关联在项目中还有 MySQL 查询路径，不能直接说 ES 已经把标签 ID 作为 filter。

### 展开结构

`must` 参与匹配和评分，`filter` 只做筛选，通常更适合状态和 ID。条件都存在时是交集关系。全文关键词内部可以用多个字段 should，并设置至少一个字段命中。

### 继续追问

- 为什么状态条件不放 must？
- 作者名用 match、term 还是 match_phrase？
- 如果必须支持 ES 标签过滤，mapping 和索引文档怎么改？

### 边界

面试官问的是“当前代码怎么做”时，不能用“未来可以”代替事实。标签查询要明确是 ES 路径、MySQL 路径，还是二者拼接。

## 039. ES 写入后为什么可能搜不到，项目怎样处理索引同步？

### 面试时先这样答

> ES 是近实时搜索。文档写入后要经过 refresh 才对搜索可见，项目在单篇同步或批量引导后会 refresh。文章上线、删除和索引重建需要分别处理，不能只依赖一次写入。代码还用 Redis 记录关键词引导状态和索引 generation，避免相同关键词被重复 bootstrap，并用短 TTL 的锁减少并发初始化。

### 展开结构

搜索不可用时先检查索引是否存在、mapping 是否完整、ES 是否启用和索引覆盖率。文章文档缺失可以从 MySQL 查询并补建，ES 返回的文章展示内容再回源 MySQL。

### 继续追问

- 为什么不每次写入都强制 refresh？
- 批量写入失败一半怎么处理？
- 索引重建时用户还能搜索吗？

### 边界

当前代码有同步、重建和关键词引导逻辑，但不应把它描述成完整的分布式索引任务系统。消息补偿、死信和全量校验要看实际部署方案。

## 040. 搜索结果为什么要按 `_score` 和更新时间排序，还要返回高亮？

### 面试时先这样答

> `_score` 体现关键词相关性，更新时间作为第二排序键，让同等相关的文章优先展示更新内容。高亮片段能告诉用户命中了标题、摘要还是正文，也能避免只返回一串文章 ID。当前查询还做分页，并从命中结果提取文章 ID、总数和 snippet，最终详情仍由 MySQL 负责。

### 展开结构

相关性排序和业务排序可能冲突，要根据产品目标调整权重。深分页时 `from + size` 会让每个分片保留更多候选，页数很深时应考虑 `search_after` 或离线导出方案。高亮文本要做长度限制和安全处理。

### 继续追问

- 只按更新时间排序有什么问题？
- 相关性分数相同如何保证顺序稳定？
- ES 返回空结果时是否直接返回空页面？

### 边界

排序和高亮改善的是搜索体验，不等于召回质量已经被证明。需要真实查询集和指标验证，而不是只看几条演示词。
