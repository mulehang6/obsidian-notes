# Mulehang Agent：执行闭环与 Hooks

这一组题围绕简历上最容易被追问的一句话：“基于 Koog Graph-based Agent 实现 ReAct 循环，支持最大迭代次数、Hooks 和项目级 Guidelines。”

## 011. 这个项目为什么算 Agent，不只是带工具的聊天界面？

### 面试时先这样答

> 关键在于系统是否形成“模型决策、工具行动、结果观察、再次决策”的闭环。Mulehang 中模型先给出文本或工具调用，工具结果会回到下一次模型调用，模型可以根据结果选择结束或继续调用其他工具。图边、权限、Hook 和迭代上限共同限制这个闭环。

### 展开结构

普通聊天通常是一问一答。固定工作流则由程序提前写死步骤。这里的下一步工具由模型结合当前上下文决定，但工具本身仍由注册表和权限策略控制。Agent 的自由度来自决策，可靠性来自边界。

### 继续追问

- 固定三步流程要不要用 Agent？
- 工具调用和 Agent 的关系是什么？
- 怎样防止模型无限调用工具？

### 边界

Agent 不是“模型回答更长”，也不是加上 function calling 就自然成立。判断重点是后续动作是否会根据环境反馈改变。

## 012. 你设计的 ReAct 图是怎样循环的？

### 面试时先这样答

> 图里有模型节点、工具执行节点和工具结果回传节点。开始后先调用模型。模型带工具调用时进入工具节点，工具执行结束后把结果写入下一轮模型上下文。模型给出纯文本且不再带工具调用时进入结束节点；如果工具结果后模型继续请求工具，就再次走工具节点。

### 展开结构

可以用这条时序表达：

```text
用户输入 → 模型 → 工具调用 → 工具结果 → 模型
                       ↘ 纯文本结果 → 结束
```

图策略负责状态迁移，Gateway 负责请求准备、资源、Hook 和事件，工具节点负责实际动作。拆开以后，每类失败都有归属。

### 继续追问

- 为什么模型节点后有两条边？
- 工具执行是串行还是并行？
- 工具结果怎样保证回到正确的调用？

### 边界

图策略保证流程结构正确，不能保证模型每次都给出正确计划。工具参数校验、权限和最大迭代次数仍要在图外或工具边界处处理。

## 013. 如果 assistant 同时返回文本和工具调用，应该结束吗？

### 面试时先这样答

> 不能直接结束。只要 assistant message 中还有工具调用，就必须先执行工具并把结果补回历史。文本可能只是“我先去检查一下”这样的过程说明，不能把它当成最终答案。只有纯文本且没有工具调用时，当前轮次才算收敛。

### 展开结构

结束条件要看结构化消息，而不是只看有没有文字或某个 finish reason。这样可以避免 UI 看到了半句文字就结束，导致工具调用没有结果，下一次请求被模型服务拒绝。

### 继续追问

- 如果 finish reason 是 stop，但仍有 tool call 呢？
- 为什么不能把文本和工具调用一起当最终结果？
- 这类情况如何写测试？

### 边界

这条规则解决的是协议和状态收敛，不代表所有工具都必须执行到底。用户取消、权限拒绝、工具失败和迭代上限都可以让运行以失败或可继续状态结束。

## 014. 自定义流式节点为什么要显式写回 assistant message？

### 面试时先这样答

> 普通的非流式调用可能由框架自动把 assistant message 放回 prompt。自定义流式节点只负责收集帧和发事件时，这个回写动作可能不会自动发生。如果不回写，下一轮工具结果送回模型时，历史里缺少前面的 assistant/tool call 配对，模型服务可能认为工具结果没有对应调用。

### 展开结构

流式处理有两条并行任务：一条把增量发给 UI，另一条把完整 assistant message 收敛后写回模型会话。两条都要完成。只更新 UI 不更新模型上下文，会出现“界面看见了工具调用，模型却没看见”的分裂状态。

### 继续追问

- 工具参数是增量到达的，什么时候算完整？
- 历史里的工具调用没有结果怎么办？
- 为什么工具结果要放在紧邻的 user 消息中？

### 边界

历史回放还要处理被中断的工具调用、非法的参数预览和不同模型协议的消息顺序。不能把 UI 中截断的 preview 当作完整工具参数。

## 015. 最大迭代次数如何设计？“无限迭代”是真无限吗？

### 面试时先这样答

> 配置层允许用户用 `-1` 表示不主动限制，但运行时不能把负数直接传给 Koog。项目把 `-1` 转成 `Int.MAX_VALUE`，普通值必须不小于 50，非法值在配置解析时拒绝。它只是把应用层限制放到运行时允许的最大值，仍会受到进程、上下文长度、取消信号和模型或工具异常的限制。

### 展开结构

最大迭代次数有三个职责：防止模型和工具形成失控循环；让资源消耗有上界；达到上限时给用户一个可以继续操作的会话状态。错误消息要区分“本次配置达到上限”和“运行时允许的最大值”。

### 继续追问

- 为什么默认值不是 1？
- 达到上限后是否自动重试？
- 怎样根据任务类型设置上限？

### 边界

不要说“支持真正无限循环”。准确说法是“支持配置语义上的不主动限制，并在 Koog 接受的正整数范围内运行”。

## 016. 工具失败后，Agent 是怎么继续或结束的？

### 面试时先这样答

> 工具失败先转成统一的工具失败事件，同时要把失败结果放回模型可见的历史。后续是否继续由模型根据失败信息决定，也可能因为权限拒绝、取消、不可恢复异常或迭代上限而结束。系统提供的是失败后的恢复路径，不是保证每次失败都能自动修好。

### 展开结构

区分四类结果：工具正常返回、工具业务失败、工具被权限策略拒绝、运行被取消。前三类需要让模型或 UI 看见原因，取消则要保留取消语义，不能把它包装成普通业务失败。

### 继续追问

- 工具失败后为什么不能由 Gateway 无脑重试？
- 工具结果和工具调用怎样配对？
- 哪些错误应该直接结束会话？

### 边界

模型可能重复调用同一个失败工具。需要靠提示、迭代上限、工具侧幂等和更明确的错误分类共同限制成本。

## 017. Hooks 在 Agent 运行时中解决什么问题？

### 面试时先这样答

> Hooks 把会话生命周期和工具动作前后的外部规则接入运行时。Hook 可以继续、允许、要求人工确认或阻断动作，也可以补充上下文或修改用户输入。它适合做项目级策略、权限前置检查和停止前的质量检查，但不能取代核心业务逻辑。

### 展开结构

当前事件包括会话开始、用户提交、工具执行前、停止、停止失败、权限请求和会话结束。同步 Hook 参与本轮决策，异步 Hook 只记录或执行副作用，不阻塞当前决策。多个 Hook 按配置顺序运行，出现 BLOCK 后停止后续命令。

### 继续追问

- Hook 超时应该允许还是阻断？
- Hook 失败会不会把主 Agent 一起打死？
- 同步和异步 Hook 怎样选择？

### 边界

Hook 是扩展点，执行它的外部进程仍可能超时、退出失败或输出非法 JSON。主流程需要安全回退，并把诊断信息记录下来。

## 018. Stop Hook 要求继续处理时，为什么要重新发起一轮？

### 面试时先这样答

> Stop Hook 认为当前结果还不完整时，系统不能只在 UI 上把结果标成“继续”，而要把上一轮用户输入和 assistant 结果追加到历史，构造一个明确的补充提示，再发起新的 Agent 运行。这样模型能看到它刚才说了什么、Hook 为什么要求继续，以及还缺什么。

### 展开结构

项目对 Stop Hook 的继续要求设置了重试上限。每次继续都携带递增的 retry count，超过上限后安全停止并报告原因。Hook 的额外上下文会加入下一轮 prompt，避免只传一句“请继续”导致模型重复原动作。

### 继续追问

- 重新运行会不会重复执行之前的工具？
- 为什么不直接修改最终文本？
- Hook 一直返回 BLOCK 或 CONTINUE 怎么办？

### 边界

这是“新一轮 Agent 处理”，不是对中断工具的事务回滚，也不是从 Koog 图节点做持久化断点续跑。可能重复产生外部副作用，所以工具仍要考虑幂等。

## 019. 项目级 Guidelines 是如何进入模型上下文的？

### 面试时先这样答

> 项目资源加载器会从用户目录和工作区层级发现指令文件，并按信任状态决定是否加载项目级资源。资源加载完成后形成本轮不可变快照，`systemPromptAppendix` 会追加到基础 system prompt。这样同一次运行使用的规则是一致的，用户手动 reload 后才产生新版本。

### 展开结构

要区分三个动作：发现文件、信任项目、构建本轮 prompt。项目级 `AGENTS.md` 或 `CLAUDE.md` 只是输入来源，最终是否生效还取决于工作区扫描边界、信任门槛、优先级和快照版本。规则不会在运行中悄悄热更新。

### 继续追问

- 为什么不每次模型调用前都重新读文件？
- 用户规则和项目规则冲突时怎么办？
- 如何避免陌生项目中的指令自动执行？

### 边界

Guidelines 进入的是模型 prompt 和运行资源，不等于它拥有操作系统权限。工具执行仍受权限预设、审批和工作区边界控制。

## 020. 为什么 UI 不能直接消费 Koog 的原始事件？

### 面试时先这样答

> Koog 的事件属于模型或框架协议，UI 需要的是稳定的应用事件，例如文本增量、工具开始、工具完成、工具失败、审批请求和任务完成。Gateway 把底层事件转换成统一事件后，UI 不需要知道具体模型供应商和工具协议。以后替换流式适配器或调整 Koog 版本，展示层的状态机更稳定。

### 展开结构

统一事件还可以承载 traceId、耗时、操作意图和文件差异预览。事件通道需要考虑缓冲、取消和关闭顺序，避免后台继续向已关闭的 UI 流发送数据。

### 继续追问

- 事件丢失时 UI 怎样恢复？
- 为什么工具输出要区分 stdout 和 stderr？
- 事件流关闭和 Agent 取消有什么区别？

### 边界

事件层负责传播状态，不负责替代持久化。窗口关闭或进程重启后要靠 SQLite 快照恢复已保存的任务，而不是指望重新播放内存中的事件。
