# 基础技术栈：简历追问

这里只保留简历技能区和两个项目会直接引出的基础题。回答要能回扣项目，不能只背定义。

## 051. HashMap 的核心实现和常见风险是什么？

### 面试时先这样答

> HashMap 用哈希定位桶，发生冲突时在桶内继续查找。现代 JDK 中桶内元素较多时可能树化，扩容时重新分配桶位置。`put` 和 `get` 平均接近 O(1)，但依赖哈希分布和容量控制。它不是线程安全容器，并发写可能造成数据覆盖或结构问题。

### 展开结构

要能说清 key 的 hash 扰动、数组下标、负载因子、扩容和 equals/hashCode 一致性。对象作为 key 时，放入后不能改变参与 hashCode 的字段，否则可能再也找不到。

### 继续追问

- 为什么 equals 相等的对象 hashCode 必须相等？
- 为什么初始容量和负载因子影响性能？
- ConcurrentHashMap 与 HashMap 的主要差异是什么？

### 回扣项目

排行榜查询会把 Redis 返回的用户 ID 和分数组装成 Map。这里的 Map 是进程内临时索引，不是持久化数据，不能把它当成 Redis 一致性保证。

## 052. `synchronized`、`volatile` 和原子类分别解决什么问题？

### 面试时先这样答

> `synchronized` 同时提供互斥和可见性，适合保护一段临界区。`volatile` 主要保证读到最新值并限制部分重排序，但不保证 `i++` 这种复合操作的原子性。原子类通过 CAS 提供单变量的无锁原子更新。选择要看共享状态是单变量更新，还是多个字段必须一起保持不变量。

### 展开结构

可见性、原子性和有序性是不同问题。比如一个取消标志可以用 volatile，任务状态和错误信息一起更新则需要锁、不可变对象或原子引用完成整体切换。

### 继续追问

- CAS 失败自旋会有什么代价？
- synchronized 锁升级要怎么理解？
- volatile 能不能替代线程安全集合？

### 回扣项目

Agent 的运行取消、事件通道和持久化调度都涉及协程和并发状态，不能因为某个布尔值用了 volatile 就认为整个任务状态线程安全。

## 053. ThreadLocal 为什么适合保存请求上下文，又为什么容易出问题？

### 面试时先这样答

> ThreadLocal 把每个线程的上下文隔离开，适合保存当前请求的 traceId、用户或租户信息，业务代码不用层层传参。但线程池会复用线程，如果请求结束后不 remove，旧上下文可能泄露给下一次任务，也会延长对象生命周期。使用时必须在 finally 清理，并谨慎处理异步切换。

### 展开结构

ThreadLocal 不提供跨线程传播，也不保证上下文一定存在。日志、数据库连接、用户信息要有默认值和清理策略。线程池任务如果需要继承上下文，应显式传递并在任务完成后恢复原值。

### 继续追问

- 为什么 ThreadLocalMap 的 key 使用弱引用？
- InheritableThreadLocal 为什么解决不了线程池传播？
- 协程中如何避免 ThreadLocal 污染？

### 回扣项目

平台的 MDC 清理放在请求 Filter 的 finally 中。这个清理动作和生成 traceId 同样重要。

## 054. 线程池参数应该怎样根据任务选择？

### 面试时先这样答

> 先区分 CPU 密集和 I/O 密集，再根据任务耗时、并发量、下游承受能力和队列策略选择核心线程数、最大线程数、队列、拒绝策略和线程工厂。I/O 密集不等于线程越多越好，数据库连接数、HTTP 连接和消息消费能力通常才是更小的瓶颈。

### 展开结构

线程池要监控活跃线程、队列长度、任务等待时间、执行耗时、拒绝数和异常。拒绝策略要符合业务：核心写请求不能静默丢，统计或日志可以降级，用户可感知的异步任务要有状态。

### 继续追问

- 为什么无界队列可能让最大线程数失效？
- `execute` 和 `submit` 的异常处理有什么差异？
- 如何优雅关闭线程池？

### 回扣项目

RabbitMQ 消费线程、请求异步任务和 Agent 执行线程都不能共用一个没有边界的线程池，否则一个慢下游就可能拖垮全部任务。

## 055. MySQL 的事务、MVCC 和隔离级别怎样落到业务？

### 面试时先这样答

> InnoDB 用 undo log 支持回滚和旧版本读取，用 redo log 做崩溃恢复，锁和 MVCC 共同实现隔离。普通一致性读通常读快照，更新和 `for update` 属于当前读。隔离级别不是越高越好，要根据是否允许不可重复读、范围插入和锁冲突来选。

### 展开结构

事务边界应围绕一个业务不变量设计。比如保存用户足迹和判断状态变化，必须明确查询、修改和唯一约束是否在同一个边界内；跨 Redis、ES、MQ 的副作用不能假设会随 MySQL 回滚。

### 继续追问

- RR 和 RC 的区别是什么？
- 快照读和当前读混用会出现什么？
- 为什么长事务会影响 undo 清理？

### 回扣项目

平台的文章事实、用户足迹和通知派生数据职责不同。MySQL 事务能保护本地事实，不能自动保护后续搜索同步和消息消费。

## 056. MySQL 索引和 SQL 调优应该从哪里开始？

### 面试时先这样答

> 先确认业务查询和数据分布，再用 `EXPLAIN` 看访问类型、候选索引、实际扫描行数、排序和回表情况。索引列顺序要匹配常用过滤、排序和范围条件，避免对索引列做函数、隐式类型转换和前缀模糊匹配。不要为了一个查询堆很多重叠索引，因为写入和空间成本也会增加。

### 展开结构

慢查询要区分 CPU、磁盘、锁等待、网络和结果集过大。分页、批量查询、覆盖索引和减少无效列都可能有效。优化前后要用同一数据规模和同一查询条件对比，而不是凭感觉。

### 继续追问

- 联合索引的最左匹配怎么理解？
- 为什么 `select *` 可能放大回表？
- 深分页有哪些替代方案？

### 回扣项目

文章热点推荐按阅读量查询、统计同步按文章 ID 更新、搜索结果回源文章详情，分别对应排序、更新和批量读取三类 SQL 场景。

## 057. Spring IoC、AOP 和 Spring Boot 自动装配怎样联系起来？

### 面试时先这样答

> IoC 把对象创建、依赖装配和生命周期交给容器，DI 是注入依赖的方式。AOP 通过代理在方法边界插入事务、日志等横切逻辑。Spring Boot 自动装配根据 classpath、配置和条件注解注册合适的 Bean，减少基础设施样板，但最终仍然是 BeanDefinition、后置处理器和代理在工作。

### 展开结构

构造器注入能明确依赖，也便于测试。Bean 后置处理器可以包装实例形成代理，事务和异步常依赖这一步。排查自动装配时先看条件是否满足、Bean 是否注册、最终注入的是原对象还是代理。

### 继续追问

- BeanFactoryPostProcessor 和 BeanPostProcessor 有什么区别？
- `@ConditionalOnProperty` 怎样影响 RabbitMQ 配置？
- 为什么同类内部调用可能绕过 AOP？

### 回扣项目

平台通过组件扫描、AOP、条件配置和服务分层组织缓存、搜索、日志和消息能力。Agent 则把执行策略和基础设施拆在不同模块，依赖方向也要保持清楚。

## 058. Spring 循环依赖和事务自调用为什么容易被问？

### 面试时先这样答

> 构造器循环依赖没有可用的半成品对象，通常会直接失败；部分单例属性注入循环依赖可以靠提前暴露引用处理，但不覆盖所有作用域和代理场景。事务自调用则是因为 `this.method()` 没有经过 Spring 代理，内部方法上的事务通知不会重新触发。工程上应优先拆分职责和事务边界。

### 展开结构

三级缓存的重点不在背三个 Map，而在于容器可能需要提前暴露一个能够生成早期代理的对象。循环依赖通常说明边界不清，修复优先级高于依赖容器技巧。

### 继续追问

- `REQUIRED` 和 `REQUIRES_NEW` 怎么选？
- 事务异常为什么可能导致 rollback-only？
- 通过注入自身代理解决自调用有什么代价？

### 回扣项目

平台的异步通知、缓存统计和业务写入需要清晰分层，否则既容易形成循环依赖，也容易让事务边界和消息边界混在一起。

## 059. MyBatis-Plus 解决了什么，什么时候仍要写 SQL？

### 面试时先这样答

> MyBatis-Plus 可以减少常规 CRUD、分页和实体映射的样板代码，但它不会替业务决定索引、事务和查询语义。简单单表写入可以使用通用能力；复杂统计、批量更新、关联查询和需要精确控制执行计划的场景仍应写清晰 SQL，并用 `EXPLAIN` 验证。

### 展开结构

ORM 的边界是对象映射，不是性能魔法。要关注 N+1 查询、批量参数大小、字段更新范围、逻辑删除条件和事务传播。数据库字段与 Java 类型的转换也要有明确规则。

### 继续追问

- 分页插件可能带来什么问题？
- 批量插入怎样避免一次参数过大？
- 为什么不能把所有查询都放在 Service 里拼字符串？

### 回扣项目

平台的文章、用户足迹、统计同步等场景同时包含简单 CRUD 和批量统计。面试中应说明哪些走通用 Mapper，哪些需要专门 SQL。

## 060. Kotlin 协程、Flow 和 Compose Desktop 在 Agent 中各解决什么？

### 面试时先这样答

> 协程用结构化并发组织模型调用、工具执行、保存和取消，避免为每个异步步骤手写线程回调。Flow 表达持续的事件流，适合把文本增量、工具状态和任务状态发送给 UI。Compose Desktop 负责根据状态重组界面，JCEF 则用于需要嵌入浏览器能力的桌面场景。三者分别对应执行、事件和展示，不是同一层的技术。

### 展开结构

取消要沿协程上下文传播，后台资源要在 finally 释放。Flow 的收集端关闭不等于底层外部进程已经终止，事件通道、工具进程和 MCP 连接都要有自己的生命周期。UI 状态应从事件和持久化快照投影，避免 Composable 直接掌控执行细节。

### 继续追问

- `CoroutineScope` 和 `SupervisorJob` 怎么选？
- Flow 背压或消费者变慢怎么办？
- Compose 重组为什么不能重复启动副作用？

### 回扣项目

Agent Gateway 使用 `channelFlow`、事件通道和后台 scope，把模型执行与桌面 UI 解耦；任务保存再用 IO dispatcher 和 Mutex 控制写入顺序。
