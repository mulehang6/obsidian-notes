# 技术交流平台：AOP、MDC 与 RabbitMQ

这一组题围绕“怎么排查”和“怎么解耦”。这两类能力比背注解名称更容易暴露真实经验。

## 041. Filter、AOP 和 MDC 在请求日志中各负责什么？

### 面试时先这样答

> Filter 站在 Servlet 请求链路的外层，适合生成请求级 traceId、收集 URI、用户和请求耗时，并在结束时清理上下文。AOP 站在 Spring Bean 方法调用边界，适合对标注的方法记录业务标识和方法耗时。MDC 是线程上下文存储，让日志框架自动把 traceId 或业务标识带到同一线程的日志中。

### 展开结构

三者不是互相替代：Filter 知道一次 HTTP 请求，AOP 知道一次业务方法，MDC 提供关联键。请求日志可回答“哪次请求慢”，AOP 日志可回答“请求内哪一个业务方法慢”。

### 继续追问

- 为什么不只用 AOP 记录所有接口？
- Filter 异常时怎样保证清理？
- MDC 是不是全局变量？

### 边界

MDC 默认绑定当前线程。进入线程池、异步任务或消息消费者后，不能假设上下文会自动跟过去。

## 042. traceId 从哪里来，如何帮助排查一次请求？

### 面试时先这样答

> 请求进入 Filter 后生成 traceId，放入 MDC，并通过 `g-trace-id` 响应头返回前端。请求结束时把 URI、用户、参数摘要和耗时写入请求日志，再清理 MDC 和请求上下文。排查时可以先用响应头里的 traceId 找请求日志，再结合方法级耗时日志判断慢在入口构建、业务执行还是输出阶段。

### 展开结构

请求级 traceId 是关联索引，不是耗时本身。耗时要记录起止时间或分段 StopWatch。日志字段要稳定，查询时不依赖一段自然语言文本。

### 继续追问

- traceId 会不会泄露敏感信息？
- 前端拿到 traceId 有什么用？
- 一个请求内部有多个线程时怎么查？

### 边界

当前实现能支撑进程内请求日志关联。没有看到 traceId 自动注入 RabbitMQ 消息或跨服务 HTTP 头的完整证据，因此不要说已经实现了端到端分布式追踪。

## 043. MDC 为什么会在线程池中丢失或串值？

### 面试时先这样答

> MDC 通常基于 ThreadLocal 保存数据，线程池复用的是工作线程。提交任务的线程有 traceId，不代表执行任务的线程也有；如果工作线程结束任务后不清理，还可能把上一个请求的 traceId 带给下一个任务。要么显式捕获并恢复上下文，要么使用经过验证的任务装饰器，并在 finally 清理。

### 展开结构

不能为了“传递 traceId”把整个 MDC Map 无条件复制。要明确哪些键允许跨线程、异步任务生命周期多长、任务取消时是否恢复旧值。RabbitMQ 消费者则应从消息头或消息体重新建立自己的上下文。

### 继续追问

- 为什么 `InheritableThreadLocal` 也不适合线程池？
- 协程上下文和 MDC 如何配合？
- 消费者没有 traceId 时怎么生成？

### 边界

当前平台项目的 Filter 和 AOP 能证明请求内日志能力，不要把未实现的异步透传说成已经完成。

## 044. AOP 如何计算业务方法耗时，并取得业务标识？

### 面试时先这样答

> 切面匹配方法或类上的 `MdcDot` 注解，在 `proceed` 前记开始时间，执行结束后在 finally 中输出类名、方法名和耗时。注解中的业务表达式会用方法参数构建 SpEL 上下文，解析出业务标识写入 MDC。finally 很重要，因为正常返回和抛异常都要留下耗时日志并恢复上下文。

### 展开结构

方法注解优先于类注解。业务表达式依赖参数名发现和 Spring Bean resolver，所以参数名不可用、表达式错误或对象为空时都可能影响日志。日志增强逻辑不应该改变主业务返回值。

### 继续追问

- 切面抛异常会不会吞掉业务异常？
- 同类内部调用为什么可能绕过 AOP？
- 业务标识里能不能直接放完整请求体？

### 边界

AOP 只能拦截经过 Spring 代理的调用。对象自行 new、代理内部自调用和不匹配的注解都可能绕过切面。

## 045. 当前 AOP + MDC 方案距离完整可观测还有什么差距？

### 面试时先这样答

> 当前方案能做请求级 traceId、响应头回写、接口和标注业务方法耗时，以及请求分段日志，适合单体或单服务问题排查。完整分布式链路还需要跨 HTTP、线程池和消息队列传播上下文，统一日志字段，采集指标和 trace span，并对采样、存储和隐私做管理。

### 展开结构

可观测性至少分日志、指标和链路三类。日志回答发生了什么，指标回答发生频率和趋势，链路回答一次请求经过哪些组件。当前项目主要覆盖日志关联和部分耗时，不要用一个 traceId 宣称三者都完成。

### 继续追问

- 慢接口没有异常时怎么查？
- 日志过大或包含请求体怎么办？
- 什么时候应该接入 SkyWalking 或 OpenTelemetry？

### 边界

工具选型要看部署环境和团队维护成本。引入链路系统不能替代日志字段设计和异常分级。

## 046. RabbitMQ 在平台中到底解耦了哪一段？

### 面试时先这样答

> 以点赞为例，主请求先保存用户足迹状态，确认发生了有效状态变化后，把通知所需的数据发布到 RabbitMQ。消费者再负责保存文章通知。这样通知落库和后续提示不需要在请求线程中同步完成。当前只有点赞通知走 RabbitMQ，其他通知仍可能走 Java 内置消息机制。

### 展开结构

准确的异步边界是“消息消费处理异步”，不是“发布调用完全异步”。发布消息本身仍是当前线程与 Broker 的同步交互，只有 Broker 接收并交给消费者后，通知处理才离开主请求。

### 继续追问

- 为什么点赞适合异步，文章发布不一定适合？
- 主请求在消息发送失败时返回什么？
- 如何避免用户重复点赞产生重复通知？

### 边界

异步只能移走允许延迟的副作用。用户足迹状态、权限和核心业务结果仍要由同步事务明确保证。

## 047. 手动 ACK 能解决哪些问题，不能解决哪些问题？

### 面试时先这样答

> 消费者关闭自动 ACK，在处理消息并成功保存通知后再调用 basicAck。这样消费者在处理失败或进程退出前没有确认时，Broker 有机会重新投递消息。它能避免“刚收到就确认、处理还没完成”的丢失窗口，但不能自动解决重复消费、毒消息、死循环重试和业务幂等。

### 展开结构

ACK 的位置应在业务成功之后。失败时要决定 requeue、重试次数、死信或人工处理。消息体要带足够的业务主键，消费者需要用唯一约束或状态判断消除重复副作用。

### 继续追问

- ACK 之前数据库提交、之后进程宕机各会怎样？
- 为什么要设计死信队列？
- 如何控制消费者一次拉取的消息数量？

### 边界

代码中能确认手动 ACK，但不能据此声称已经有完善的重试、死信和投递确认体系。

## 048. 如果消息重复投递，通知会不会重复？

### 面试时先这样答

> 不能只靠 RabbitMQ 保证不重复。消费者至少要用业务唯一键判断一条通知是否已经处理，或者让数据库唯一索引和幂等写入承担去重。项目部分通知逻辑会按用户、关联对象和通知类型查询已有记录再决定是否保存，这能减少重复，但必须结合所有消息类型的业务键检查，不能只看 ACK。

### 展开结构

消息系统通常优先保证至少一次投递，重复是正常情况。消费者处理流程最好是“解析消息、校验版本、幂等落库、确认消息”。如果业务动作不可重复，不能把外部副作用放在没有幂等保护的位置。

### 继续追问

- 业务唯一键应该怎么选？
- 数据库写成功但 ACK 失败会怎样？
- 如何让重复消息不影响计数？

### 边界

“手动 ACK”描述的是消息确认时机，不等于 exactly-once。精确一次通常需要业务层去重和状态机配合。

## 049. RabbitMQ 发布失败、消费失败和消息堆积分别怎么处理？

### 面试时先这样答

> 发布失败要记录业务 ID 和错误原因，决定同步失败、降级到本地消息或返回可重试结果；消费失败要区分临时依赖故障和永久数据错误，临时故障可以有限重试，永久错误进入死信或人工处理；消息堆积要看生产速度、消费速度、单条耗时和失败率，再通过限流、增加消费者或降低无关任务来处理。三类问题不能只靠“重启消费者”。

### 展开结构

监控至少包含 publish error、unacked 数、ready 数、消费耗时、重试次数和死信数量。生产端最好使用 publisher confirm，消费者要设置合理的 prefetch 和超时。

### 继续追问

- 如何保证数据库提交和消息发布的一致性？
- 本地消息表和 Outbox 有什么作用？
- 为什么无限重试会放大故障？

### 边界

当前项目代码展示了连接池、交换机/队列声明和手动 ACK，但没有看到完整的死信、重试和发布确认实现。面试时把“已经做的”和“生产上会补的”分开。

## 050. 现有 RabbitMQ 实现有哪些你会主动说明的风险？

### 面试时先这样答

> 当前实现已经把点赞通知从请求处理链路拆出，并使用持久化交换机、持久化队列和手动 ACK。但我会主动说明两个风险：消费者在注册消费后紧接着关闭 channel，存在消费者生命周期问题；消费循环还有定时 sleep 的过渡实现。继续完善时，我会让连接和 channel 生命周期由消费者进程管理，补发布确认、有限重试、死信、幂等和积压监控。

### 展开结构

风险说明要有优先级。先修复可能直接导致消费失效的生命周期问题，再补可靠性和运维能力，最后再考虑吞吐和扩展。不要用“加机器”掩盖消息确认和重复处理问题。

### 继续追问

- 为什么 channel 关闭会影响消费？
- 连接池适合长期消费者吗？
- 怎样验证消息没有丢或重复？

### 边界

指出风险不是否定项目，而是说明你知道当前实现的完成度。面试官通常更想听到你能不能识别真实故障模式。
