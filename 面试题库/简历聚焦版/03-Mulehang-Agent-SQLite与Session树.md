# Mulehang Agent：SQLite 与 Session Tree

这一组题回答简历上的第二、第三条主线：任务状态怎样保存，历史为什么要做成树，以及“恢复”到底恢复到什么程度。

## 021. 为什么要把 Agent 任务做成 SQLite 快照？

### 面试时先这样答

> Agent 任务不是一条最终文本，它还包含用户输入、assistant 历史、推理块、工具调用和结果、执行状态、错误信息、当前活动条目和会话树。只把最终答案写入文件，重启后无法还原 UI，也无法继续编辑历史分支。SQLite 适合把这些结构化数据放在一个本地事务里保存，查询和迁移也比散落的 JSON 文件容易控制。

### 展开结构

项目把任务主表、时间线、模型 history 和条目树拆成关联表。任务主表保存状态和当前指针，子表保存有序负载，外键级联清理关联数据。读取时再映射回桌面状态。

### 继续追问

- 为什么不直接序列化整个 UI 状态？
- 为什么 timeline 和 history 要分开？
- 快照保存频率如何决定？

### 边界

SQLite 快照保存的是应用状态，不等于保存所有外部世界。例如文件系统已经被工具修改，数据库只能记录工具事件，不能自动撤销文件副作用。

## 022. 连续流式输出会频繁改变状态，怎样避免写库过多？

### 面试时先这样答

> 用 300 毫秒 debounce 合并连续状态变化，取消旧的延迟写入，只保存最近快照。真正写入时用 Mutex 串行化，避免旧的流式状态在新快照之后完成，把新内容覆盖掉。应用启动时要先加载历史并映射到窗口，再开启写入，防止空 UI 先落库覆盖历史。

### 展开结构

这里有三个时间点：恢复前不写、运行中合并写、关闭前主动 flush。取消延迟任务只代表旧快照不再需要写，不代表取消整个应用协程。持久化异常要反馈，协程取消则是新快照替换旧快照的正常调度。

### 继续追问

- 为什么不用每个事件都写？
- debounce 期间进程崩溃会丢多少？
- flush 失败时窗口关闭怎么办？

### 边界

debounce 是写入策略，不是可靠日志。若需要更小的数据丢失窗口，要增加 WAL 事件或更频繁的 checkpoint，但复杂度和磁盘写压力也会上升。

## 023. 进程重启后，Agent 能从中断位置继续吗？

### 面试时先这样答

> 当前实现能恢复已经写入 SQLite 的任务状态、时间线、历史和会话树，让用户重新看到任务并继续操作；它不能恢复已经消失的 JVM 协程、HTTP 连接、模型请求或外部工具进程。运行中的任务重启后应显示为已中断或上次保存的状态，需要重新发起一次 Agent run 才能继续处理。

### 展开结构

真正的断点续跑还需要保存可重放的图节点、工具幂等键、审批 continuation、外部副作用状态和模型上下文版本。当前 SQLite 记录的是任务快照，目标是恢复“可见状态和可编辑历史”。

### 继续追问

- 为什么不把当前 Koog 节点序列化？
- 如果工具已经执行成功但快照没写上怎么办？
- 如何设计真正可恢复的任务？

### 边界

回答中要把“重启恢复任务”与“重启后自动继续执行”分开。前者已实现，后者不是当前快照能力能保证的事情。

## 024. Schema 迁移怎样避免直接改坏用户数据？

### 面试时先这样答

> 数据库有独立的 `schema_migration` 表记录已应用版本。打开连接后先启用外键和 WAL，再检查待迁移版本；有历史任务且存在待迁移时先做备份，然后在事务中按版本顺序执行建表或加列，成功后写入迁移记录。这样迁移是可判断、可重复检查的，不依赖“当前数据库一定是最新结构”。

### 展开结构

当前版本已经从初始任务表演进到会话偏好、工作区名称、分离工作区、会话树和 head 指针等版本。每个版本有清晰的结构变化，启动时自动补齐旧库。

### 继续追问

- 迁移执行到一半失败怎么办？
- 为什么不直接比较表结构？
- 加列的默认值会不会影响历史任务？

### 边界

Schema 版本表只能记录应用尝试过的迁移。生产级迁移仍要准备异常恢复、兼容读写和真实旧库演练，不能只在全新数据库上测试。

## 025. 为什么迁移前要做 WAL checkpoint 和数据库备份？

### 面试时先这样答

> SQLite 开启 WAL 后，部分最新修改可能在 WAL 文件中。迁移前先做 `wal_checkpoint(FULL)`，把 WAL 内容合并到主数据库，再复制数据库文件，备份才包含一个更完整的状态。备份只在已有任务且确实有待迁移时生成，并按保留数量清理旧副本，避免每次打开全新数据库都产生无意义备份。

### 展开结构

备份解决的是迁移写错或版本不兼容时的回退入口，事务解决的是当前迁移过程的原子性。二者作用不同。迁移成功不代表备份可以立刻删除，因为新版本仍可能在后续启动中暴露问题。

### 继续追问

- 复制 SQLite 文件时为什么不能忽略 WAL？
- 备份文件损坏怎么办？
- 为什么只保留最近几份？

### 边界

代码中的备份是本地回退副本，不是异地容灾。它不能防止磁盘损坏、用户误删整个配置目录或备份目录本身不可写。

## 026. SQLite 任务保存怎样保证主表和子表不会半更新？

### 面试时先这样答

> 保存任务集合时在一个数据库事务里先替换任务主表，再插入 timeline、history 和 entries。任何一部分失败就 rollback，成功才 commit。子表通过外键引用 task，并开启 `foreign_keys`，删除任务时由数据库级联清理关联内容，避免留下孤立记录。

### 展开结构

全量替换的好处是实现简单，任务集合状态容易保持一致；代价是任务多或快照大时写放大明显。当前桌面场景优先保证恢复结果完整，未来可以按任务增量保存。

### 继续追问

- 为什么不每次只 update 一行？
- SQLite WAL 和事务分别解决什么问题？
- 保存过程中被强制终止会出现什么？

### 边界

数据库事务只能保证本次 SQLite 写入的一致性，不能把文件修改、模型请求和数据库保存组成跨系统事务。

## 027. Pi 风格 Session Tree 的数据结构是什么？

### 面试时先这样答

> 会话有两层关系。外层任务用 `parentConversationId` 形成会话之间的父子关系；单个会话内部的条目只保存自己的 id、parentId 和内容类型，所有条目共同组成可保留兄弟分支的树。当前会话通过 `activeEntryId` 指向正在看的 leaf，通过 `headEntryId` 记录持久末端。

### 展开结构

条目类型包括用户或助手消息、推理、工具调用、工具结果、分支摘要、标签以及模型和推理强度变更。父指针比把完整历史复制到每个分支更省重复，也能从任意 leaf 回溯祖先路径。

### 继续追问

- 为什么不用一条线性消息数组？
- 父指针出现环路怎么办？
- `activeEntryId` 和 `headEntryId` 不同意味着什么？

### 边界

这是一棵持久化的内容和上下文树，不是 Koog 内部执行图的持久化。树上的节点不能自动代表外部工具已经完成或可以重放。

## 028. 为什么要把 timeline 和 model history 分开？

### 面试时先这样答

> UI timeline 关注人能看懂的展示，例如推理块展开状态、工具卡片、完整输出和文件差异；model history 关注供应商协议需要的消息顺序、工具调用和工具结果配对。两者都从当前 leaf 的祖先路径投影出来，但字段和组织方式不同。把它们混成一个列表，会让 UI 的展示变化污染模型上下文。

### 展开结构

投影过程先沿 active leaf 回溯路径，再按条目类型分别追加 timeline 和 history。模型切换或推理强度变化会更新路径配置，标签只影响 UI，不进入模型 history。

### 继续追问

- 为什么工具结果需要同时出现在两边？
- 推理内容是否全部发给模型？
- 历史缺少工具结果时如何回放？

### 边界

当前 history 回放会对孤立工具调用补一个占位结果，保证协议闭合。占位结果只是告诉模型“上次没有完成”，不代表工具真的返回过这个内容。

## 029. 从历史用户消息创建分支和克隆会话有什么区别？

### 面试时先这样答

> 从用户消息创建分支，会复制该用户消息之前的祖先路径，恢复这条消息的输入到 composer，随后重新发送就会生成新的兄弟分支。克隆会话则复制当前 active leaf 的完整祖先路径，生成一个独立子会话，保留历史但不复制源会话的其他兄弟分支。两者都重新生成条目 id 和父指针。

### 展开结构

复制路径而不是复制整棵树，可以避免把无关分支带到新会话。复制时还要重写 BranchSummary、Label 等引用其他条目的 id，否则新树会指向旧树节点。

### 继续追问

- 为什么从用户消息开始时要恢复草稿？
- 克隆后修改会不会影响源会话？
- 附件和模型配置怎么处理？

### 边界

会话分支隔离的是历史和任务视图，不自动隔离工作区文件副作用。两个分支如果使用同一个工作区，工具仍可能修改同一份文件。

## 030. 切换历史节点时，为什么需要 Branch Summary？

### 面试时先这样答

> 直接删除当前 leaf 之后的历史会让模型失去用户已经探索过的信息。切换到另一个分支时，系统先找出当前路径中真正被离开的条目，让摘要模型压缩它们，再把 `BranchSummary` 挂到目标路径上，然后重新投影 timeline 和 history。这样上下文变短了，但仍能告诉模型“之前离开的分支发生过什么”。

### 展开结构

用户消息和自定义条目有回到父节点、恢复输入的语义；工具和助手条目可以直接作为 leaf。`activeEntryId` 可以偏离 `headEntryId`，表示正在看历史分支；回到 head 则重新切换到持久末端。

### 继续追问

- 摘要生成失败时能否切换？
- 摘要会不会被再次摘要导致信息损失？
- 为什么切换前要取消当前运行？

### 边界

摘要是上下文压缩，不是精确回放。关键数据如果不能丢，应保留原始条目或让用户选择不摘要。当前实现也不能把摘要当成工具执行凭证。
