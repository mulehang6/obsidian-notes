# 技术交流平台项目深挖（301-325）

## 301. 请介绍技术交流平台项目

### 面试时可以这样答

> 这是一个 Spring Boot 技术内容社区，后端按 core、api、service、web 和 ui 等模块拆分。MySQL 保存用户、文章和互动等核心数据，MyBatis-Plus 负责常规数据访问；Redis 承担排行榜等高频读；Elasticsearch 提供文章搜索；RabbitMQ 把点赞后的非实时操作异步化；AOP 与 MDC 统一记录接口耗时和 traceId。
>
> 我主要参与 Redis 排行榜、ES 检索、接口耗时追踪和 RabbitMQ 点赞链路。面试时我会围绕数据流和一致性讲，而不是只报中间件名称。

## 302. 多模块架构有什么价值？

### 面试时可以这样答

> 模块把依赖方向写进构建边界。core 放通用模型和基础能力，api 定义对外契约，service 组织业务，web 接收请求，ui 负责前端资源或展示。这样 web 不应绕过 service 直接拼数据访问。
>
> 模块不是越多越好。若只是按包名机械拆分，却互相循环依赖，编译和理解成本更高。应以职责和可替换边界决定。

## 303. 为什么使用 MyBatis-Plus？

### 面试时可以这样答

> 它减少单表 CRUD、分页和条件构造的重复代码，同时保留写自定义 SQL 的能力。内容平台有大量普通增删改查，使用它能把精力放到业务规则。
>
> 复杂联表、统计和性能敏感查询仍要写清楚 SQL，并看执行计划。Wrapper 生成 SQL 不代表索引一定有效，也不能把 N+1 查询藏在 service 循环里。

## 304. 排行榜为什么适合 Redis ZSet？

### 面试时可以这样答

> ZSet 为每个成员保存 score，并按分数有序。文章 ID 作为 member，热度作为 score，可以用 ZINCRBY 更新，用 ZREVRANGE 取前 N 名，单次操作复杂度和实现都比每次查 MySQL 排序合适。
>
> Redis 排行榜通常是派生视图，数据库仍保存点赞、评论等事实数据。缓存丢失后要能重建。

## 305. 热度 score 如何设计？

### 面试时可以这样答

> 可按点赞、评论、收藏和浏览赋不同权重，再加入时间衰减，防止老文章永久霸榜。具体权重不能拍脑袋，应通过业务目标和历史数据回放调整。
>
> 若把所有指标压成一个 Double，要注意精度和解释性。也可以先保存各项计数，由定时任务计算热度分数。规则变更时从原始计数重算，比只保留最终 score 更容易回放和解释。

## 306. ZSet 分数相同时如何排序？

### 面试时可以这样答

> Redis 在 score 相同的情况下按 member 字典序，不一定符合发布时间或文章 ID 的业务顺序。若需要稳定二级排序，可以把时间编码进分数的低位，但要控制 Double 精度；也可以取出同分结果后在应用层排序。
>
> 面试时要先说明业务是否真的要求严格顺序，不要为很少出现的同分制造复杂编码。

## 307. Redis 排行榜与 MySQL 不一致怎么办？

### 面试时可以这样答

> MySQL 保存事实，Redis 保存可重建结果。业务写入先保证数据库事务成功，再通过消息或事务提交后的事件更新 Redis。更新失败进入重试，后台定期按数据库数据校准。
>
> 不能承诺强一致。界面可接受秒级延迟，但点赞明细和权限判断不能只信排行榜缓存。

## 308. 排行榜 Key 如何设计？

### 面试时可以这样答

> Key 应包含业务、时间窗口和范围，例如文章日榜、周榜、某分区榜。成员使用稳定文章 ID，不把标题放进 member。时间窗口结束后设置合理 TTL，热门榜也要防止永久堆积。
>
> 集群环境要考虑 hash slot。需要原子操作多个相关 key 时，可以用相同 hash tag，但不要让所有榜单集中到一个热点槽。

## 309. 热点排行榜 Key 过热怎么办？

### 面试时可以这样答

> 读热点可以在应用内做短 TTL 本地缓存，或把结果定期物化成只读 JSON；写入可以先聚合再批量更新。分地区或分频道拆 key 也能分散负载。
>
> 若所有请求最终仍读同一个 ZSet 主节点，增加应用实例不会解决 Redis 热点。先看 QPS、慢查询和网络流量再选方案。

## 310. Elasticsearch 搜索链路怎么设计？

### 面试时可以这样答

> 文章发布后，把标题、正文摘要、作者、标签、状态和发布时间同步到 ES。查询时对标题和正文做 multi_match，标题可以给更高 boost，再用状态、分区和权限 filter，按相关度或时间分页。
>
> 搜索结果只返回文章 ID 和展示字段，关键详情可以回源数据库。ES 是搜索索引，不作为核心事实唯一来源。

## 311. ES mapping 为什么不能完全动态生成？

### 面试时可以这样答

> 动态 mapping 可能把数字、日期或 keyword 识别错，后续无法直接修改字段类型。标题与正文需要 text 和中文 analyzer，标签、状态、作者 ID 应是 keyword，时间是 date。
>
> 正式索引应使用模板显式声明 mapping。版本升级通过新索引加 alias 切换，避免在旧索引原地硬改。

## 312. 数据库内容如何同步到 ES？

### 面试时可以这样答

> 业务事务完成后发布文章变更事件，消费者按 articleId 读取最新状态并 upsert ES。消息只携带 ID 和版本，避免旧消息把新内容覆盖。删除可以写 tombstone 或删除索引文档。
>
> 还要有全量重建任务和差异校验。只依赖消息链，一次长期失败就可能永久缺文档。

## 313. ES 延迟同步时用户看到什么？

### 面试时可以这样答

> 新文章详情页可以立即从 MySQL 访问，但搜索结果可能延迟几秒。产品应接受这种最终一致性，发布成功不承诺立刻能搜到。若需要“作者立即看到”，可在搜索结果外补当前用户最近发布内容。
>
> 不应为了搜索实时性把数据库事务与 ES 写入绑成分布式强事务，复杂度通常不值。

## 314. ES 深分页为什么慢？

### 面试时可以这样答

> `from + size` 越大，每个分片都要收集并排序更多候选，协调节点再合并，内存和 CPU 增长。普通翻页限制最大页数；连续滚动使用 `search_after` 加稳定排序字段。
>
> `search_after` 不支持随意跳页，需要前一页 sort values。后台导出可用 PIT 保持视图一致。

## 315. 为什么用 RabbitMQ 异步处理点赞？

### 面试时可以这样答

> 点赞请求的核心是记录用户意图，通知、热度更新和部分统计不必全部阻塞 HTTP。请求成功后发送事件，消费者异步更新派生数据，降低主链延迟并解耦模块。
>
> 如果连点赞事实也只放消息、不先可靠落库，消息发送失败会让用户看到成功但数据丢失。需要明确同步边界。

## 316. 如何保证 RabbitMQ 消息不丢？

### 面试时可以这样答

> 生产端开启 publisher confirm，并处理 nack 与超时；交换机、队列和消息按需要持久化；消费端业务成功后手动 ack，失败则重试或进入死信队列。网络确认与业务事务之间仍有空窗。
>
> 更严格的方案用本地消息表或 Outbox，在数据库事务内记录事件，再由后台投递。不能只说“持久化消息就绝对不丢”。

## 317. 消费重复怎么办？

### 面试时可以这样答

> 至少一次投递下重复是正常现象。消息带 eventId，消费者在业务事务中记录已处理 ID，或让更新本身幂等。例如点赞关系使用用户 ID 与文章 ID 唯一键，重复插入不重复加计数。
>
> 先查后写在并发下仍会重复，必须依赖唯一约束或原子条件更新。处理记录与业务修改应在同一事务提交，否则“已记录但未生效”会让后续重投被错误跳过。

## 318. 点赞消息需要保证顺序吗？

### 面试时可以这样答

> 同一用户对同一文章可能快速点赞再取消，若消息乱序，最终状态会错。消息应携带版本或操作时间，消费者只接受更新版本；也可按 articleId 或关系 ID 路由到同一队列并保持单消费者顺序。
>
> 全局顺序代价太高，真正需要的是同一业务实体的局部顺序。即便使用同一队列，也要确认重试和多消费者不会改变完成顺序，版本校验仍是可靠兜底。

## 319. 消息积压怎么处理？

### 面试时可以这样答

> 先确认是消费逻辑慢、下游数据库慢、异常重试还是生产突增。增加消费者前要看队列是否有序约束和数据库承载能力。批量处理、减少单条查询和扩容消费者都可能有效。
>
> 积压期间用户看到的热度会延迟，应监控队列深度、最老消息年龄和消费失败率，并准备降级非关键统计。

## 320. 死信队列如何使用？

### 面试时可以这样答

> 消息超过重试次数、过期或被拒绝后进入 DLQ，保留原消息、失败原因和重试次数。运维或后台任务可以修复根因后重新投递。
>
> DLQ 不是垃圾桶。必须有告警、查看和处理流程，也要避免无限重放毒消息。重放前应修复代码或数据并验证幂等，保留原消息 ID 才能关联最初失败与后续处理结果。

## 321. AOP 如何统计接口耗时？

### 面试时可以这样答

> 切面拦截 Controller 或自定义注解方法，调用前记录单调时钟，`proceed` 放在 try 中，finally 计算耗时并记录方法、状态和 traceId。异常不能被切面吞掉，要继续抛给统一异常处理。
>
> 使用 `System.nanoTime` 计算耗时比 wall clock 更稳，日志内容要避免打印完整请求体和敏感参数。

## 322. 为什么使用 MDC 保存 traceId？

### 面试时可以这样答

> MDC 是线程上下文中的键值映射，日志格式可以自动带 traceId，不用每层方法手工传参。入口过滤器创建或接收 traceId，放入 MDC，请求结束时必须 clear，防止线程池复用串号。
>
> 它解决日志关联，不等同于完整分布式追踪。跨服务还要通过 Header 传播，并记录 span 关系。

## 323. traceId 如何生成？

### 面试时可以这样答

> 现有笔记记录的方案由服务器 IP 的十六进制、毫秒时间戳、进程号和自增序列组成，便于从 ID 看出生成节点和时间。面试时要说明这是项目方案，不是行业唯一标准。
>
> 生产中也可用 UUID、雪花 ID 或 OpenTelemetry trace ID。重点是全局碰撞概率、长度和跨服务透传，不必追求可读性。

## 324. MDC 为什么在异步线程中会丢？

### 面试时可以这样答

> MDC 通常基于 ThreadLocal。请求线程切到线程池、CompletableFuture 或消息消费者后，不会自动继承原线程值，即使偶尔继承也可能因线程复用污染。
>
> 提交任务时复制 contextMap，在子线程设置并 finally 清理；Spring TaskDecorator 或日志框架适配器可统一处理。MQ 中要把 traceId 放消息 Header，再在消费端重建 MDC。

## 325. 这个项目你最该强调的工程收获是什么？

### 面试时可以这样答

> 我不把亮点概括为“会用 Redis、ES 和 MQ”，而是理解了事实数据与派生数据的边界。MySQL 保存可靠事实，Redis 与 ES 提供读性能，RabbitMQ 传播变化，日志链路负责定位它们何时不一致。
>
> 面试时我会选一次真实问题讲清楚现象、定位证据、修改和验证。若没有真实压测数字，就不编 QPS 或提升百分比。
