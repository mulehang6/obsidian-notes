# 答题标准与简历风险

## 一道合格答案应该有什么

项目题建议按下面的顺序组织，而不是机械套用八股模板：

1. **先给结论**：一句话回答面试官真正问的内容。
2. **再讲场景**：项目里为什么出现这个问题，约束是什么。
3. **说明选择**：为什么选这个方案，没有选哪些替代方案。
4. **落到实现**：关键类、数据流、状态变化或异常路径是什么。
5. **给出验证**：测试、日志、指标或复现方式是什么。
6. **主动限定边界**：当前实现解决到哪里，哪些仍是待改进项。

一个回答如果只有定义，没有取舍和证据，听起来就像背题。反过来，只报类名和代码细节而没有结论，也会让面试官抓不到重点。

## 回答长度

- 直接问答：先用 30 到 60 秒给出完整结论。
- 项目深挖：准备 2 到 3 分钟版本，包括动机、实现、异常路径和验证。
- 继续追问：每次只补当前问题，不要把预先背好的整段重新说一遍。

## 当前材料中的高风险表述

### 1. “三级缓存解决 Spring 循环依赖”过于绝对

更准确的说法是：Spring 的三级缓存机制可以处理一部分单例 Bean 的属性注入循环依赖，并且提前暴露对象工厂有助于在需要代理时取得早期引用。它不能覆盖构造器循环依赖，也不等于所有作用域、所有代理场景都能正常处理。

面试时不要只背三个 Map 的名字。重点解释为什么不能直接把半成品 Bean 当成最终 Bean，以及早期代理对象与最终对象保持一致的问题。

### 2. “Session Tree 已实现”要区分功能层级

当前源码已经能证明会话树落地：外层任务用 `parentConversationId` 组成父子树，内层 `ConversationEntry` 用 `parentId` 保留消息、推理、工具、摘要和标签等兄弟分支；`ConversationTreeController` 提供 fork、clone、导航、回到 head、归档、恢复和删除，SQLite 也持久化了完整条目图。不要再把它说成纯设计项。

面试时仍要主动限定边界：这是一套可恢复内容与分支路径的 Session Tree，不等于 Koog 图级 Agent Checkpoint。当前没有持久化图节点、在途请求、工具进程或审批 continuation，运行中任务重启后会恢复为“执行已中断”；分支也不会自动创建 Git worktree 或隔离文件副作用。

可以回答：

> 我实际落地的是两层会话树：任务之间用父子关系组织，任务内部用条目父指针保留兄弟分支；活动 leaf 投影出 UI 时间线和模型 history，SQLite 保存完整条目图。它支持从用户消息 fork、克隆当前路径、切换分支和回到 head，但这仍是任务快照与会话分支能力，不是 Koog 图节点断点续跑。

### 3. “工具失败后继续运行”不能说成无条件容错

当前事件模型允许把单次工具失败表示为 `ToolCallFailed`，并继续由 Agent 决定下一步。但是否真的继续，仍取决于消息历史是否补齐工具结果、模型后续决策、迭代上限以及不可恢复异常。应当说“系统具备单次工具失败后的恢复路径”，而不是“工具失败不会影响任务”。

### 4. “无限迭代”不是真正没有上限

项目把 `-1` 映射为 Koog 接收的 `Int.MAX_VALUE`。这只是配置语义上的“不主动限制迭代次数”，进程生命周期、上下文长度、取消信号、模型或工具异常仍然会终止运行。

### 5. RAG 项目不要只说技术栈

“Spring Boot + Elasticsearch + Redis + Kafka + MinIO”不是项目亮点。至少要能回答：

- 文档如何解析、清洗和切片，为什么这样设置粒度；
- 向量、关键词与元数据过滤如何组合；
- 如何判断召回质量，而不是只看最终回答顺不顺；
- Elasticsearch 作为向量检索方案的适用边界；
- 数据更新、删除、失败重试与索引一致性如何处理。

详见 [[派聪明/派聪明面经]]，后续会整理到 251-300 题。

### 6. 技术交流平台要准备一致性和退化路径

排行榜、点赞、搜索和异步消息很容易被追问：

- Redis 与数据库数据不一致怎么办；
- RabbitMQ 消息丢失、重复、堆积怎么办；
- Elasticsearch 同步延迟如何向用户解释；
- AOP + MDC 能追踪什么，跨线程和跨服务时如何传递；
- 缓存击穿、穿透、雪崩分别发生在哪里。

不要把“用了中间件”当成“解决了问题”。中间件只把问题转化成了新的工程约束。

## 不确定时怎么答

可以明确区分三层：

> 这部分我实际完成的是 A，并通过 B 验证。C 是我读过源码后形成的理解，但没有在项目中落地。若继续改进，我会先用 D 做小范围验证，再决定是否引入。

这种回答比猜一个听起来完整的结论可靠。面试官通常不要求候选人无所不知，但会关注你是否能识别事实、推断和计划之间的界线。
