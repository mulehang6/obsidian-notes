# Mulehang Agent：工具调用与失败恢复（051-075）

这一卷不讨论“模型会不会调用函数”这种表面问题。重点是工具怎么注册、危险动作在哪里被拦住、失败结果如何进入历史，以及 MCP 工具为什么不能绕开本地权限。

## 051. `ToolRegistry` 在项目里起什么作用？

### 面试时可以这样答

> `ToolRegistry` 是模型可用工具的运行时清单。它把工具名称、参数描述、返回类型和执行实现交给 Koog。模型只能请求清单中的工具，执行器也只会从这个注册表解析调用。项目先通过 `DesktopToolRegistryFactory` 创建本地工具注册表，再由 `McpToolRegistryBridge` 把本轮启用的远程工具合并进去，最后把合并后的注册表交给 `AIAgent`。
>
> 我没有把注册表做成全局静态对象，因为工具能力与当前会话有关。工作区路径、权限档位、交互桥、取消状态、Hook、sessionId 都是本轮上下文。每次按请求构建，可以防止 A 会话的工作区或权限泄漏到 B 会话。
>
> 注册表只是能力入口，不是安全边界。模型能看到工具，不代表可以无条件执行。真正执行前还要经过路径检查、权限矩阵、Hook、自动审核或人工确认。

### 继续追问

- **为什么不按角色复用一个 Registry？** 复用工具定义可以，但绑定工作区、权限和会话状态的实例不应跨会话共享。
- **模型编造一个不存在的工具名怎么办？** 执行器无法在注册表解析，应返回明确失败，让模型修正，不能用反射猜测执行。

## 052. `DesktopToolSet` 里有哪些工具，为什么这样划分？

### 面试时可以这样答

> 当前工具集覆盖读取文件、列目录、按 glob 找文件、搜索代码、应用补丁、运行 PowerShell、运行指定 Shell 和向用户提问。划分依据是动作语义，而不是底层都能否用命令行完成。读取、搜索、写入和执行命令的风险不同，参数、返回结构和审批规则也不同。
>
> 例如改文件必须走 `apply_patch`。它能先生成精确 diff，再决定是否批准。Shell 工具明确不负责编辑文件，因为把写入藏在一段命令里后，系统很难预览实际变化。文件搜索也使用独立工具，避免模型为了找一个类就执行任意脚本。
>
> 这种划分会增加工具数量，但换来了更窄的权限和更清楚的审计记录。工具越通用，模型越方便，安全判断却越困难。桌面 Agent 应优先提供用途明确的小工具。

## 053. 工具的名称和描述为什么会影响调用质量？

### 面试时可以这样答

> 模型选择工具时主要依赖名称、说明和参数 schema。描述含糊时，模型容易把 `grep_code` 当文件名搜索，也可能没读原文件就生成补丁。项目在 `@LLMDescription` 中写了使用顺序和反例，例如先用 `list_dir`、`glob_files`、`grep_code` 发现目标，再用 `read_file` 获取上下文，修改文件只用 `apply_patch`。
>
> 描述不能代替程序校验。模型仍可能传入非法正则、超大 limit 或外部绝对路径，所以实现会限制行数、结果数、超时和路径范围。好的描述降低误调用，参数校验负责兜底。
>
> 我会通过失败率和重复调用观察描述是否有效。如果模型经常在 `glob_files` 与 `grep_code` 间来回试，问题可能不是模型笨，而是工具边界没有说清。

## 054. 为什么要求修改前先 `read_file`？

### 面试时可以这样答

> 补丁需要匹配当前文件的真实上下文。模型若只凭搜索片段或旧历史修改，很容易覆盖用户刚做的改动、复制错误的行号前缀，或在同名代码中改错位置。先读目标文件，可以确认内容、编码、相邻逻辑和最新状态。
>
> 这也是并发编辑下的基本防护。`read_file` 不能彻底消除读取后又被修改的竞态，但能明显缩短模型凭空编辑的距离。更严格的实现还可以在预览补丁时校验原始上下文或文件摘要，不匹配就拒绝应用并要求重读。
>
> 面试时不要把它说成绝对保证。它是一条降低错误概率的操作规则，真正防止覆盖还依赖补丁上下文匹配和版本检查。

## 055. 为什么禁止通过 Shell 修改文件？

### 面试时可以这样答

> Shell 可以把读写、删除、重定向和命令替换混在一个字符串里。审批界面看到的是命令文本，很难稳定推导最后哪些文件会变化。不同 Shell 的转义规则也会让静态判断失真。项目因此要求文件变化走 `apply_patch`，Shell 只承担确实需要进程执行的任务。
>
> `apply_patch` 会先解析补丁，得到每个目标文件的 diff，判断是否包含工作区外写入，再把预览交给用户或审核器。它比批准一句 `Set-Content` 或重定向命令更容易理解和回滚。
>
> 这并不代表 Shell 绝对不能改变文件系统，而是产品策略不允许 Agent 用它做文件编辑。实现还要检测明显危险命令，不能只靠工具描述自律。

## 056. 工作区路径为什么是工具安全的核心？

### 面试时可以这样答

> Agent 获得文件工具后，最先要限定它能操作哪里。项目把 `workspacePath` 注入 `DesktopToolSet`，相对路径都应解析到这个工作区。写入风险也区分 `WORKSPACE_WRITE` 与 `EXTERNAL_WRITE`。即使某个权限档位允许自动修改工作区，也不应顺便允许改用户目录或系统目录。
>
> 路径校验不能只检查字符串前缀。需要规范化绝对路径，处理 `..`、符号链接、大小写和 Windows 盘符，再判断最终目标是否仍在工作区内。外部路径不是普通失败后的备用选择，它必须是用户有意选择的目标。
>
> 这里的原则是最小作用域。用户把一个项目交给 Agent，不等于把整台电脑都交给它。

## 057. 为什么读取工作区外文件也要审批？

### 面试时可以这样答

> 读取不是无风险操作。工作区外可能有 SSH 密钥、浏览器配置、其他项目源码或包含个人信息的文档。模型读到后，内容还可能进入提示词、日志或远程模型请求。只防写入而放开任意读取，会留下明显的数据泄露通道。
>
> `read_file` 会先解析路径。如果目标在工作区内就继续；如果在外部，则构造一个风险为 `UNKNOWN` 的审批请求，经过 Hook、AUTO 审核或人工确认。拒绝后不读取内容。
>
> 真正的产品还应对敏感文件名、凭据格式和日志脱敏做额外控制。审批只是授权动作，不代表可以把读取结果原样记录到所有日志中。

## 058. 项目如何给工具动作分级？

### 面试时可以这样答

> 当前模型至少区分工作区写入、外部写入、命令执行、危险操作和未知风险。风险级别会影响自动批准、人工确认和审计来源。例如工作区补丁在 `EDIT_ALLOW` 下可以自动放行，外部写入不会因为这个档位就获得同样待遇。明显危险命令则在进入普通审批前由硬规则拒绝。
>
> 风险不能只看工具名。同一个 `apply_patch`，改项目 README 与改工作区外配置不是一个级别；同一个命令工具，执行测试与递归删除也不同。因此判断需要结合目标路径、操作意图、命令内容和 diff。
>
> 目前的分类是工程化起点，不是完整的安全模型。后续可以加入网络访问、凭据接触、数据规模和可恢复性等维度。

## 059. 五种 `PermissionPreset` 有什么区别？

### 面试时可以这样答

> 当前有 `AUTO`、`DEFAULT`、`EDIT_ALLOW`、`PLAN` 和 `BRAVE`。只读工具在五种档位中默认可用。`PLAN` 明确禁止写入和命令执行。`EDIT_ALLOW` 可以自动批准工作区内写入，但不会自动批准执行命令。`BRAVE` 可以自动批准写入和执行。`DEFAULT` 不自动批准这两类动作。`AUTO` 会把动作交给独立审批模型，审核器给不出合法结论时再回退人工。
>
> 这里最容易答错的是把 `AUTO` 说成全自动放行。它只是自动评审，不是取消安全检查。另一个边界是 MCP 工具，项目把它们视为外部危险操作，不会因为普通本地工具策略就默默执行。
>
> 权限档位控制默认决策，Hook 和硬规则仍能阻止动作。越宽松的档位越需要明确提示和审计。

## 060. `AUTO` 模式是怎么审批的？

### 面试时可以这样答

> `AUTO` 会构造包含工具名、风险、目标路径、操作意图和 diff 摘要的 `ApprovalRequest`，交给独立的 `KoogToolApprovalAgent`。这个审核 Agent 使用单轮、无工具的快速模型，只允许返回 `ALLOW`、`ASK` 或 `DENY`。
>
> 若输出无法解析，或者审核模型调用失败，代码不会默认放行，而是返回 `ASK`，转人工确认。这是 fail closed 的思路。危险风险更严格，审核 Agent 在调用模型前就直接 `DENY`，来源记为 `hard-rule`。
>
> 自动审批的价值是减少低风险确认弹窗，但它本身也会犯错。因此输入必须限制和脱敏，决策来源需要记录，并且不能让审核 Agent 调用工具改变环境。

## 061. 为什么审批 Agent 要与主 Agent 隔离？

### 面试时可以这样答

> 主 Agent 的目标是完成用户任务，它天然有推动动作执行的倾向。如果让它同时判断自己的动作是否安全，相当于让申请者兼任审批者。项目使用独立 prompt、独立模型调用和空 `ToolRegistry` 的审核 Agent，只做一次分类，不让它继续行动。
>
> 隔离还能减少提示注入影响。工具参数或文件 diff 可能包含诱导文字，审核系统提示要求只返回三个固定值，解析器拒绝其他输出。它仍不能彻底消除注入，但比直接相信主 Agent 的自我评价更稳。
>
> 最终兜底仍是硬规则和人工。模型审批适合处理语义模糊的中间区域，不适合覆盖明确禁止的危险操作。

## 062. 为什么危险操作直接拒绝，而不是让模型判断？

### 面试时可以这样答

> 对递归删除、破坏性重置等明确危险动作，没有必要花一次不稳定的模型判断。代码在 `run_shell` 中先调用危险命令检测，命中后记录审计并返回拒绝，不进入普通审批。`KoogToolApprovalAgent` 对 `DANGEROUS` 风险也直接给 `DENY`。
>
> 硬规则的优点是确定、便宜、可测试。缺点是覆盖有限，可能误报，也可能被复杂转义绕过。所以项目同时限制 Shell 用途，不允许用它编辑或删除文件，并把常见动作拆成结构化工具。
>
> 面试时要承认当前注释里也有 TODO，未来希望引入 Shell 语法树，用解析结果替代模型提供的 `operation_intent`。现在的意图文本只能帮助审核，不能证明命令真实效果。

## 063. 自动审核失败时为什么回退人工，而不是默认拒绝？

### 面试时可以这样答

> 自动审核失败可能只是模型超时、返回格式多了说明文字，或服务暂时不可用。如果一律拒绝，AUTO 模式会在网络波动时让正常工作完全停摆。项目把这类情况标成 `ASK`，交给用户做最终决定，同时记录 `invalid_model_output` 或 `reviewer_failed` 原因。
>
> 这不是宽松放行。没有人工同意，动作仍不会执行。它在安全和可用性之间选择了“无法自动判断就请求人”。对于已经由硬规则认定的危险动作，则不会回退人工绕过硬拒绝。
>
> 审批结果应区分决定和来源。相同的 `ASK`，可能来自策略要求、Hook 强制或审核器失败，排障时含义不同。

## 064. `apply_patch` 为什么先预览，再批准，再落盘？

### 面试时可以这样答

> 用户真正需要批准的是文件将发生什么变化，而不是模型声称“我要修一个 bug”。`apply_patch` 先解析完整补丁，计算每个文件的 diff 和目标路径，再判断是否包含工作区外写入。审批界面因此能展示精确变化，批准后才真正应用。
>
> 这个顺序也防止先改后问。若补丁格式错误、上下文不匹配或目标越界，预览阶段就应失败，不触碰磁盘。审批通过后仍可能因为并发修改导致应用失败，这种失败要原样返回模型，不能静默重试覆盖新内容。
>
> 多文件补丁需要一次展示全部文件，而不能只拿第一处改动概括。当前请求模型同时保留单个 diff 和 diff 列表，就是为了完整预览。

## 065. 工具审计日志应该记录什么，不该记录什么？

### 面试时可以这样答

> 审计至少要回答谁在什么会话里请求了哪个工具、目标是什么、风险级别、最终允许还是拒绝、决定来自硬规则、Hook、自动审核还是人工，以及失败原因。这样发生误操作时，才能还原决策过程。
>
> 审计不应原样记录密钥、完整环境变量、请求头或大段敏感文件内容。命令和 diff 也可能包含凭据，需要截断或脱敏。项目的自动审批记录已经区分 `source` 和 `reason`，这是可审计性的基础。
>
> 日志本身也需要访问控制和保留期限。把所有敏感输入永久写进本地 JSON，并不能因为“只在本机”就视为安全。

## 066. PowerShell 工具是如何执行命令的？

### 面试时可以这样答

> `DesktopPowerShellTool` 先探测 `pwsh` 版本，只支持 7.x。实际执行时使用 `pwsh -NoLogo -NoProfile -Command`，工作目录固定为当前 workspace，避免用户 Profile 脚本影响行为。工具参数包含脚本、超时、取消函数和输出回调。
>
> 外层 `DesktopToolSet` 要求模型同时给出中文 `operation_intent`，并在执行前经过权限和审批。意图用于给用户理解，但安全判断不能只相信这段说明。命令本身仍要受用途限制和危险模式检测。
>
> 返回结果包括退出码、stdout、stderr、是否截断以及完成、超时或取消状态。模型据此判断测试失败、命令不存在，还是用户主动停止。

## 067. 命令超时和用户取消有什么区别？

### 面试时可以这样答

> 超时表示命令超过调用方设定的时间预算，取消表示上层任务已不再需要它，例如用户停止 Agent 或 Flow 被取消。两者都要终止子进程，但呈现和后续策略不同。超时可能提示增加合理预算或优化命令，取消则不应被模型当成工具错误继续重试。
>
> PowerShell 工具默认超时 120 秒，最大 600 秒，并把 `isCancelled` 回调传给进程运行器。结果用不同 `Outcome` 表示，不靠字符串猜测。
>
> 只取消协程而不处理子进程会留下后台任务继续占用资源。桌面 Agent 必须把取消向下传播到正在执行的进程和输出读取逻辑。

## 068. 为什么要分别流式传递 stdout 和 stderr？

### 面试时可以这样答

> 长命令若等结束后一次返回，用户会以为应用卡死，输出过大还会占满内存。进程运行器通过回调逐块发送 stdout 和 stderr，网关再转换为带流类型的 `ToolOutputDelta`，UI 可以实时展示。
>
> 两个流不能简单拼成一个字符串。编译器常把诊断写到 stderr，但退出码仍可能成功；有些程序也会交错输出。保留来源有助于排障。最终结果还会标注内存安全上限处是否截断，避免模型把不完整日志当成完整证据。
>
> 流式事件解决可见性，最终退出码负责判定进程结果。看到 stdout 中有“success”不能替代检查退出码。

## 069. `ask_user` 工具什么时候该用？

### 面试时可以这样答

> 只有当决定会实质改变结果，并且现有对话和工具无法查明时才应询问。例如用户没有说明要修改当前模块还是整个项目。文件是否存在、测试是否通过这类事实应该由工具检查，不能甩给用户。
>
> 项目支持一次提交多个问题，也兼容旧的单问题参数。输入会被规范化，空问题被拒绝，选项数量受限，并允许自由文本。网关先发出 `QuestionRequested` 事件，再等待交互桥返回答案。
>
> Agent 过度提问会把工作推回用户，完全不问又会擅自扩大范围。判断标准是这个未知信息能否安全地用可逆操作验证，以及不同答案是否会导致明显不同的实现。

## 070. 工具执行失败后，Agent 为什么还能继续？

### 面试时可以这样答

> 工具失败也是环境观察。例如路径不存在时，模型可以先搜索正确路径；测试失败时，可以读取报错后修复。项目用 `ToolCallFailed` 表示单次工具失败，它和运行级 `Failed` 不同。图仍可把失败结果交回模型，由模型决定重试、换方法或结束说明。
>
> 能继续不等于必须继续。权限拒绝、用户取消、重复相同失败和不可恢复的基础设施错误都可能要求终止。系统需要保留失败类型和原因，而不是统一返回 `false`。
>
> 更重要的是，失败路径仍要闭合消息协议。直接抛异常并丢掉工具结果，会让下一轮模型请求中的调用历史不合法。

## 071. 为什么每个 `function_call` 都必须有对应的 `function_call_output`？

### 面试时可以这样答

> 工具调用协议把一次调用分成模型发出的 `function_call` 和程序返回的 `function_call_output`，二者通过 `call_id` 关联。没有 output，服务端会认为上一轮工具调用仍未完成，后面的 assistant 内容或新用户消息就处在非法顺序。
>
> 成功时 output 是工具结果，失败时也要生成包含错误信息的 output。错误不是缺席结果，而是一种结果。项目曾针对 DeepSeek 遇到 `No tool output found for tool call X` 的 400，因此增加了回归测试。
>
> 这个问题很容易被 UI 掩盖。界面上显示“工具失败”并不代表模型历史里已经补齐 output，必须检查真正发送给模型服务的请求体。

## 072. 失败工具历史的回归测试是怎么做的？

### 面试时可以这样答

> 测试构造了一段历史，其中 assistant 消息包含五个失败的 ToolCall，没有真实 ToolResult，并附带最终文本。录制型 HTTP Client 会捕获下一轮流式请求体，不发真实网络请求。
>
> 断言分两层。数量上，请求体必须保留五个 `function_call`，并为每个 call_id 生成一个匹配的 `function_call_output`。顺序上，工具结果必须紧跟最后一个 function call 闭合这一轮，不能在中间插入另一个 assistant output message。
>
> 这类测试比只断言内存对象更有价值，因为 bug 出现在协议序列化之后。捕获最终 HTTP body，才能证明发给提供商的数据真的合法。

## 073. MCP 工具如何合并进本地工具注册表？

### 面试时可以这样答

> 网关先创建本地 `ToolRegistry`，再根据本轮资源快照中的 MCP 服务配置建立连接。`McpToolRegistryBridge` 取得各服务的远程注册表，把工具逐个包装后加入本地列表，最后生成新的合并注册表。
>
> 连接失败不会让整个应用无提示卡住。Bridge 返回工具注册表和诊断列表，网关把每条诊断转换为可见的 `ToolCallFailed` 事件。这样某个 MCP 服务不可用时，用户能知道缺失的是哪个服务，其他工具仍有机会工作。
>
> MCP 连接由应用级管理器持有，一轮结束释放的是本轮包装视图。回答时要区分连接生命周期和 Agent run 生命周期。

## 074. 本地工具与 MCP 工具重名怎么办？

### 面试时可以这样答

> 项目选择本地工具优先。合并时先收集已有名称，远程工具若重名就不加入，并生成包含 serverId 和冲突名称的诊断。它不会静默覆盖本地实现。
>
> 静默覆盖很危险。模型看到的仍是同一个名字，但实际执行代码、权限和返回格式可能已经变化。即使两个工具功能相近，也应通过命名空间或显式配置解决，而不是依赖加载顺序。
>
> 当前策略简单且确定，但大量 MCP 服务接入后可能需要 `server.tool` 形式的命名空间。无论采用哪种方案，冲突必须在运行前可见。

## 075. MCP 工具为什么还要再包一层审批？

### 面试时可以这样答

> 远程工具来自外部服务，项目无法静态确认它是只读查询还是会修改外部系统，所以 `ApprovalGatedMcpTool` 默认把它视为 `DANGEROUS`。调用前先执行 `PRE_TOOL_USE` Hook，再检查当前权限档位，然后发出 `PERMISSION_REQUEST` Hook，最后根据策略或人工确认决定是否调用 delegate。
>
> `PLAN` 会直接禁止执行 MCP 工具。Hook 可以 `BLOCK` 或强制 `ASK`。即使 Hook 返回普通继续，只有权限允许自动执行或交互桥确认后才放行。这样 MCP 不能绕过本地工具已有的权限体系。
>
> 包装器保留原工具的 descriptor、参数类型和结果类型，只在执行入口增加控制。安全层若改变 schema，模型看到的定义和实际调用就可能不一致。
