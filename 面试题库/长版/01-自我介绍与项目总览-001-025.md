## 007. 技术交流平台最核心的数据链路是什么？

### 面试时可以这样答

> 写请求先经过 Web 层参数校验和身份上下文，进入 Service 执行业务规则，再在事务中写 MySQL。Redis 排行榜和 ES 索引属于可重建的派生数据，消息队列用于把允许最终一致的更新从主请求移出。
>
> 设计关键是明确权威来源：详情和最终状态以 MySQL 为准，Redis 或 ES 缺失时可回源或降级。异步消费者按业务 ID 幂等处理，并对失败和积压提供监控，不能用“发了 MQ”替代一致性说明。

## 008. 为什么技术交流平台要做模块化？

### 面试时可以这样答

> core 放稳定领域模型与基础约定，api 定义对外契约，service 承载业务用例，web 处理协议入口，ui 负责展示。模块化使依赖方向更清楚，也便于独立测试和替换基础设施实现。
>
> 但模块不是越多越好。若只把类分目录却允许循环依赖，仍然没有边界；我会通过构建依赖和公开接口限制跨层访问，并在新增功能时检查它属于哪类变化。

## 009. 为什么项目同时使用 MySQL、Redis 和 Elasticsearch？

### 面试时可以这样答

> 三者解决不同访问模式。MySQL 提供事务、约束和权威状态；Redis 以低延迟数据结构处理热点缓存、计数与排行榜；Elasticsearch 用倒排索引支持分词、相关性和复杂搜索。
>
> 代价是多份数据的一致性和运维复杂度，所以不是“技术越多越高级”。如果数据量和搜索需求很小，先用 MySQL 会更合理；引入后必须能说明同步、降级与重建路径。

## 010. 点赞为什么适合异步化？

### 面试时可以这样答

> 点赞后的通知、统计聚合等副作用不一定要阻塞用户主请求，可先可靠记录核心状态，再通过 RabbitMQ 异步处理后续动作，缩短响应链路并削峰。消费者失败可重试，也能独立扩容。
>
> 用户是否已经点赞这类即时状态不能无条件全部异步，否则会出现重复操作和体验混乱。要区分同步确认的核心写入与异步派生动作，并用唯一约束、消息 ID 和条件更新保证幂等。

## 011. 排行榜为什么选择 Redis ZSet？

### 面试时可以这样答

> ZSet 的成员唯一、score 可原子增减，并原生支持按分数取 Top N 和查询名次，正好匹配排行榜的核心访问。相比每次在 MySQL 聚合排序，它能降低高频读取和更新的延迟。
>
> MySQL 或事件日志仍保留可重建事实，Redis 是派生视图。需要定义同分排序、统计周期、TTL 与校准机制，避免缓存丢失后无法恢复或排名长期漂移。

## 012. Elasticsearch 与 MySQL 的数据不一致怎么办？

### 面试时可以这样答

> 我先明确搜索允许最终一致，详情回到 MySQL 校验。写库成功后通过可靠事件或 CDC 更新 ES，消费者以业务 ID 幂等 upsert；失败进入重试和死信，并提供按 ID 对账与全量重建能力。
>
> 如果搜索结果指向已删除或权限变化的数据，详情接口仍必须做权限和存在性校验。不能把 ES 搜到就当作业务真相，也不能只靠固定延迟假设同步已经完成。

## 013. 你的 RAG 项目解决什么问题？

### 面试时可以这样答

> 它让用户上传或接入私有文档，经过解析、切片、向量与关键词索引，在提问时召回相关片段，经过融合和重排后把证据交给模型生成答案，并尽量返回引用。
>
> 项目重点不只是“接了大模型 API”，而是检索质量与可评估性。我会把失败拆成解析、切片、召回、排序、上下文组装和生成阶段，分别收集证据，而不是统一归因于模型不聪明。

## 014. RAG 为什么需要混合检索？

### 面试时可以这样答

> 向量检索擅长语义相似，但可能忽略编号、专有名词和精确字符串；BM25 对精确术语强，却不理解同义表达。两路召回后用 RRF 等排名融合，通常能覆盖更多查询类型。
>
> 混合不是固定更好。需要用标注问题集测 Recall@K、MRR 或 nDCG，按内容类型调权重，并记录每路贡献；否则增加一路只会提高延迟和复杂度。

## 015. RAG 切片策略如何设计？

### 面试时可以这样答

> 优先按标题、段落、列表和代码块等结构边界切分，再控制 token 上限并保留适量重叠；每个片段携带文档、章节、页码和权限元数据。纯固定字符切割容易把语义和代码结构截断。
>
> 块太小会丢上下文并增加候选噪声，太大则降低定位精度、浪费上下文窗口。应通过问题集比较不同粒度的召回命中和最终回答质量，而不是只凭经验选一个数字。

## 016. 如何评估 RAG，而不是凭感觉看答案？

### 面试时可以这样答

> 建立包含问题、相关证据和期望要点的评测集，把检索与生成分开评。检索看 Recall@K、MRR、nDCG，生成看忠实性、答案相关性、引用命中和拒答；线上再看用户反馈、延迟与成本。
>
> 每次修改切片、embedding、融合或 prompt 后运行同一基线集，并保留失败分类。没有真实标注时可从日志抽样人工审核，但要避免完全让另一个模型自评后直接当真值。

## 017. 如何降低 RAG 幻觉？

### 面试时可以这样答

> 先提升证据质量：权限过滤、查询改写、混合召回和重排；再限制生成只根据给定上下文回答，要求引用，并在证据不足或冲突时明确拒答。结构化任务可让模型输出可校验字段。
>
> 最终还要在应用侧验证引用确实来自检索片段，对高风险答案增加规则或人工确认。模型提示词只能降低概率，不能形成事实保证。

## 018. Mulehang Agent 的总体架构是什么？

### 面试时可以这样答

> UI 发起一次运行后，系统冻结本轮使用的模型、系统提示、MCP 工具与本地资源快照；Koog 图节点调用模型并接收流式输出，识别工具调用后交给桌面工具集与审批代理执行，再把工具结果写回消息历史继续推理。
>
> 运行过程以事件流向 UI 暴露文本、工具请求、工具结果、失败和完成状态，SQLite 保存任务等本地数据。这个结构把一次运行的确定性资源与全局可变配置分开，便于取消、诊断和后续恢复。

## 019. Agent 与普通聊天应用最大的工程差异是什么？

### 面试时可以这样答

> 普通聊天主要是请求和响应；Agent 会循环产生工具调用，工具可能修改文件或执行进程，还会等待用户审批、失败重试和被取消。因此需要显式状态机、权限边界、结构化事件和可恢复记录。
>
> 模型输出只能视为不可信建议，真正副作用由受控执行层完成。每个工具要有参数校验、路径策略、超时、输出上限和审计，不能让模型直接获得无限系统权限。

## 020. 你在 Mulehang Agent 中最关注的设计是什么？

### 面试时可以这样答

> 我最关注工具执行边界和事件语义。工具调用先经过策略判断，必要时发起审批；进程执行限制工作目录、超时和输出；流式事件区分工具失败与整轮运行失败，使 UI 能正确展示并决定是否继续。
>
> 另一个重点是每轮固定运行时资源快照，避免用户在运行中修改配置导致前后使用不同工具或提示词。这些设计比单纯“能调用模型”更接近可用 Agent。

## 021. 为什么 Mulehang Agent 使用 Kotlin 和 Compose Desktop？

### 面试时可以这样答

> Kotlin 与 JVM 生态兼容，协程适合表达流式模型调用、取消和异步事件；密封类型、空安全与数据类也适合建模运行状态。Compose Desktop 用声明式状态构建跨平台桌面 UI，与 Kotlin 代码共享类型和协程模型。
>
> 代价是桌面生命周期、JCEF 和协程作用域需要谨慎管理，部分库版本兼容也要验证。选择它是为了 JVM 生态与桌面交互的组合，不是因为语言本身自动带来更高性能。

## 022. 当前 Agent 项目哪些功能还没有完成？

### 面试时可以这样答

> 当前代码已经有流式执行、工具审批、MCP 与本地资源快照、Hook、SQLite 任务持久化，以及已经落地的两层 Session Tree：外层任务通过 `parentConversationId` 组织，内层条目通过 `parentId` 保留兄弟分支。已有 fork、clone、分支导航、自动或自定义分支摘要、回到 head、归档/恢复/删除和右侧树面板。
>
> 仍未完成的是更强的 Agent Checkpoint：数据库没有保存 Koog 图节点、在途网络请求、工具进程、审批 continuation 和外部副作用确认，因此重启不能从原执行节点安全续跑；分支也不自动隔离工作区。下一步应围绕执行状态机、幂等工具记录和工作区隔离补齐，而不是把现有 Session Tree 误称为完整断点续跑。

## 023. 你如何证明项目不是照着教程拼出来的？

## 024. 你的优势和不足是什么？

### 面试时可以这样答

> 我的优势是愿意沿执行链把问题拆开并核实证据。例如做 RAG 时区分召回失败与生成失败，做 Agent 时把工具失败和运行失败建成不同事件，而不是只改提示词或加 try-catch。
>
> 不足是生产规模经验还有限，目前很多结论来自项目压测和源码验证，而非大流量线上事故。我正在通过更完整的指标、故障注入、复盘记录和阅读框架实现来补齐；回答时不会把学习项目包装成生产成绩。

## 025. 如果面试官认为你的项目复杂度不够，怎么回答？

### 面试时可以这样答

> 我会先承认项目规模与成熟商业系统有差距，再把讨论落到可验证的复杂点：多存储一致性、消息幂等、RAG 评估、Agent 权限与取消。这些问题即使在小规模项目里也有明确正确性边界，我能说明设计、失败方式和验证。
>
> 同时说明哪些方案暂时没有引入，例如不为单机项目强行上分布式协调；若规模增长，什么指标会触发分库、分片或任务调度演进。这样既不夸大，也能展示对复杂度来源的理解。
