# Redis、缓存与分布式问题（451-475）

## 451. Redis 为什么快？

### 面试时可以这样答

> 主要数据在内存，避免磁盘随机访问；核心命令执行路径短，事件循环减少了共享数据结构上的线程竞争；RESP 协议和专门的数据结构也降低了通用数据库的额外成本。
>
> “单线程”不是完整解释，Redis 的网络 I/O、持久化和部分后台任务可使用其他线程或进程。复杂命令、大 key、网络和 fork 开销仍会造成延迟尖峰。

## 452. Redis 常见数据结构如何选？

### 面试时可以这样答

> String 适合缓存值、计数和位操作；Hash 适合字段化对象；List 适合简单双端队列；Set 做去重和集合运算；Sorted Set 按 score 排序，适合排行榜与时间轴；Stream 适合可消费确认的消息流。
>
> 选择应看访问模式和基数，而不是把整个 Java 对象一律 JSON 化。技术交流平台的排行榜用 ZSet 比“缓存一个完整排行榜 JSON 后每次重写”更容易做增量更新与区间查询。

## 453. String 底层为什么不是普通 C 字符串？

### 面试时可以这样答

> Redis 使用带长度和容量信息的动态字符串表示，可在 O(1) 获取长度，支持二进制安全，并通过预分配减少频繁扩容。值没有依赖 `\0` 作为终止符，因此可以存任意字节。
>
> 对业务的意义是 String 不只存文本，也可存序列化数据和整数计数；但大对象依然会占内存、阻塞传输和删除，二进制安全不等于适合无限增大。

## 454. ZSet 如何实现排行榜？

### 面试时可以这样答

> 成员唯一，score 决定排序，可用 `ZINCRBY` 原子增加分数，用 `ZREVRANGE` 或带分数版本取 Top N，用 rank 命令查询用户名次。相同分数还会按成员字典序形成确定顺序。
>
> 要先定义并列规则、统计周期和落库策略。若 score 同时编码时间做 tie-break，要注意浮点精度；排行榜通常是派生视图，最终事实仍应可从数据库或事件重建。

## 455. Redis 过期键如何删除？

### 面试时可以这样答

> Redis 结合惰性删除和周期性主动过期：访问键时发现过期就删除，后台也抽样扫描带 TTL 的键，避免所有过期键都等待访问。它不是为每个键单独创建定时器。
>
> 所以键到期与物理内存立即释放之间可能有短暂差距。大量键在同一时刻过期还会引发负载波动，应给缓存 TTL 加合理抖动并监控 expired_keys。

## 456. Redis 内存淘汰策略如何选择？

### 面试时可以这样答

> 达到 maxmemory 后，可选择不淘汰，或在所有键/带 TTL 键中按 LRU、LFU、随机或 TTL 等策略近似选择淘汰对象。作为纯缓存常考虑 allkeys-lru 或 allkeys-lfu，混合关键数据时要更谨慎。
>
> 淘汰意味着数据在 TTL 前也可能消失，应用必须能回源。Redis 同时承担缓存和不可丢状态时，单一淘汰策略很难表达两者优先级，最好拆实例或至少拆清资源边界。

## 457. RDB 和 AOF 有什么区别？

### 面试时可以这样答

> RDB 周期性生成数据快照，文件紧凑、恢复快，但两次快照之间的数据可能丢失；AOF 记录写命令，按刷盘策略缩小丢失窗口，文件通常更大，并需要重写压缩。
>
> 二者可组合使用，但仍不是备份的全部。要验证重启恢复、异地备份和灾难演练，并根据 RPO、RTO 选择刷盘与快照频率。

## 458. Redis 主从复制的作用与限制是什么？

### 面试时可以这样答

> 主节点把写入传播给副本，副本可用于读扩展和故障接管基础；断线后尽量增量同步，条件不满足时需要全量同步。复制通常是异步的，主节点确认写入不代表副本已持久化。
>
> 因此故障切换可能丢失最近写入，读副本也可能看到旧数据。需要按业务决定是否可接受，而不是把“有副本”等同于强一致和零丢失。

## 459. Sentinel 和 Cluster 解决的问题有什么不同？

### 面试时可以这样答

> Sentinel 监控主从实例、判断故障并选举新主，主要解决高可用，不做数据分片；Cluster 把键空间划为槽分布到多个主节点，并为每个主节点配置副本，同时解决容量扩展和一定的高可用。
>
> Cluster 的多键操作通常要求键位于同一槽，可用 hash tag 显式归组，但会带来热点风险。客户端还要处理重定向、拓扑变化和故障期间的错误。

## 460. 什么是缓存穿透？

### 面试时可以这样答

> 请求的数据在缓存和数据库都不存在，每次都绕过缓存打到数据库。可对合法参数做校验、对不存在结果短期缓存空值，或用布隆过滤器拦截确定不存在的 key。
>
> 空值 TTL 应较短并考虑后来创建数据时主动删除；布隆过滤器有假阳性且需要维护。还要配合限流，防止攻击者持续生成不同非法 key。

## 461. 什么是缓存击穿？

### 面试时可以这样答

> 某个高频 key 失效瞬间，大量请求同时回源重建，把数据库压垮。可用互斥重建让一个请求加载，其他请求等待或返回旧值；也可采用逻辑过期，后台异步刷新。
>
> 互斥锁必须有超时和所有者校验，等待也要有上限。逻辑过期提高可用性但允许短期旧数据，应明确业务能接受的陈旧窗口。

## 462. 什么是缓存雪崩？

### 面试时可以这样答

> 大量 key 同时过期，或 Redis 整体不可用，导致请求集中回源。应让 TTL 分散并加随机抖动，对热点预热，配置高可用，同时在应用侧做限流、熔断和降级。
>
> 只加随机 TTL 只能缓解集中失效，解决不了实例宕机。必须用容量压测验证数据库在降级流量下能否存活，并避免无限重试形成二次放大。

## 463. Cache Aside 如何工作？

### 面试时可以这样答

> 读时先查缓存，未命中则读数据库并回填；写时先更新数据库，再删除缓存，让下次读取重新构建。删除而非直接更新缓存，可减少多写方并发下旧值覆盖新值的窗口。
>
> 它仍不是强一致协议，删除失败或并发读写都可能短暂不一致。应配置 TTL，删除失败重试，必要时通过 binlog/消息补偿，并按业务定义可接受窗口。

## 464. 为什么“先删缓存再更新数据库”容易出错？

### 面试时可以这样答

> 删除后若并发读先查到旧数据库值并回填，随后写事务提交，缓存中就留下旧值直到过期。先更新数据库再删缓存可缩小这个典型窗口，但删除失败仍需处理。
>
> 延迟双删只能降低概率，延迟值难精确选择，也不是严格证明。强一致要求更高时，应减少双写来源，使用失效事件和版本校验，或直接绕开缓存读取权威数据。

## 465. 如何识别和治理热 key？

### 面试时可以这样答

> 通过客户端请求统计、Redis 热键采样、代理层指标和 CPU/网络分布识别，不能只看 key 大小。治理可在进程内增加短 TTL 缓存、拆分读副本、对可分片计数打散 key，或对重建请求合并。
>
> 本地缓存带来节点间不一致和失效广播问题，打散 key 也增加聚合成本。先确认热点是稳定、突发还是恶意流量，再选方案。

## 466. 什么是 big key？有什么风险？

### 面试时可以这样答

> big key 可能是超大字符串，也可能是成员过多的集合。读取、序列化、复制和删除都可能占用事件循环较长时间，造成延迟尖峰，并放大网络、持久化和迁移成本。
>
> 应用扫描工具与内存采样识别，按业务拆分、分页访问；删除使用渐进或异步方式。判断不能只按字节，还要看命令复杂度与访问频率。

## 467. Pipeline 和事务有什么区别？

### 面试时可以这样答

> Pipeline 把多条命令批量发送，主要减少网络往返，并不保证其他客户端命令不会穿插；MULTI/EXEC 把命令排队后按顺序执行，执行期间不会被其他命令插入，但它不提供传统数据库那样的自动回滚。
>
> 若后一条命令依赖前一条结果，普通 pipeline 也未必适用。原子读改写可考虑单条原子命令或 Lua 脚本。

## 468. Redis Lua 脚本适合什么场景？

### 面试时可以这样答

> 脚本在服务器侧原子执行多步逻辑，适合“校验锁所有者后删除”、限流计数等短小操作，还能减少网络往返。脚本运行期间会阻塞其他命令，因此必须有明确上界。
>
> 不应在脚本中遍历巨大集合或做复杂业务。集群中涉及的键还要满足同槽要求，并处理脚本缓存、超时和失败重试的幂等性。

## 469. 如何正确实现一个基础 Redis 分布式锁？

### 面试时可以这样答

> 获取锁用 `SET key token NX PX ttl`，token 对每个持有者唯一；释放时用 Lua 比较 token 后再删除，防止线程 A 的锁过期后误删线程 B 的新锁。业务耗时可能超过 TTL 时还要续期或重新设计临界区。
>
> 锁只提供尽力互斥，客户端暂停、网络分区和主从切换都可能破坏假设。对资金等强一致资源，应依靠数据库约束、版本号或具备 fencing token 的协调方案兜底。

## 470. 什么是 fencing token？

### 面试时可以这样答

> 每次成功获取租约时得到单调递增令牌，下游资源只接受比已处理令牌更新的写入。即使旧持有者因长暂停后恢复，它携带的旧令牌也会被拒绝。
>
> 这弥补了“锁已过期但旧客户端并不知道”的问题。前提是令牌生成单调，且真正被保护的存储系统参与比较，否则只在 Redis 侧生成数字没有保护作用。

## 471. Redis 实现限流有哪些方法？

### 面试时可以这样答

> 固定窗口计数简单但边界突刺明显；滑动窗口日志精确但占空间；滑动窗口计数是折中；令牌桶允许受控突发，漏桶强调稳定流出。Redis 可用原子命令或 Lua 完成判断与更新。
>
> 限流维度、窗口、突发容量和失败策略应来自下游容量。还要决定 Redis 不可用时是放行还是拒绝，并监控被限请求而非只返回 429。

## 472. 布隆过滤器为什么有误判？

### 面试时可以这样答

> 插入元素时对多个位设 1，查询时只要任一位为 0 就一定不存在；全部为 1 可能是其他元素共同造成，因此存在假阳性，但没有假阴性，前提是数据没有被错误删除或漏同步。
>
> 误判率由位数组大小、哈希数量和元素数共同决定。它适合挡住大部分不存在请求，误判后的请求仍需查询数据库确认。

## 473. Redis 消息 Pub/Sub 和 Stream 怎么选？

### 面试时可以这样答

> Pub/Sub 是实时广播，订阅者离线期间消息不会保留，也没有消费确认；Stream 保存消息 ID，支持消费者组、pending 列表和确认，更适合需要重放与消费进度的任务。
>
> Stream 仍需处理重复消费、积压修剪和失败认领。需要成熟路由、跨机房和大规模持久化时，专业消息队列通常更合适。

## 474. 缓存对象序列化要注意什么？

### 面试时可以这样答

> 要权衡体积、速度、可读性、类型安全和跨版本兼容。键名应含业务命名空间与必要版本，值结构新增字段尽量向后兼容，避免 Java 原生序列化带来的安全和耦合问题。
>
> 变更模型时要有双读、批量迁移或自然过期策略。压缩可省内存和网络，但增加 CPU，只有对象足够大且收益经测量才值得。

## 475. 如何设计可观测的缓存层？

### 面试时可以这样答

> 至少记录命中率、请求量、Redis 延迟与错误、回源量、重建耗时、连接池等待、淘汰和过期数量，并按缓存名称区分。只看整体命中率会掩盖某个热点接口持续穿透。
>
> 日志不能打印敏感值或每次命中，避免制造新瓶颈。告警应关联数据库负载，因为缓存故障的真实风险通常是回源把权威存储压垮。
