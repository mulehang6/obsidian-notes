# Kotlin 语言与工程实践（201-225）

## 201. Kotlin 的空安全解决了什么，没解决什么？

### 面试时可以这样答

> 类型系统区分 `String` 与 `String?`，对可空值必须安全调用、判空或显式断言，编译器因此能消除大量普通空指针错误。`?.` 传播 null，`?:` 提供回退，智能转换能在稳定判空后当作非空使用。
>
> 它不能保证绝不出现 NPE。`!!`、Java platform type、初始化阶段泄漏 `this`、反射和并发变化都可能破坏假设。项目与 Java 或 JDBC 交互时仍要在边界显式校验。

## 202. `?.`、`?:` 和 `!!` 应该怎么选？

### 面试时可以这样答

> `?.` 适合缺值就跳过后续动作，`?:` 适合提供默认值或立即 `return`、`throw`。`!!` 表示程序员承担非空证明，证明错了就在运行时崩溃。
>
> 业务入口应尽早把 nullable 转成明确结果，避免整条调用链都是 `?.`。`!!` 只适合已经由框架契约保证、且失败确实代表程序 bug 的窄位置，并写清理由。

## 203. 什么是 platform type？

### 面试时可以这样答

> Kotlin 调用没有空注解的 Java API 时，编译器无法确定返回值是否可空，会显示为 `T!`。它既能赋给非空类型，也能赋给可空类型，因此空安全责任回到开发者。
>
> JDBC 的 `getString`、旧 Java 库和反射代码常出现这种边界。我会先接成可空值并验证，而不是为了少写判空直接声明非空。

## 204. `val` 一定不可变吗？

### 面试时可以这样答

> `val` 只保证引用不能重新赋值，不保证引用对象的内部状态不可变。`val list = mutableListOf(...)` 仍能 add。真正不可变需要使用只读接口、不可变实现，并避免把内部可变对象暴露出去。
>
> Kotlin 的 `List` 接口是只读视图，也不保证底层不会被其他引用修改。跨线程共享时还要考虑实际实现和发布方式。

## 205. `data class` 自动生成哪些能力？

### 面试时可以这样答

> 编译器根据主构造函数中的属性生成 `equals`、`hashCode`、`toString`、`componentN` 和 `copy`。它适合值对象和不可变状态。类体内额外属性不参与这些生成逻辑，这是常见坑。
>
> `copy` 是浅拷贝。若属性里有 MutableList，新旧对象仍共享列表。用 data class 建模 UI 状态时，应优先放不可变集合或明确复制嵌套对象。

## 206. 为什么项目大量使用 sealed interface？

### 面试时可以这样答

> `AgentStreamEvent`、输入 part 和执行状态都是有限变体。sealed hierarchy 让编译器知道允许的子类型，`when` 可以做穷尽检查。新增事件时，遗漏处理分支会尽早暴露。
>
> interface 比 sealed class 更灵活，变体可以是 data class 或 data object，也不强迫共享构造状态。若子类型集合需要让第三方任意扩展，就不应 sealed。

## 207. `object` 与 `data object` 有什么区别？

### 面试时可以这样答

> 两者都是单例。`data object` 为单例提供稳定的 `toString`，并与 data class 变体在 sealed hierarchy 中保持一致的值语义表达，适合 `Started`、`Idle` 这类无负载状态。
>
> object 初始化是惰性的线程安全单例，但持有可变状态仍可能造成全局共享问题。无状态策略对象更适合使用 object。

## 208. Kotlin 的智能类型转换有什么限制？

### 面试时可以这样答

> 编译器只有确认值在判定后不会变化才 smart cast。本地 val 通常可以，可被覆盖的 open 属性、带自定义 getter 的属性和可能被并发修改的 var 往往不行。
>
> 遇到这种情况可以先复制到局部 val，再判型。不要用 `as` 强转绕过编译器，它只是把不确定性推到运行时。

## 209. `as` 与 `as?` 的区别是什么？

### 面试时可以这样答

> `as` 转换失败抛 `ClassCastException`，`as?` 失败返回 null。处理外部 JSON、多态插件结果时，`as?` 配合明确的错误分支更稳。内部不变量被破坏时，用强转让程序尽快失败也可能合理。
>
> 更好的设计通常是 sealed 类型和多态序列化，减少到处做运行时类型猜测。

## 210. 扩展函数真的修改了原类吗？

### 面试时可以这样答

> 没有。扩展函数在 JVM 上编译成静态函数，接收者作为参数，分派依据变量的静态类型。若成员函数与扩展同名同参数，成员优先。
>
> 它适合把格式转换和边界辅助放在相关类型旁边，但不能访问 private 成员。过多通用扩展会让调用来源难找，项目中应控制包和命名。

## 211. `inline` 函数有什么价值？

### 面试时可以这样答

> 编译器把函数体与 lambda 展开到调用处，可以减少高阶函数的对象分配和虚调用，并允许 lambda 非局部 return。`reified` 类型参数也只能用于 inline 函数，因为类型信息被带到调用点。
>
> 代价是字节码膨胀和调试栈变化。短小且频繁接收 lambda 的函数适合 inline，大函数不要为了“快”盲目展开。

## 212. `crossinline` 与 `noinline` 分别做什么？

### 面试时可以这样答

> inline lambda 默认允许从外层函数非局部 return。若 lambda 会被放进另一个对象或稍后调用，编译器无法支持这种跳转，需要 `crossinline` 禁止非局部 return。`noinline` 则让指定 lambda 不展开，可以保存到变量或传给非 inline API。
>
> 两者表达的是调用方式约束，不是性能标签。

## 213. `reified` 为什么能拿到泛型类型？

### 面试时可以这样答

> JVM 泛型通常擦除，普通函数里的 `T` 无法直接 `is T`。inline 函数在调用点展开，编译器知道实际类型，因此 reified T 可以用于类型检查、class 获取和序列化入口。
>
> 它不能用于普通成员虚调用，也不能恢复运行时嵌套泛型的全部信息。复杂类型仍应传 `KType`、serializer 或 TypeToken。

## 214. `lateinit` 与 `lazy` 有什么区别？

### 面试时可以这样答

> `lateinit var` 表示非空引用稍后由外部流程赋值，读取前未初始化会抛异常；它不支持 nullable 和基本类型。`by lazy` 是 val，第一次读取时执行初始化器并缓存结果，默认提供线程安全模式。
>
> 依赖注入和测试装配可用 lateinit，昂贵且按需创建的不可变对象适合 lazy。能在构造函数传入就不要延迟初始化。

## 215. 属性委托是怎么工作的？

### 面试时可以这样答

> `by` 把属性的 get 和 set 交给 delegate 的 `getValue`、`setValue`。标准库有 lazy、observable 和 map 委托，Compose 的 `var state by mutableStateOf` 也借助委托简化访问。
>
> 委托可以复用缓存、校验和状态通知，但副作用隐藏在普通属性语法后。耗时 I/O 或难以预料的行为不适合塞进 getter。

## 216. Kotlin 的 `==` 与 `===` 有什么区别？

### 面试时可以这样答

> `==` 会做空安全的结构相等判断，本质调用 equals；`===` 判断两个引用是否指向同一对象。值对象和 data class 通常用 `==`，缓存身份或单例判断才用 `===`。
>
> boxed 数字和字符串驻留让引用相等结果容易误导，业务逻辑不应依赖这些实现细节。自定义值对象还要让 equals 与 hashCode 保持一致，否则集合查找会出现难以解释的结果。

## 217. `when` 为什么适合状态处理？

### 面试时可以这样答

> `when` 可以按值、类型和条件分支，也能作为表达式返回结果。配合 sealed hierarchy 时，编译器检查是否覆盖所有变体，不需要 default 吞掉未来状态。
>
> 对公开可扩展枚举或外部输入仍要处理未知情况。持久化枚举值恢复时，项目会显式回退默认值，而不是把数据库字符串直接交给 `valueOf`。

## 218. Scope functions 应该怎么选？

### 面试时可以这样答

> `let` 用 `it` 并返回 lambda 结果，常用于 nullable 转换；`run` 用 `this` 并返回结果；`apply` 返回接收者，适合配置对象；`also` 返回接收者，适合附带日志；`with` 是非扩展的接收者代码块。
>
> 连续嵌套 scope function 会让 `this` 与 `it` 来源难辨。能用普通局部变量说清楚时，就不要为了 Kotlin 风格强行链式。

## 219. Kotlin 集合的 `List` 与 `MutableList` 有何边界？

### 面试时可以这样答

> `List` 只暴露读取 API，`MutableList` 允许修改。它是接口能力限制，不保证底层对象不可变。把 MutableList 以 List 返回后，持有原引用的一方仍能改变内容。
>
> 状态快照最好在构造时复制集合，避免调用方后续修改。并发环境则使用不可变数据或同步机制。

## 220. `Sequence` 一定比集合链更快吗？

### 面试时可以这样答

> Sequence 延迟逐元素执行，长链、需要 early termination 或大数据集时能减少中间集合。小集合和简单操作中，迭代器与 lambda 开销可能反而更高。
>
> Sequence 只能消费时才执行，若操作依赖已关闭的文件流会出错。选择前看数据量、链长度和生命周期，性能结论要用基准验证。

## 221. Kotlin 异常为什么都是 unchecked？

### 面试时可以这样答

> Kotlin 不要求在签名中声明 checked exception，调用方可以选择处理或传播。这样 API 更简洁，但也失去 Java 编译器强制处理提示。
>
> 对可预期业务失败，使用 sealed result 或明确返回类型通常比抛异常更清楚；I/O 和真正异常仍用 exception。协程代码要特别保留 CancellationException。

## 222. `runCatching` 有什么陷阱？

### 面试时可以这样答

> `runCatching` 捕获 Throwable 并包装 Result，写边界适配很方便。但在协程中若直接 `getOrElse`，可能把 CancellationException 当普通失败吞掉，破坏取消传播。
>
> 另一个问题是连续链式处理容易丢失错误上下文。需要取消语义或精确分类时，显式 try catch 更安全。

## 223. 接口默认实现与抽象类怎么选？

### 面试时可以这样答

> 接口适合能力契约和多实现，可以有无状态默认方法；抽象类适合共享受保护状态、构造约束和模板流程，但只能单继承。项目的 `AgentHookDispatcher` 用接口，因为实现只需要统一 dispatch 和生命周期方法。
>
> 不要把大量可变字段塞进抽象基类换复用，组合通常更容易测试。

## 224. Kotlin Multiplatform 的 `commonMain` 能写什么？

### 面试时可以这样答

> commonMain 只能依赖所有目标都可用的 Kotlin 和多平台库，适合请求模型、状态、权限规则等平台无关契约。JDBC、JCEF、Windows 进程属于 JVM 或桌面实现，应放 jvmMain 或 desktopApp。
>
> 如果公共代码需要平台能力，可用 expect/actual 或接口注入。不能在 commonMain 偷用 java.io，再声称项目具备真正多平台实现。

## 225. 你如何让 Kotlin 代码保持可测试？

### 面试时可以这样答

> 把网络、时钟、进程和文件系统放在窄接口后，通过构造函数注入。纯转换写成无副作用函数，状态用 sealed 类型表达。项目的 Hook command executor、HTTP recording client 和 process starter 都能替换，因此失败路径不需要真实外部服务。
>
> 测试性不是给每个类都造接口，而是隔离非确定性边界。只有一个实现且纯计算的类不必机械抽象。
