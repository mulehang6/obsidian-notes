# Java 并发与线程池（376-400）

## 376. 进程、线程和协程有什么区别？

### 面试时可以这样答

> 进程是资源隔离和分配的基本单位，拥有独立地址空间；线程是进程内的执行单元，共享堆和文件等资源，但各自有栈和程序计数器。协程是用户态调度的轻量任务，挂起通常不阻塞承载线程，切换成本也更低。
>
> 三者不是简单的替代关系。Java 平台线程适合一般并发，虚拟线程适合大量阻塞式 I/O，Kotlin 协程还提供结构化并发和挂起函数；CPU 密集任务的上限最终仍受核心数约束。

## 377. Java 线程有哪些状态？

### 面试时可以这样答

> `NEW` 是尚未启动，`RUNNABLE` 同时包含正在运行和等待操作系统调度，`BLOCKED` 是等待进入 `synchronized`，`WAITING` 与 `TIMED_WAITING` 是无期限或有期限等待，`TERMINATED` 是执行结束。
>
> 排障时尤其要区分 `BLOCKED` 和等待 I/O。线程 dump 中大量 BLOCKED 往往指向锁竞争；大量 WAITING 可能只是线程池工作线程正常空闲，必须结合栈顶方法判断。

## 378. 为什么调用 start 而不是直接调用 run？

### 面试时可以这样答

> `start()` 请求 JVM 创建并调度新线程，新线程随后执行 `run()`；直接调用 `run()` 只是当前线程的一次普通方法调用，不产生并发。一个 Thread 实例也只能成功启动一次，重复 `start()` 会抛异常。
>
> 验证时可打印线程名或看调试器调用栈。业务代码更推荐把任务提交给线程池，而不是频繁手工创建 Thread，这样生命周期、并发度和异常处理更可控。

## 379. Java 的中断机制是什么？

### 面试时可以这样答

> 中断是协作式取消，不是强行杀死线程。`interrupt()` 设置中断标记；sleep、wait、join 等阻塞方法会以 `InterruptedException` 响应，并清除标记；计算循环要主动检查 `isInterrupted()`。
>
> 捕获中断异常后不能无声吞掉。若当前层不能完成取消，应清理资源后退出，或调用 `Thread.currentThread().interrupt()` 恢复标记再向上返回，否则线程池关闭和请求取消都会失效。

## 380. synchronized 保证了什么？

### 面试时可以这样答

> `synchronized` 同时提供互斥和可见性：同一监视器一次只允许一个线程持有，解锁前的写入对随后获得该锁的线程可见。实例方法锁当前对象，静态方法锁 Class 对象，代码块锁显式给出的对象。
>
> 正确性的前提是所有相关访问遵守同一把锁。若写入加锁而读取绕开锁，或错误地锁了不同实例，就不能形成完整的 happens-before 关系。

## 381. synchronized 为什么是可重入的？

### 面试时可以这样答

> 同一线程已经持有某对象监视器时，可以再次进入由该监视器保护的方法或代码块，JVM 维护进入次数，退出相同次数后才真正释放。否则同步方法调用同对象的另一个同步方法就会把自己锁死。
>
> 可重入解决的是同线程嵌套调用，不代表锁可以跨线程转移，也不消除多个锁之间的死锁风险。设计时仍应减少持锁范围并保持固定加锁顺序。

## 382. volatile 能解决什么问题？

### 面试时可以这样答

> volatile 保证单次读写的可见性，并限制特定指令重排序；对该变量的写 happens-before 后续读。它适合状态标记、配置快照引用和单写多读场景。
>
> 它不把复合操作变成原子操作，`count++` 仍包含读、计算、写三步。计数竞争应使用原子类、锁或聚合方案，多个字段要维持联合不变量时通常也需要锁或不可变快照。

## 383. 什么是 happens-before？

### 面试时可以这样答

> happens-before 是 Java 内存模型规定的可见性与顺序关系，不等同于墙上时钟的先后。典型规则包括程序次序、监视器解锁先于后续加锁、volatile 写先于后续读、线程 start 前的操作对子线程可见、线程结束先于 join 返回。
>
> 判断并发代码时，我会问“两个访问之间由哪条规则建立关系”。如果答不出来，即使测试偶尔正确，也可能依赖缓存一致性的偶然表现，不能认为线程安全。

## 384. CAS 的原理和局限是什么？

### 面试时可以这样答

> CAS 比较内存中的当前值与期望值，相等才原子地写入新值，失败方通常重试。它让原子类在低竞争下避免阻塞和线程切换，但“无锁”不等于没有同步成本，仍会涉及内存屏障和缓存行竞争。
>
> 高竞争时自旋会浪费 CPU；CAS 只比较一个值时难以维护跨变量不变量，还存在 ABA 问题。应按竞争程度选择原子类、分段累加或锁，而不是把 CAS 当作普遍更快。

## 385. 什么是 ABA 问题？如何处理？

### 面试时可以这样答

> 线程读到 A 后暂停，另一个线程把值改成 B 又改回 A，普通 CAS 只看当前值，会误以为期间没有变化。对链表节点复用、状态机版本推进等场景，这可能破坏业务语义。
>
> 处理方式是把版本号或时间戳与值一起比较，例如 `AtomicStampedReference`；也可以避免节点复用，或改用锁。是否需要处理取决于中间变化是否影响正确性，不能看到 CAS 就机械套版本号。

## 386. AtomicLong 与 LongAdder 怎么选？

### 面试时可以这样答

> `AtomicLong` 在一个值上 CAS，读取是精确快照，适合序列号和需要线性化语义的状态。`LongAdder` 在竞争时把更新分散到多个槽，读取时求和，吞吐更高，但 `sum()` 与并发更新并非一个严格原子快照。
>
> 因此监控计数、QPS 累加可用 LongAdder；余额、库存或必须基于当前精确值做判断的逻辑不能因为吞吐高就改用它。

## 387. AQS 解决了什么问题？

### 面试时可以这样答

> AQS 用一个同步状态、原子更新和 FIFO 风格等待队列抽象了锁与同步器的共同骨架。子类定义独占或共享模式下如何获取、释放状态，框架负责竞争失败后的排队、阻塞和唤醒。
>
> ReentrantLock、Semaphore、CountDownLatch 等都建立在这个思路上。理解重点不是背队列节点字段，而是状态语义由实现者定义，排队策略也不自动等于严格公平。

## 388. ReentrantLock 和 synchronized 怎么选？

### 面试时可以这样答

> 两者都提供可重入互斥和内存可见性。`synchronized` 语法简单且异常退出会自动释放；ReentrantLock 支持可中断获取、超时尝试、公平策略和多个 Condition，但必须在 finally 中解锁。
>
> 默认优先选结构简单的 synchronized；确实需要 `tryLock`、中断等待或多条件队列时再用 ReentrantLock。性能不能凭旧版本经验下结论，应以当前 JDK 和负载基准为准。

## 389. Condition 比 Object.wait/notify 强在哪里？

### 面试时可以这样答

> 一个 Lock 可以创建多个 Condition，把“队列非空”“队列未满”等不同等待原因分开；Object 监视器只有一组等待集合。`await` 会原子释放锁并等待，返回前重新竞争锁，`signal` 只是把等待者转为可竞争状态。
>
> 等待必须放在 while 循环里重新检查条件，因为可能发生虚假唤醒，或条件在抢到锁前又被其他线程改变。调用 await、signal 时也必须持有关联的锁。

## 390. CountDownLatch、CyclicBarrier、Semaphore 有什么区别？

### 面试时可以这样答

> CountDownLatch 是一次性倒计时，一个或多个线程等若干任务完成；CyclicBarrier 让固定数量线程在阶段边界互相等待，并可重复使用；Semaphore 用许可证限制同时进入资源的并发数。
>
> 我会按业务语义选：启动依赖或批次汇合用 latch，分阶段并行计算用 barrier，数据库连接或外部接口并发保护用 semaphore。它们不替代业务超时、取消和失败传播。

## 391. 为什么要使用线程池？

### 面试时可以这样答

> 线程池复用线程，降低创建销毁成本，并用最大线程数、队列和拒绝策略把并发变成可控资源。它还集中承载命名、监控、异常处理和优雅停机，避免每个请求随意创建线程。
>
> 线程池不是性能魔法。边界队列如果过大只是把过载变成高延迟和内存压力；必须连同任务耗时、到达速率、下游容量和降级策略一起设计。

## 392. ThreadPoolExecutor 七个核心参数是什么？

### 面试时可以这样答

> 参数是核心线程数、最大线程数、非核心线程空闲时间、时间单位、工作队列、线程工厂和拒绝处理器。线程工厂应设置可识别名称和未捕获异常处理，方便监控与 dump 定位。
>
> 参数彼此联动，尤其是队列类型会改变最大线程数是否有机会生效。直接使用无界 LinkedBlockingQueue 时，队列通常不会满到扩容到 maximumPoolSize。

## 393. 线程池接收任务后的执行流程是什么？

### 面试时可以这样答

> 工作线程少于 corePoolSize 时先创建核心线程；否则尝试入队；队列满且线程数未到 maximumPoolSize 时再创建线程；两者都无法接收才执行拒绝策略。期间还会处理线程池状态变化，必要时回滚刚入队的任务。
>
> 这解释了为什么不能孤立调最大线程数。无界队列下它几乎不起作用；SynchronousQueue 不存任务，会更积极创建线程，也更需要严格上限。

## 394. CPU 密集和 I/O 密集任务如何估算线程数？

### 面试时可以这样答

> CPU 密集任务通常从核心数或核心数加一附近起步，避免过多上下文切换；I/O 密集任务可按 `核心数 × (1 + 等待时间/计算时间)` 粗估，再用压测修正。
>
> 公式只是起点。还要受数据库连接池、远端限流、内存和延迟目标约束，并分别观察活跃线程、队列长度、拒绝数、任务等待时间与执行时间。

## 395. 线程池工作队列如何选择？

### 面试时可以这样答

> ArrayBlockingQueue 有界且内存更可控；LinkedBlockingQueue 可设容量，但默认近似无界要谨慎；SynchronousQueue 直接移交，不存任务；PriorityBlockingQueue 可排序但通常无界，还可能让低优先级任务饥饿。
>
> 在线请求通常优先有界队列，使过载尽早暴露。容量应结合允许的排队时间和吞吐估算，并在满载时有明确拒绝或降级行为。

## 396. 四种内置拒绝策略有什么差异？

### 面试时可以这样答

> AbortPolicy 抛 `RejectedExecutionException`；CallerRunsPolicy 让提交线程执行，形成一定反压；DiscardPolicy 静默丢弃；DiscardOldestPolicy 丢队头再重试。后两种若无监控很容易造成数据无声丢失。
>
> 我通常自定义拒绝策略记录任务类型、池状态和指标，再根据业务决定快速失败、降级或持久化补偿。CallerRuns 也要小心，它可能占住 Web 线程并把延迟扩散给上游。

## 397. execute 和 submit 有什么区别？

### 面试时可以这样答

> `execute` 接受 Runnable、没有返回值，未捕获异常通常交给线程的异常处理机制；`submit` 返回 Future，可承载返回值或异常，但任务异常被封装到 Future，调用 `get()` 才会重新抛出。
>
> 如果提交后从不观察 Future，失败可能被悄悄遗漏。工程上应明确谁消费结果，或在任务边界统一记录异常，而不是把 submit 当成更安全的 execute。

## 398. Future 和 CompletableFuture 的差别是什么？

### 面试时可以这样答

> Future 主要提供等待、取消和取结果，组合多个异步步骤比较笨重。CompletableFuture 可用 `thenApply`、`thenCompose`、`allOf` 等建立非阻塞式组合，并用 `exceptionally`、`handle` 处理失败。
>
> 要明确同步与 Async 后缀的执行线程，并为 Async 方法传入受控线程池，避免把阻塞 I/O 堆到公共 ForkJoinPool。取消 CompletableFuture 也不保证底层外部操作一定停止。

## 399. 死锁产生的条件和预防方法是什么？

### 面试时可以这样答

> 经典条件是互斥、占有且等待、不可剥夺、循环等待。工程上最有效的是破坏循环等待：统一锁顺序；也可缩小持锁范围、避免锁内调用外部服务、使用超时 `tryLock` 并在失败后释放已有资源。
>
> 线上定位用线程 dump 查 `Found one Java-level deadlock` 或相互等待的锁对象，再映射到业务调用链。不能只重启，必须修正锁顺序或资源持有设计。

## 400. 如何系统排查一个并发问题？

### 面试时可以这样答

> 先把现象归类为正确性、活性或性能问题，再收集线程 dump、JFR、线程池指标和请求链路。正确性问题寻找共享可变状态和缺失的 happens-before；活性问题看死锁、饥饿和无限等待；性能问题看锁竞争、队列与上下文切换。
>
> 复现时固定输入、提高竞争窗口并重复运行，用最小案例验证假设。修复后除了功能测试，还要加入并发测试、超时和可观测指标，证明问题不是被时序变化暂时掩盖。
