# JVM、内存、类加载与 GC（351-375）

## 351. JVM 运行时内存怎么划分？

### 面试时可以这样答

> 线程共享区域主要有堆和方法区实现的元空间；线程私有区域有虚拟机栈、程序计数器和本地方法栈。对象通常在堆，栈帧保存局部变量、操作数栈和返回信息，类元数据在元空间。
>
> 这是逻辑划分，不代表对象绝不会被优化到栈上。JIT 可通过逃逸分析做标量替换，排障仍应以实际监控和 dump 为准。

## 352. 栈溢出与堆溢出有什么区别？

### 面试时可以这样答

> 深递归或单线程栈帧过大可能触发 StackOverflowError；大量存活对象超过堆上限会触发 Java heap space OOM。线程过多还可能因无法创建 native thread 失败，它不等于堆满。
>
> 排查栈溢出看递归调用链和 `-Xss`，排查堆溢出看 GC 日志、heap dump 和对象引用链，不能统一靠加内存。

## 353. 对象一定分配在堆上吗？

### 面试时可以这样答

> Java 语义上对象由堆和 GC 管理，但 JIT 若证明对象不逃逸，可以消除分配或把字段拆成标量放在寄存器和栈帧中。TLAB 也让多数小对象先在当前线程的堆内区域快速分配。
>
> 面试回答应区分语言语义和虚拟机优化，不要绝对地说所有 new 都产生可见堆对象。是否发生标量替换要看实际编译层级和逃逸结果，不能从源码形态直接断言。

## 354. 什么是逃逸分析？

### 面试时可以这样答

> JIT 分析对象是否逃出方法或线程。未逃逸对象可能被标量替换、消除锁或消除实际分配。它依赖热点编译和具体代码，不能作为业务正确性前提。
>
> 性能优化前先用 JFR 或基准定位分配热点，不要为了让对象“不逃逸”把代码写得难读。逃逸分析是 JVM 的优化机会，不是 Java 规范对某次运行的行为承诺。

## 355. 对象头里有什么？

### 面试时可以这样答

> HotSpot 对象头通常包含 Mark Word 和类型指针，数组还包含长度。Mark Word 在不同状态下承载 hash、GC 年龄和锁相关信息。具体位布局受 JVM、压缩指针和版本影响。
>
> 面试重点是理解同步和 GC 需要对象元数据，不必把某个 JDK 的每一位当永久标准。

## 356. 如何判断对象可回收？

### 面试时可以这样答

> 主流 JVM 使用可达性分析，从 GC Roots 出发遍历引用图，不可达对象才有资格回收。Roots 包括线程栈引用、静态字段、JNI 引用和 JVM 内部对象等。
>
> 引用计数无法单独处理循环引用，因此不是 HotSpot 判断存活的主要方法。对象不可达后也不保证立刻回收，真正回收时机仍由收集器和内存压力决定。

## 357. 强、软、弱、虚引用有什么区别？

### 面试时可以这样答

> 强引用存在时对象通常不会回收；软引用在内存压力下可回收，曾用于缓存但行为难预测；弱引用下一次 GC 即可能清理，适合不影响生命周期的关联；虚引用必须配合 ReferenceQueue，用于回收后通知和堆外资源管理。
>
> 缓存更适合显式容量和过期策略，不应把 SoftReference 当可靠缓存系统。

## 358. 什么是 Stop-The-World？

### 面试时可以这样答

> JVM 在某些 GC 阶段暂停应用线程，以获得一致的对象图或完成移动。并发收集器也不是全程无停顿，初始标记、重新标记或重定位仍可能 STW。
>
> 优化目标是让停顿满足业务 SLO，而不是追求绝对零停顿。需要同时看频率、最长停顿和吞吐损失，并把 GC 时间与同一时刻的接口尾延迟关联起来。

## 359. Minor GC、Major GC、Full GC 怎么区分？

### 面试时可以这样答

> Minor 或 Young GC 主要回收年轻代；Major 常指老年代回收，但不同收集器日志术语不完全一致；Full GC 通常处理整个堆并可能连带元空间，停顿更重。
>
> 排障不要只看名词，要看当前收集器的 GC cause、阶段、回收前后容量和停顿时间。不同日志工具对 Major 的命名可能不同，生产判断应以实际事件含义为准。

## 360. 为什么要分代收集？

### 面试时可以这样答

> 大多数对象朝生夕死，少量长期存活。年轻代用复制方式快速回收大量死亡对象，存活多轮后晋升老年代，减少每次扫描全部堆的成本。
>
> 大对象、晋升担保和存活率异常会破坏这一假设。日志中年轻代回收后存活过多，可能说明缓存或批处理对象生命周期偏长，需要结合对象年龄分布而不是盲目扩大年轻代。

## 361. G1 的基本思路是什么？

### 面试时可以这样答

> G1 把堆划成许多 Region，跟踪各区回收收益，在目标停顿时间内优先回收垃圾多的 Region。它按逻辑保留年轻代和老年代，并支持并发标记与混合回收。
>
> `MaxGCPauseMillis` 是目标，不是保证。堆过小、分配过快、大对象多或引用处理重仍会超时。

## 362. ZGC 与 G1 的取舍是什么？

### 面试时可以这样答

> ZGC 把更多标记和重定位工作并发化，面向低停顿和大堆，代价是额外 CPU、内存和对版本环境的要求。G1 更成熟通用，吞吐与停顿平衡容易接受。
>
> 选择应基于 JDK 版本、堆大小、延迟 SLO 和压测，不是看到“低延迟”就直接换收集器。迁移时还要比较同吞吐下的 CPU 余量、内存占用和最坏停顿。

## 363. 哪些对象容易进入老年代？

### 面试时可以这样答

> 在年轻代 GC 中多次存活、动态年龄判断达到条件，或分配担保与大对象策略触发时会进入老年代。具体阈值和路径依收集器而异。
>
> 大量对象过早晋升会增加老年代压力。应检查对象生命周期和 Survivor 空间，而不是只调晋升阈值。若根因是无界缓存或队列，调 GC 参数只能延后问题。

## 364. 内存泄漏在有 GC 的 Java 中怎么发生？

### 面试时可以这样答

> 对象已经不再有业务用途，却仍能从 GC Root 到达，例如静态 Map 无界增长、ThreadLocal 未 remove、监听器未注销、缓存无淘汰和类加载器被引用。GC 只能回收不可达对象，不知道业务上是否无用。
>
> 排查用 heap dump 的 dominator tree 和到 GC Root 路径，结合时间观察谁持续持有对象。

## 365. ThreadLocal 为什么可能泄漏？

### 面试时可以这样答

> ThreadLocalMap 的 key 是弱引用，key 回收后 value 仍被线程强引用，直到 Map 清理或线程结束。线程池线程长期存活，value 可能长期残留并污染下一请求。
>
> 使用后在 finally 调用 remove。MDC、租户和用户上下文尤其要清理。

## 366. 如何排查 OOM？

### 面试时可以这样答

> 先确认 OOM 类型和时间点，收集 GC 日志、进程内存、线程数和自动 heap dump。堆 OOM 用 MAT 看最大支配对象和引用链；native thread 看线程 dump；Metaspace 看类加载器和动态类数量；Direct buffer 看堆外指标。
>
> 先保留现场再重启。直接加 `-Xmx` 可能只是延后泄漏。

## 367. 类加载经历哪些阶段？

### 面试时可以这样答

> 通常概括为加载、链接和初始化。链接包含验证、准备和解析。加载取得字节并创建 Class，准备为静态字段分配默认值，初始化执行静态赋值和 `<clinit>`。
>
> 解析有时可延迟。面试回答要区分“类被加载”和“类初始化已执行”。只有首次主动使用等触发条件出现时才初始化，读取编译期常量未必触发。

## 368. 什么是双亲委派？

### 面试时可以这样答

> 类加载器收到请求先委托父加载器，父无法完成时自己尝试。这样核心 Java 类优先由平台加载器提供，避免应用伪造 `java.lang.String`，也减少重复类定义。
>
> SPI、插件和容器会有意改变委派方式，以便父层接口加载子层实现。打破委派要有清晰隔离规则。

## 369. 为什么相同类名仍可能不是同一个类型？

### 面试时可以这样答

> JVM 中类型身份由类全限定名和定义它的 ClassLoader 共同决定。两个插件加载器各自加载同名类，实例不能互相强转。
>
> 插件系统应让公共接口由共同父加载器加载，实现类由子加载器加载，跨边界只传公共类型或序列化数据。卸载插件还要清理线程和静态引用，否则类加载器无法回收。

## 370. 类初始化在什么情况下触发？

### 面试时可以这样答

> new 对象、访问非编译期常量的静态字段、调用静态方法、反射主动使用、初始化子类前初始化父类，以及启动主类都会触发。引用编译期常量可能被内联，不触发声明类初始化。
>
> 仅创建数组类型或通过子类访问父类静态字段也有不同规则，面试可用例子解释而不是死背列表。

## 371. JIT 编译做什么？

### 面试时可以这样答

> JVM 先解释或以较低优化执行，收集热点信息后把常用方法编译成本地代码，并做内联、逃逸分析、去虚拟化等优化。假设失效时可能反优化回到较低层级。
>
> 因此微基准需要预热，不能用一次 `System.currentTimeMillis` 比较两段 Java 代码。

## 372. 什么是 safepoint？

### 面试时可以这样答

> JVM 在特定安全位置掌握线程栈和对象引用状态，可执行 GC、反优化或某些诊断操作。请求 safepoint 后，各线程运行到可停位置再暂停。
>
> 总停顿不仅是 GC 工作时间，还可能包含等待线程到达 safepoint。现代 JVM 已减少长时间不可达安全点问题，但诊断要看日志。

## 373. volatile 能保证对象发布安全吗？

### 面试时可以这样答

> 把构造完成的对象引用写入 volatile，读线程随后读取该引用，写前操作 happens-before 读后操作，可以看到构造状态。前提是构造期间没有让 this 提前逃逸，后续可变字段仍需同步。
>
> final 字段还有初始化安全保证，但同样不能在构造完成前泄漏对象。

## 374. Java 序列化为什么常被谨慎使用？

### 面试时可以这样答

> 原生 Serializable 把类结构与字节格式强绑定，版本演进脆弱，反序列化历史上也有 gadget 安全风险。跨服务更适合显式 JSON、Protobuf 等协议和白名单类型。
>
> 若必须读取旧序列化数据，应限制输入来源、配置过滤器，并定义 serialVersionUID。不要反序列化不可信字节。

## 375. JVM 性能问题如何形成证据链？

### 面试时可以这样答

> 先用业务指标确认是吞吐、延迟还是错误，再看 CPU、堆、GC、线程和 I/O。CPU 高抓 JFR 或火焰图，停顿看 GC 日志，卡死看线程 dump，内存增长看多时点 heap dump。
>
> 一次快照只能说明当时状态。优化后用相同负载复测 P95、资源和正确性，不能以“代码看起来更快”结案。
