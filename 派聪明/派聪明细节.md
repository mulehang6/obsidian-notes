# 1. Apache Tika如何解析各种格式的文档？

^272a66

文档解析的核心入口是`ParseService.parseAndSave`。整体思路上是先把上次文件包装成`BufferedInputStream`，先做一次内存检查，避免大文件直接把JVM顶满。然后判断是不是pdf，如果是pdf，则交给单独的pdf解析器([[派聪明细节#1. 为什么pdf要单独解析]])，如果不是，则交给Tika的`AutoDetectParser`。
`AutoDetectParser`的作用是自动识别文件类型，他会根据文件头等信息自动选择合适的解析器去处理不同类型的文档。解析出来之后，通过SAX事件流不断回调`characters()`，项目里定义了一个`StreamingContentHandler`去接收这段文本流。

## 1-1. 为什么pdf要单独解析

pdf容易出现页眉页脚、分页噪声、页码错乱这类问题，单独处理可以保留页码信息，也方便后续引用定位和单页预览
# 2. `PareService`如何把文档切成小段？这一块具体怎么做的？

^abaae0

这是一个两层切分策略。

第一层叫父块切分，Tika在流式解析时会不断把文本回调到`StreamingContent.characters()`中，项目先把文本累计到一个大缓冲区，达到`parentChunkSize`以后再触发一次处理，这个父块默认比较大，主要目的是流式消费和防止OOM。

第二层叫语义子块切分。父块拿到后，会调用`spiltTextIntoChunksWithSemantics`做真正的切片。他的策略是先按段切分；如果某个段落太长。就继续按句子切，正则同时兼容中英文句号、问好和分号；如果单独还是太长，就用HanLP做中文分词，按词粒度切；如果HanLP出问题，还会降级成字符切

# 3. `ChatHandler`具体如何协调对话过程

^2baaff

前端先通过`WebSocker`建立连接，`ChatWebSocketHanlder`会先校验JWT，拿到用户身份后把消息传给`ChatHandler`里的`processMessage`。

进入`ChatHandler`之后第一步先做聊天限流

第二步从Redis里获取或创建`conversationId`，这个ID会和用户ID绑定七天

第三步读取历史对话

第四步调用`HybridSearchService.searchWithPermission`做带权限的混合检索，这里既有向量召回，也有关键词匹配和BM25重排，同时会把用户自己的文档、公开文档、组织内文档做权限过滤

第五步把检索结果组装成上下文，格式是`[1] (文件名 | 页码) 摘要内容`，同时保存引用编号到原文chunk的映射

第六步把用户问题、历史记录、检索上下文一起交给`LlmProviderRouter`，由他选择模型并按openai兼容的格式走流式接口

第七步模型每输出一个token，`ChatHandler`就一边累计到内存里的`responseBuilder`，一边通过WebSocket实时推送给前端

第八部后台有一个完成监控线程，如果发现一轮响应时间不再增加，就认为生成结束，发送`completion`通知，并把本轮`user/assistant`消息连同映射一起写回Redis，只保留最近20条历史记录。
