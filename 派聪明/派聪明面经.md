## 1. 请描述RAG系统架构，包括主要组件和数据流向

整个系统架构主要围绕“文件上传 - 文件存储 - 向量生成”来设计。

当用户上传文件时，首先通过`Upload`接口来先处理上传文件，然后把文件处理任务放到kafka消息队列来异步处理，避免大文件上传时中途失败或者等待时间较长造成不好的用户体验

然后就是文档解析，`FileProcessingConsumer`作为kafka消费者会异步处理这些消息。==我们用的是`apache tika`来解析各种格式的文档 [[派聪明细节#^272a66]]==，如pdf，word等，==然后通过`ParseService`把文档切成小段[[派聪明细节#^abaae0]]==，这样做的好处是既保持了语义的完整性，又能够控制向量化的粒度。

向量化这块是RAG的核心，`VectorizationService`会调用智谱的Embedding 3 模型将文本向量化，我们将这些向量存储在es中，主要是因为es在向量检索方面的性能比较好，而且支持混合检索。

说到检索，这是模型能否正确回答问题的关键。我们实现了混合检索策略，既有基于向量相似度的语义检索，也有传统的关键词检索，这样在不同的场景下都有不错的召回效果。而且我们也在检索时加入了权限控制，确保用户只能检索到自己有权访问的文件。

生成答案部分，使用的是DeepSeek的API，并且支持流式响应，跟主流的AI 应用保持一致。

整个对话过程是==通过`ChatHandler`来协调的 [[派聪明细节#^2baaff]]==，他会先调用检索服务找到相关文档，然后把这些文档作为上下文传给LLM，最后把生成的回答通过WebSocket实时推送给用户。我们还在Redis中维护了对话历史，这样AI能够理解上下文，并进行多轮对话

权限控制方面，我们实现了基于组织标签的多租户架构。通过`OrgTagAuthorizationFilter`确保用户只能访问自己组织内的文档，实现数据的安全隔离。

## 2. ## 在设计RAG系统时，如何选择合适的向量数据库？## Elasticsearch、Pinecone等有什么区别？

第一个原因就是我们对ES比较熟悉，第二个是因为ES的混合检索能力比较强，即支持传统的全文检索，也支持向量检索，这对RAG来说是很大的优势。

但实话实话，在纯向量检索上，ES不如专门的向量数据库。如果系统主要是向量相似度搜索，专门的向量数据库会更合适，比如Pinecone，他就是专门为向量检索设计的云服务，性能也确实不错，而且使用起来很简单，基本上开箱即用。但是有个问题就是成本

就个人来说，先用ES这样的通用方案快速验证业务价值，等业务稳定以后再根据性能瓶颈考虑是否应该迁移到专门的向量数据库，这样既能快速上线，又能控制技术风险。毕竟RAG的核心价值还是业务逻辑和数据质量上，选择合适的就行。

## 3. RAG中的混合检索是什么？如何实现？

混合检索简单来说就是把不同的检索方法结合起来，取长补短，提高检索的召回率和准确性

这个项目采取的是语义检索和关键词检索。语义检索就是基于向量相似度的，它能够理解查询的语句含义，即使用词不同也能查到结果。关键词检索就是传统的全文检索，更适合查找人名、地面等专有名词

实现如下：

首先对用户查询同时执行向量检索和语义检索，然后把两个结果集合并。这里有个关键问题就是如何合并及排序。我们这里采用的是加权融合的方式，给语义检索和关键词检索分别设置权重，然后计算综合得分

第一阶段：KNN向量召回
```java
// KNN 向量召回阶段 
s.knn(kn -> 
	kn.field("vector")
	.queryVector(queryVector) // 查询向量
	.k(recallK) // 召回数量（topK * 30）
	.numCandidates(recallK) // 候选数量
	);
```

第二阶段：关键词过滤
```java
// 必须命中关键词 + 权限过滤 
s.query(q -> q.bool(b -> b
	.must(mst -> ｍｓｔ．ｍａｔｃｈ(m -> ｍ．ｆｉｅｌｄ("textContent").query(query))) // 关键词匹配 
	.filter(f -> f.bool(bf -> bf
	.should(s1 -> s1.term(t -> t.field("userId").value(userDbId))) // 用户权限
	.should(s2 -> s2.term(t -> t.field("public").value(true))) // 公开文档
	.should(s3 -> /* 组织权限 */) // 组织权限 
	)) 
));
```

第三阶段：BM25重排序
```java
// BM25 rescore 重排序 
s.rescore(r -> r 
	.windowSize(recallK) 
	.query(rq -> rq .queryWeight(0.2d) // KNN分数权重20% 
	.rescoreQueryWeight(1.0d) // BM25分数权重100% 
	.query(rqq -> rqq.match(m -> m 
		.field("textContent") 
		.query(query) 
		.operator(Ｏｐｅｒａｔｏｒ．Ａｎｄ) // 严格关键词匹配 
		)) 
	) 
);
```

具体算法是这样的：假设一个文档在语义检索中的得分是0.8，在关键词检索中的得分是0.3，可以设置这两种检索对应的权重然后计算最终得分，这个权重当然需要根据实际情况来调整

在此基础上，我们还加入了权限过滤的逻辑。用户只能检索到自己有权限访问的文档，这个过滤是在检索结果合并之后进行的

## 1. 五分钟，介绍RAG项目整体流程，说出1-2个难点
- 整体流程：用户上传文档后，系统会将文档进行分片处理，分为多个chunk，每个chunk生成对应的向量，并将向量和文本同时存入es。
  
  用户提问时，系统会对问题进行向量化，在es中执行混合检索(向量检索和BM25关键词检索)，把召回的相关chunk拼接进LLM的prompt，最后通过WebSocket实时推送给前端

- 难点1：chunk的大小设计，如果太小，那么信息就太稀疏，没有什么用处；如果太大，那么一是有可能会超出嵌入模型的上下文(以智谱的Embedding 3模型为例，上下文只有8K)，二是会稀释语义
- 难点2：对话上下文管理。多轮对话需要把历史记录也带进prompt中，但模型的上下文都是有限的，如何在保留足够上下文的前提下控制token数，是RAG项目里很实际的工程问题

  然后是语义切分，首先按段落切分，如果段落过长就按句子切分，句子过长就按词切分，再过长就按字符切分

- 难点2：主要分4个点
  - 1. 历史记录会存进Redis，但实际使用的只有最近的20条
  - 2. 对于文档检索返回的结果，只取最相关的前5条，并且每条限制在300个字符以内
  - 3. 使用`max_token`限制模式的最大输出token
  - 4. 项目中有个`UsageQuotaService`用于预估每次回答的token消耗，可以在一定程度上帮助设计token管理

## 2. 除了分片上传，有做断点续传吗？

有的。

前面已经说到一个文档会被分为多个chunk，每个chunk都会用Redis的Bitmap存储上传的状态，成功设置成1，否则为0，并且只有所有chunk上传完成时才会在服务端完成拼接(由MinIO完成)，如果中途有上传失败，那么前端在上传时会先查一下Bitmap，只上传失败的部分

### 2-1. 为什么这么设计？

如果每次失败都要完整的走一遍上传流程，很浪费时间，一来用户体验不好，而来也会浪费服务器资源。断点续传加上Bitmap记录进度，成本低，实现简单，效果也不错

## 3. 既然用了Bitmap存储分片索引，Redis底层怎么实现的？还有哪些使用场景？

- 底层本质上是对String的封装。String在Redis中是以字节数组的方式存放的，Bitmap操作(SETBIT、GETBIT、BITCOUNT)本质上都是对字节数组进行位运算。每个字节有8位，一个512M的String可以存储2^32个位，空间效率极高
- 签到。userId作为offset，每天一个key，签到就SETBIT，统计每月签到就用BITCOUNT。
- 活跃用户统计。每天记录哪些用户活跃，多天取交集(BITOP AND)就知道连续活跃用户。
- 布隆过滤器。虽然Redis4.0之后有原生的Bloom Filter，但是Bitmap自己实现也是常见方案。

## 4. 混合检索用了嵌入模型+IK分词器，为什么这样设计？

因为向量检索的优势在于语义匹配，能够找到语义相近的部分，但是对于精确匹配关键词，效果就不太理想了。
而BM25是词频统计模型，只看词有没有出现，出现了多少次，完全不懂语义。
这两者结合，优势互补，向量检索用于检索语义相近的chunk，而IK分词器 + BM25负责精确匹配关键词最后用RRF(Reciprocal Rank Fusion，多路检索结果融合算法，常用于混合检索场景，不直接比较不同检索器的原始分数，而是根据文档在各个结果列表中的排名位置进行融合，最后得到一个统一排序)或者加权的方式把两者的结果融合，最终得到新的排序。

补充：IK分词器是专门针对中文的分词器，因为原版分词器是专为英文设计的，英文天然词与词之间有空格分开，但中文没有，于是就需要专用的中文分词器对每个词语进行分隔

## 5. BM25算法和KNN算法分别是什么？具体怎么实现的？

BM25(Best Matching 25)是信息检索领域的经典算法，是TF-IDF的改进版。

核心思路是；一个词在一个文档中出现的次数越多(词频，TF)，那么这个词对这个文档就越重要。如果一个词在不同文档中出现的次数越多(ITF，逆词频)，那么他的权重就要打折扣。

BM25在此基础上加入了文档长度归一化，避免长文档因为词出现次数多就天然占优。

以下仅作了解，写了你也记不住(😅，搞笑，上面的也记不住)：
BM25 的打分公式大概是这样的：

$$
\text{score}(D, Q) = \sum_{i=1}^{n} \text{IDF}(q_i) \cdot \frac{f(q_i, D)\cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{avgdl}\right)}
$$

其中 $f(q_i, D)$ 是词 $q_i$ 在文档 $D$ 中的词频，$|D|$ 是文档长度，$avgdl$ 是平均文档长度，$k_1$ 和 $b$ 是可调参数。在 ElasticSearch 中，BM25 是默认的相似度算法，开箱即用。

KNN(K-Nearest Neighbors，K近邻)在向量检索中指的是找到和查询向量最相近的K个向量。

文档被嵌入模型转成高维向量后，存入向量索引，查询时把问题也转换成向量，在索引中查找余弦相似度最高的K个文档

ES 8.x版本后原生支持dense_vector类型和knn查询，可以直接在ES里面做向量检索，而无需单独的向量数据库，在ES的mapping里定义dense_vertor字段，索引文档时把向量化结果写入该字段，查询时用knn查询指定query_vertor和k值即可

## 7. 为什么选WebSocket

主要是为了实现LLM的流式输出。大模型生成的答案是一个token一个token地输出，而不是一次性全部输出，如果答案较多，就需要等很久，用户体验不好。而WebSocket是全双工的，支持服务端主动向客户端推送消息，而不像传统HTTP的SSE(`Server-Sent Event`)那样，只能客户端向服务端发送消息。当然，如果只需要单向推送，那SSE更简单

### WebSocket基于什么协议？

基于TCP[[计算机网络#^0fde80]]，但建立连接的过程借用了HTTP，具体来说：
- 客户端发送一个HTTP请求，带上`Upgrade: websocket`和`Connection: Upgrade`头。
- 服务端返回一个`101 Switching Protocols`，表示同意升级
- 之后这个TCP连接就不再走HTTP协议，而是走WebSocket帧协议，实现全双工通信
WebSocket的默认端口是`80(ws://)`和`443(wss://，加密版)`和HTTP跟HTTPS一样，便于穿透防火墙[[ws连接过程.excalidraw]]

## 8. 用Redis存储上下文，具体用哪种类型？

对话上下文是一个有序的消息列表，每条消息有角色和内容两个字段，基于这个特点，**Redis的List**类型是最合适的。

具体是这样的：

- 将用户ID与会话ID作为key，每条消息序列化成JSON字符串后，用RPUSH追加到List末尾
- 读取时用LRANGE key 0 -1 读取所有的消息，或者用-20 -1取最近10轮(每个用户+AI回复消息是一轮)

### 疑问：为什么不用String、Hash、ZSet？

- String因为需要每次存放和取出时都序列化和反序列化，麻烦且有并发风险
- 因为消息列表是有序的，而Hash不保证这一点
- ZSet是有序集合，可以用时间戳来保证消息顺序，但是比List复杂，对这个场景来说有点大材小用，因为还要维护score

## 9. 对话上下文过长怎么办？除了取最近10轮，还有别的办法吗？

最简单的就是取最近10轮，但是这样缺点很明显，会丢失前面的信息。

更进阶的有这几种方案：

- 1. 摘要压缩：~~也是目前主流Agent的实现方案，细节上可能有些差别，但大体相同。~~(持怀疑态度) 当上下文窗口达到阈值时(我一般设定为90%)，就调用大模型进行一次上下文总结摘要，并将最近几轮的历史消息连同摘要一起加入上下文。
  
- 2. 重要性打分：对历史消息进行重要性打分，优先保留重要性高的，例如用户说记住我叫xxx，明显比闲聊更重要
  
- 3. 外部记忆：把重要信息单独存放到记忆库里，每次对话时先从记忆库里检索相关信息然后拼进prompt，类似RAG的思路

- 4. 动态token管理：复杂问题多分配上下文，简单的就分配少点。
