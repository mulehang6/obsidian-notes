## 1. 分片上传、断点续传、分片合并

### 一句话版本

我这块做的是一个基于 `前端分片 + 后端幂等 + Redis Bitmap 快速状态判断 + MySQL/MinIO 持久化` 的上传方案，核心目标是支持大文件稳定上传、断点续传和安全合并。

### 展开回答

如果面试官问“你具体怎么做的”，可以这样答：

> 前端会先计算文件 MD5，把文件按 `5MB` 固定大小切片，然后并发上传。单文件最多 `4` 个分片并发，整体同时最多处理 `3` 个文件。每个分片请求都会带上 `fileMd5`、`chunkIndex`、`totalSize`、`fileName`、`orgTag`、`isPublic` 这些元数据。  
>  
> 后端收到分片后，不是直接无脑写存储，而是先做几层判断。第一层是文件状态判断，如果文件已经在 `MERGING` 或 `COMPLETED`，直接拒绝继续传，避免脏写。第二层是断点续传判断，我用了 `Redis Bitmap` 做上传进度的快路径，key 形如 `upload:{userId}:{fileMd5}`，bit 位对应分片下标。  
>  
> 如果 Redis 命中，说明这个分片已经传过了，就按幂等成功返回；如果 Redis 没命中，还会查一次数据库 `ChunkInfo`，因为数据库才是最终事实来源。如果数据库里已经有这个分片，就回填 Redis，再按幂等成功返回。  
>  
> 真正的新分片才会进入上传流程：先算分片 MD5，再把分片写到 MinIO，路径是 `chunks/{fileMd5}/{chunkIndex}`，然后把分片元数据落到 MySQL，最后再设置 Redis Bitmap。这个顺序是故意这样设计的，也就是 `先存储、再落库、最后标记 Redis`，避免 Redis 提前标成功但数据库和对象存储没落稳。(GPT5.4这黑话到这还挺合适的，好像确实没有比落稳更合适的词了)  
>  
> 合并的时候，我单独做了 `/upload/merge` 接口。它会先校验文件归属、校验分片是否传完整，再用数据库层的 CAS 更新把文件状态从 `UPLOADING` 改成 `MERGING`，避免并发重复合并。之后再按分片顺序从 MinIO 取出路径列表，用 MinIO 的 `composeObject` 做服务端合并，最终生成 `merged/{fileMd5}` 这个对象。合并成功后，会删除旧分片、清理 Redis 状态、更新文件状态为 `COMPLETED`，然后返回预签名 URL。

### 这样设计的原因

你可以补这段，显得思路比较完整：

> 我当时重点考虑了四件事：  
> 第一，大文件上传不能因为网络抖动就整文件重传，所以必须支持断点续传。  
> 第二，上传接口一定要幂等，因为前端重试、浏览器重复提交、网络超时补发都很常见。  
> 第三，上传进度查询要快，所以我用 Redis Bitmap 做状态快查；但 Redis 不能当最终真相，所以数据库里单独保留了 `ChunkInfo`。  
> 第四，合并必须防并发，所以我没有只靠内存锁，而是用了数据库状态流转控制，确保同一个文件只会被一个请求真正执行合并。

### 高频追问

#### Q1：为什么用 Redis Bitmap，而不是直接查数据库？

> 因为分片上传场景下，状态查询非常高频。直接按分片逐个查数据库，QPS 一上来数据库压力会很大。Bitmap 很适合这种“某个下标是否上传”的布尔状态场景，读写都是 O(1)，而且空间占用也小。  
> 但我没有把 Redis 当最终事实来源，因为 Redis 可能丢数据，所以数据库 `ChunkInfo` 仍然保底，Redis miss 时会从数据库回源并回填。

#### Q2：你怎么保证幂等？

> 幂等主要做了三层：  
> 第一层，Redis Bitmap 命中直接返回成功；  
> 第二层，Redis miss 但数据库已经存在 `fileMd5 + chunkIndex`，也直接返回成功；  
> 第三层，数据库保存分片信息时，如果遇到唯一性冲突，会按“已经存在”处理，而不是报错中断。

#### Q3：为什么分片合并放在对象存储侧做？

> 因为如果把所有分片拉回应用服务器再拼接，会占带宽、占磁盘、占 JVM 内存，应用层压力大。现在直接用 MinIO 的 `composeObject` 做服务端合并，链路更短，资源消耗也更可控。

#### Q4：断点续传具体是怎么恢复的？

> 前端本地拿到文件 MD5 以后，可以根据服务端返回的已上传分片列表，只补传缺失分片，不需要从头再来。服务端状态查询本质上是 Redis Bitmap 优先，数据库兜底。

#### Q5：上传时你还考虑了什么业务约束？

> 我在首个分片会做文件类型校验；如果用户不是管理员，还会校验组织级上传大小限制。这个限制不是只看前端传的总大小，我还会结合 `chunkIndex * 5MB + 当前分片大小` 估算已上传体积，防止前端把 `totalSize` 少报绕过限制。

### 30 秒背诵版

> 我做的是一个支持大文件断点续传的上传链路。前端先算文件 MD5，再按 5MB 分片并发上传；后端用 Redis Bitmap 记录分片状态做快速判断，用 MySQL 的分片表做最终事实存储，用 MinIO 存真实分片文件。  
>  
> 如果 Redis 或数据库里已经有这个分片，就按幂等成功返回；新的分片才会真正写 MinIO、落库并标记 Redis。合并时我做了权限校验、完整性校验和状态 CAS，把状态从上传中改成合并中，再用 MinIO 的 composeObject 做服务端合并，最后清理旧分片并更新状态。这套方案的核心是高频查询快、失败可恢复、并发下不重复合并。

## 2. Kafka 异步解耦文件合并、文档解析、向量化

### 一句话版本

我把“上传完成”和“文档解析、向量化入库”拆成了两段链路，通过 Kafka 异步衔接，目的是缩短用户同步等待时间，同时把重 CPU/重 IO 的任务从接口线程里剥离出来。

### 展开回答

> 在这个系统里，用户最直观的痛点不是“上传慢”，而是“上传完之后还要等很久”。因为文件真正耗时的不是合并，而是后面的文档解析、切片、向量化和索引入库。  
>  
> 所以我在设计上把上传链路拆成两段：  
> 第一段是同步链路，负责分片上传、完整性校验、服务端合并，以及一个轻量的 Embedding 用量预估；  
> 第二段是异步链路，负责真正的文档解析和向量化。  
>  
> 文件合并成功后，我会构造一个 `FileProcessingTask`，把 `fileMd5`、`filePath`、`fileName`、`userId`、`orgTag`、`isPublic`、`taskType` 这些信息发到 Kafka。之所以把权限字段也带上，是因为后续解析和向量化不能丢上下文，不然会影响组织隔离和文档可见性。  
>  
> 生产端我用了事务发送 `executeInTransaction`，同时 Kafka Producer 配了 `acks=all`、`enable.idempotence=true`、`retries=3`，尽量保证消息可靠投递。消费者这边通过 `@KafkaListener` 监听文件处理主题，收到任务后下载合并后的文件，顺序执行 `parseAndSave` 和 `vectorizeWithUsage`。  
>  
> 如果消费失败，我没有吞异常，而是显式抛出，让 Kafka 的 `DefaultErrorHandler` 处理。当前策略是固定退避 `3 秒`，最多重试 `4 次`，重试耗尽就进入死信队列 `file-processing-dlt`。这样做的好处是主流程响应更快，后台任务也具备重试和失败隔离能力。

### 为什么这样做

> 主要是三点考虑：  
> 第一，解析和向量化本身耗时长、依赖外部服务，放在同步请求里会把接口 RT 拉得很高。  
> 第二，这类任务失败后通常适合重试，不适合让用户一直卡在请求里等待。  
> 第三，上传成功和知识入库成功是两个不同阶段，拆开以后状态更清晰，我可以单独维护 `PENDING / PROCESSING / COMPLETED / FAILED` 这套向量化状态。

### 高频追问

#### Q1：为什么不直接开线程池异步处理？

> 线程池只能解决“当前实例内异步”，但不能很好解决可靠投递、失败重试、宕机恢复和死信隔离。Kafka 更适合这种跨阶段、可恢复、需要重试的任务链路。

#### Q2：为什么消息里要带 `orgTag` 和 `isPublic`？

> 因为文档向量化后要进入检索链路，权限上下文不能丢。消息里把租户和可见性信息带全，后续解析、向量化、检索都能沿用同一套权限边界。

#### Q3：你怎么体现“接口等待时间减少”？

> 我做法上是把重任务从同步接口里拿掉。现在用户在 `/merge` 阶段完成后就可以马上拿到成功响应和预估 Token，不需要等待整个解析和向量化结束。也就是说，用户感知的是“上传完成即可返回”，后面的重处理在后台跑。

#### Q4：Kafka 这块你做了哪些可靠性配置？

> Producer 侧用了 `acks=all`、幂等生产者和事务发送；Consumer 侧用了 `DefaultErrorHandler + DeadLetterPublishingRecoverer`，固定间隔重试，多次失败后进 DLT。这个组合能把常见的瞬时失败、外部服务抖动和脏消息隔离开。

### 30 秒背诵版

> 我把上传合并和解析向量化拆成了同步、异步两段。同步链路只负责上传、校验、合并和轻量预估，保证接口尽快返回；异步链路通过 Kafka 执行文档解析、切片和向量化。  
>  
> 我们的消息里会带上文件标识、用户、组织、公开性这些上下文，避免后续权限丢失。Producer 侧做了事务、`acks=all` 和幂等配置，Consumer 侧做了重试和死信队列。这样既缩短了用户等待时间，也把长耗时任务从接口线程里解耦出来了。

## 3. Apache Tika 多格式解析与基础文本切分

### 一句话版本

我用 Apache Tika 做多格式文档抽文本，对 PDF 做了单独优化；解析完之后不是简单按固定长度硬切，而是做了“父块流式处理 + 段落/句子级切分 + 重叠窗口”的文本分块策略，兼顾性能和语义完整性。

### 展开回答

> 解析层我做了两条路径。  
> 对非 PDF 文档，主要使用 `Tika AutoDetectParser` 做自动格式识别和流式解析，这样像 `pdf/doc/docx/xls/xlsx/ppt/pptx/txt/rtf/md/html/xml/json/csv/epub` 这些常见文档格式都能统一处理。  
>  
> 对 PDF，我没有完全走通用 Tika 流程，而是单独做了页级处理，用 `PDFBox` 按页抽文本，再做页眉页脚等重复边界文本清理。原因是 PDF 在真实业务里噪音比较多，如果直接整本抽文本，重复页眉页脚会污染切片和召回结果。  
>  
> 在文本切分上，我不是一次性把整份文档读进内存，而是采用流式父块处理。系统里配置了一个较大的 `parentChunkSize`，默认是 `1MB`，Tika 在解析过程中不断往缓冲区里写字符，缓冲区到阈值后就触发一次处理。每个父块再按更小的业务切片去拆，当前配置的子切片大小是 `512`，重叠窗口是 `100`，最小切片是 `100`。  
>  
> 具体切法上，先按段落切；段落过长再按句子切；如果句子还过长，再继续拆。拆完以后，我还做了两个优化：  
> 第一，小块合并，避免只有标题或半句这种切片太碎；  
> 第二，语义重叠，把上一个切片尾部的一部分句子带到下一个切片里，减少切片边界导致的信息断裂。  
>  
> 最后每个子切片都会作为 `DocumentVector` 先落库，保存 `fileMd5`、`chunkId`、`textContent`、`pageNumber`、`anchorText`、`userId`、`orgTag`、`isPublic` 等字段，供后续向量化和检索使用。

### 关于 Token 预估，你可以这样答

因为你又补了 `UsageQuotaService`，这段建议你一起背：

> 文档合并完成后，我还加了一步 Embedding 用量预估。这个预估不是简单按字符数除一个固定值，而是做了一个轻量的多字符集估算模型：  
> ASCII 字符按 `0.30`，中日韩字符按 `0.95`，其他字符按 `0.55` 的系数估算，再加固定开销，最后整体乘一个 `1.15` 的安全系数。  
>  
> 这样做的目的不是做到和模型返回的 usage 完全一致，而是为了在上传完成时，先给用户一个比较稳定的 Token 消耗预期，也方便后续额度校验和预算控制。

### 为什么不直接固定长度硬切？

> 因为固定长度硬切实现简单，但是效果差，最容易把一句话、一个段落甚至一个表格描述切断。对于 RAG 来说，切片语义断裂会直接影响向量召回质量和最终回答质量，所以我至少做到了段落优先、句子兜底和跨块 overlap。

### 高频追问

#### Q1：为什么要做 PDF 特殊处理？

> 因为 PDF 在企业知识库里是高频格式，而且最容易出现页眉页脚、页码、重复版权信息等噪音。如果不清理，最终会把无意义内容切进很多 chunk，影响召回质量。

#### Q2：为什么要流式解析？

> 因为大文件如果先整份读入内存再处理，容易吃掉大量 JVM 堆内存，甚至 OOM。流式父块处理可以把内存占用控制在一个稳定范围内，而且代码里还做了内存阈值检查，默认阈值是 `0.8`。

#### Q3：为什么切片还要做 overlap？

> overlap 主要是为了减少边界损失。比如某个概念的定义刚好出现在两个 chunk 的交界处，如果完全不重叠，检索时可能两个 chunk 都不够完整；适当重叠以后，召回稳定性会更好。

#### Q4：向量化前为什么先落 `DocumentVector`？

> 因为我希望解析和向量化是两个可拆阶段。先把文本切片落下来，后面向量化失败也能重试，不需要重新解析原始文件，而且这也更利于问题排查和异步重试。

### 30 秒背诵版

> 我用 Tika 负责多格式文档抽文本，PDF 单独用 PDFBox 做页级处理和页眉页脚清理。解析不是整文件一次性吃进内存，而是流式处理父块，到一定大小后再按段落、句子去切成更小的子块。  
>  
> 子块不是硬切，我做了小块合并和 overlap，尽量保持语义完整，减少 RAG 检索边界损失。切片数据会先落库，再进入异步向量化。上传完成时还会做一次 Embedding Token 预估，估算逻辑按 ASCII/CJK/其他字符不同权重加安全系数计算。

## 你可以直接背的精简总版

> 这块我主要做了三件事。  
> 第一，做了大文件分片上传和断点续传。前端按 5MB 切片并发上传，后端用 Redis Bitmap 做分片状态快查，用 MySQL 分片记录做最终事实来源，用 MinIO 存真实分片。新分片写入时按照“先对象存储、再落库、最后标 Redis”的顺序处理，保证幂等和一致性。文件合并时会先做权限校验、完整性校验和状态 CAS，再用 MinIO 的 composeObject 完成服务端合并。  
>  
> 第二，把合并后的解析和向量化放到了 Kafka 异步链路里。这样用户上传完成后不用等完整的知识入库流程，接口响应时间更短。Kafka 这块我做了事务发送、幂等生产、重试和死信队列，保证处理链路更稳。  
>  
> 第三，在文档处理层，我用 Apache Tika 做多格式文档抽文本，对 PDF 单独做了页级清洗；切片时不是简单硬切，而是用了流式父块处理、段落句子级切分、小块合并和 overlap，尽量保证语义完整性。同时我还加了 Embedding Token 预估，方便用户提前知道向量化成本，也方便额度控制。
