# 2. 介绍一下ES的倒排索引

(答完后，面试官：八股还是要多背啊 原话)

倒排索引就是把 `文档到内容` 的关系反过来，变成 `词到文档` 的关系。比如有三篇文章，ES会先通过分词器把标题，正文等字段拆成一个词，然后像建立词项到文档ID列表的映射。用户搜索关键词时，ES不需要像 `like %xxx%` 那样扫描所有文本，而是直接根据关键词找到包含它的文档列表，索引全文检索效率高

> 补充：倒排索引除了文档ID，还可以记录词频、位置、偏移量等信息，所以ES能实现相关性排序、短语匹配和关键词高亮。中文场景下，倒排索引的效果很依赖分词器

# 7. RabbitMQ和Kafka这两个，具体到项目中你会如何选择？

如果是普通业务系统里的消息解耦，比如下单后发通知、更新积分、订单超时取消、文章发布后同步ES，我会选择RabbitMQ。因为RabbitMQ的exchange、routing key、queue模型比较适合业务路由，同时ack、死信队列、消息延迟消息、失败重试这些机制也比较适合业务消息

如果是日志采集、用户行为埋点、数据同步、实时计算这类场景，我会选Kafka。Kafka的核心优势是高吞吐、可持久化、按offset消息、支持多个消费者组同步消费一份消息，适合大数据和流式处理场景

# 8. MySQL的索引在哪些情况下会失效？

- 对索引列使用函数或者表达式
  ```sql
	-- 索引失效
	SELECT * FROM users WHERE YEAR(create_time) = 2023;
	SELECT * FROM products WHERE price*2 > 100;
	
	-- 优化方案（使用范围查询）
	SELECT * FROM users WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31';
	SELECT * FROM products WHERE price > 50;
  ```

- like模糊查询以通配符开头
```sql
-- 索引失效
SELECT * FROM articles WHERE title LIKE '%数据库%';

-- 可以使用索引（但范围有限）
SELECT * FROM articles WHERE title LIKE '数据库%';

-- 解决方案：考虑全文索引或搜索引擎
SELECT * FROM articles WHERE MATCH(title) AGAINST('数据库');
```

- 联合索引违反最左前缀原则
```sql
-- 假设有联合索引 (a, b, c)
SELECT * FROM table WHERE b = 2 AND c = 3;  -- 索引失效
SELECT * FROM table WHERE a = 1 AND c = 3;  -- 只使用a列索引

-- 正确使用联合索引
SELECT * FROM table WHERE a = 1 AND b = 2 AND c = 3;
```

可不背

- 使用or连接非索引列条件
```sql
-- 假设name有索引但age没有
SELECT * FROM users WHERE name = '张三' OR age = 25;  -- 全表扫描

-- 优化方案1：使用UNION ALL
SELECT * FROM users WHERE name = '张三'
UNION ALL
SELECT * FROM users WHERE age = 25 AND name != '张三';

-- 优化方案2：考虑为age添加索引
```

- 使用 `!=` 或 `<>` 不等值查询会导致索引失效
```sql
SELECT * FROM user WHERE status != 1;  -- 若大部分行 `status=1`，可能全表扫描

-- 优化方案：使用范围查询
SELECT * FROM user WHERE status < 1 OR status > 1;
```

## 什么情况下模糊查询不走索引？

```sql
SELECT * FROM table WHERE column LIKE '%xxx%';
```

这个查询结果会返回column列中包含的xxx的记录

但是如果 `%` 出现在模糊查询的开始位置，如 `like %xxx`，MySQL就无法使用索引，因为数据库必须全表扫描以匹配任意位置的字符串

# 9. RabbitMQ怎么保证信息一致性

生产者端开启 `publisher confirm` 和 `return callback`，确认消息成功到达交换机并路由到队列；Broker端设置交换机、队列和消息持久化，防止RabbitMQ重启导致消息丢失；消费端使用手动ACK，业务成功处理后再确认，失败时重试或者进入死信队列

另外消费者还要做幂等，因为消息可能重复投递，比如使用业务唯一id，数据库唯一索引、redis去重，或者用主键覆盖更新。对于数据库和MQ发送之间的一致性，可以使用本地消息表，把业务数据和待发送消息放在同一个数据库事务里提交，再异步投递MQ，失败就重试，保证最终一致性
