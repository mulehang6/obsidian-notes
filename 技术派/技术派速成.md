## 一、Redis：真实实现到底是什么

### 先说结论

如果面试官按你的简历问：

> 你说 Redis 做了热点文章缓存和排行榜统计，这块具体怎么做的？

你不要直接按“热点文章缓存”去讲，因为**当前项目代码里，Redis 主要承担的是两类能力**：

1. **文章 / 用户统计计数**
2. **用户活跃度排行榜**

而不是“文章列表结果直接缓存到 Redis”。

---

### 面试官问：Redis 这一块你具体怎么做的？

你可以这样答：

我在这个项目里，Redis 主要不是拿来缓存整页文章列表，而是用来做**高频统计数据的实时累加和排行榜计算**。

具体分两部分。

第一部分是**文章和用户统计信息**。  
我把文章维度和用户维度的统计信息分别放在 Redis Hash 里，比如：

- 文章点赞数
- 文章收藏数
- 文章评论数
- 文章阅读数
- 用户粉丝数
- 用户关注数
- 用户累计获赞数
- 用户文章数

请求查询这些统计数据时，服务层直接从 Redis 读，而不是每次都查库聚合。

第二部分是**用户活跃排行榜**。  
项目里把用户点赞、收藏、评论、发文、关注这些行为映射成不同分值，然后用 Redis 的有序集合做日榜、月榜。

所以更准确地说，我是用 Redis 做了“**计数加速 + 榜单计算**”。

### 面试官问：你这里的统计数据是怎么更新的？

你可以这样答：

统计更新主要分两种。

一种是**直接在业务动作后增量更新 Redis**。  
比如点赞、取消点赞、收藏、取消收藏、评论、关注这些行为，会通过事件监听器异步更新 Redis Hash 里的对应字段，用的是 `hIncr`。

另一种是**阅读数这种高频指标先只写 Redis，再定时刷库**。  
项目里文章阅读量不会每次阅读都直接更新数据库，而是先在 Redis 里累加，之后由定时任务每 5 分钟把 Redis 里的阅读总数同步到数据库。

这样设计主要是因为阅读量是高频写，如果每次都直接写数据库，成本会比较高。

---

### 面试官问：你为什么这么做？

可以这样答：

我这里的核心考虑是把**高频、可容忍短暂延迟**的数据从数据库热点路径里摘出来。

像阅读数、点赞数、收藏数、粉丝数、活跃榜这些数据有几个特点：

- 更新频繁
- 查询也频繁
- 页面展示对秒级绝对一致要求没那么高

所以比较适合先放 Redis 做实时累加或聚合，数据库作为最终落地存储。

这样做的好处是：

1. 查询快
2. 减少数据库聚合压力
3. 写入压力从同步写库变成了 Redis 增量写

- 在线请求时只写 Redis
- 定时任务每 5 分钟把 Redis 中的总数覆盖写回 `read_count`

这意味着短时间内 Redis 和数据库可能不完全一致，但对阅读统计场景是可接受的，而且换来了更好的写性能。

## 二、Elasticsearch：文章全文检索

### 面试官问：你这一块具体怎么做的？

你可以直接这样答：

我这块做的是一套基于 Elasticsearch 的文章搜索链路，核心思路是 **ES 负责全文检索，MySQL 负责业务数据回填**。

具体流程是这样的：

1. 用户输入关键词后，请求先进入搜索接口。
2. 服务层先调用 Elasticsearch 做全文检索。
3. ES 主要在文章的 `title`、`shortTitle`、`summary`、`content` 这几个字段里做匹配。
4. ES 返回命中的文章 ID、相关性分数和高亮片段。
5. 我再根据这些文章 ID 去 MySQL 批量查完整文章数据。
6. 最后把文章标题、作者、标签、分类、阅读数这些页面真正需要的数据组装后返回前端。

所以它不是“直接把 ES 当数据库查完就返回”，而是“**ES 先召回，MySQL 再补全**”。

---

### 面试官问：你的 ES 查询是怎么设计的？

你可以这样答：

我这里用的是 `bool` 查询，把条件拆成两类：

- 全文检索条件放 `must`
- 精确过滤条件放 `filter`

关键词会去匹配：

- `title`
- `shortTitle`
- `summary`
- `content`

过滤条件这边，前台至少会限制：

- 文章必须在线
- 文章不能删除

后台搜索还支持继续叠加：

- 作者
- 标题
- 专栏
- 状态

排序上先按 `_score`，再按 `updateTime`。

---

### 面试官问：你为什么不用 MySQL 直接模糊查询？

可以这样答：

因为 MySQL `%keyword%` 在这类全文场景下有几个天然短板：

- 多字段全文匹配性能差
- 很难做相关性排序
- 高亮展示不方便

所以我把全文召回交给 ES，把权威业务数据保留在 MySQL。

---

### 面试官问：索引怎么同步？

你可以这样答：

这里用的是**文章领域事件 + 异步索引同步**。

文章新增、修改、删除后，会触发文章事件。监听器收到事件后：

- 删除事件：删除 ES 文档
- 其他事件：重新构建单篇文章索引并写回 ES

这个方案的核心考虑是：

1. 不阻塞主流程
2. 同步链路清晰
3. 支持单篇增量更新

---

### 面试官问：你简历里写“关键词、标签、作者组合查询”，当前代码真支持吗？

这个问题你要谨慎答。

最稳妥答法：

> 当前代码里，关键词全文检索和作者等条件组合过滤是有实现支撑的；但如果严格看索引结构，`tagIds` 还没有真正建进 ES 文档里，所以“标签组合查询”更准确地说是现成扩展点，而不是完全落地能力。如果要继续补，我会把 `tagIds` 聚合进索引文档，再在查询 DSL 里加 `terms filter`。

---

### 一段话直接背

> 我这块做的是一套基于 Elasticsearch 的文章搜索链路。整体设计上，我把 ES 当成检索副本，用它来做标题、短标题、摘要、正文这几个字段的全文检索、相关性排序和高亮展示；再把 MySQL 当成权威数据源，基于 ES 返回的文章 ID 回查完整文章信息，补齐作者、标签、分类和统计数据。查询上我采用的是 `bool` 结构，把关键词放到 `must`，把状态、作者、专栏这类精确条件放到 `filter`，排序先按 `_score` 再按更新时间。同步上我用了文章事件驱动的异步增量更新，新增修改就重建单篇索引，删除就删 ES 文档，同时保留全量重建能力兜底。

## 三、AOP + MDC：请求标识与耗时日志

### 面试官问：你这一块具体是怎么做的？

你可以这样答：

这块我实际上做了两层。

第一层是**请求级 traceId 注入**。  
在 Web 层的 `ReqRecordFilter` 里，请求一进来就生成 `traceId`，放进 MDC，同时把 traceId[[技术派面经#1. traceId怎么生成的？]] 回写到响应头 `g-trace-id`，这样前后端和日志都能对上。

第二层是**方法级耗时和业务标识日志**。  
我定义了一个 `@MdcDot` 注解，再通过 `MdcAspect` 去拦截被标注的方法，把业务标识 `bizCode` 写进 MDC，并在方法执行结束后统一打印耗时日志。

所以这块不只是“打印请求日志”，而是把：

- 请求级 traceId
- 方法级 bizCode
- 方法耗时

统一打进日志上下文里。

### 面试官问：为什么用 MDC，不直接把 requestId 一层层传下去？

可以这样答：

因为手动透传 `requestId` 有两个问题：

1. 侵入业务代码
2. 很容易漏传

MDC 的好处是把上下文信息放到当前线程里，日志框架打印时自动带出来，不需要业务代码层层传参。

---

### 面试官问：为什么还要再加 AOP？

可以这样答：

因为请求级 traceId 只能解决“同一个请求串起来”，但还不够定位“某个业务对象、某个方法具体耗时多少”。

所以我又补了一层 AOP：

- 通过 `@MdcDot` 给关键方法打业务标识
- 用切面统一记录方法耗时

这样日志既能按请求追踪，也能按业务对象定位。

---

### 面试官问：你这里的核心考虑是什么？

可以这样答：

我主要考虑三件事：

1. **统一**：所有日志都要能带 traceId
2. **低侵入**：不希望业务代码到处传 requestId
3. **可排查**：除了请求链路，还希望能定位到具体业务对象和方法耗时

所以最后是 `Filter + MDC + AOP` 这套组合。

---

### 一段话直接背

> 我这块不是简单做了个日志打印，而是做了两层日志追踪机制。第一层是在请求进入时通过 Filter 生成 traceId，放进 MDC，并回写到响应头，保证同一请求在全链路日志里都能串起来；第二层是通过自定义 `@MdcDot` 注解和 AOP，在关键方法上补充业务标识 `bizCode`，同时统一记录方法耗时。日志格式里会直接打印 `traceId` 和 `bizCode`，这样线上排查时既能按请求查，也能按业务对象和方法定位慢点或异常点。

## 四、RabbitMQ：真实实现是什么

### 先说结论

这个项目里的 RabbitMQ 不是 Spring `RabbitTemplate/@RabbitListener` 那种标准接法，而是：

- **自定义连接池**
- **手动 publish**
- **手动 consumer**
- 当前主要用于 **点赞通知** 这条异步链路

所以你面试里不要讲成“我们所有异步流程都走 MQ”，那会说过头。

---

### 面试官问：RabbitMQ 这一块你具体怎么做的？

你可以这样答：

当前项目里，RabbitMQ 主要是用来做**点赞通知的异步解耦**。

具体流程是：

1. 用户点赞后，主流程先完成用户足迹 `UserFootDO` 的落库。
2. 如果这次操作确实改变了数据库状态，就进入通知流程。
3. 对于点赞通知，如果 RabbitMQ 开关打开，就把这条点赞消息序列化后发到 RabbitMQ。
4. 消费端收到消息后，再去落通知消息。

也就是说，RabbitMQ 在这里承担的是“把点赞后的通知处理从主流程里拆出去”的作用。

### 面试官问：为什么要引入 MQ？

可以这样答：

因为点赞动作本身属于主流程，但“生成通知消息”属于后置动作。

如果把通知处理同步串在点赞主流程里，会带来两个问题：

1. 接口响应时间变长
2. 点赞逻辑和通知逻辑耦合太紧

所以我把它拆成：

- 主流程负责完成点赞业务
- 通知逻辑异步化处理

这样主流程更轻，后面通知怎么扩展也更独立。

---

### 面试官问：为什么不是所有通知都走 RabbitMQ？

你可以这样答：

当前实现里其实是有区分的。

- **点赞通知**：优先走 RabbitMQ
- **其它通知类型**：还是走应用内事件 `MsgNotifyHelper.publish(...)`

所以这不是一个“全量 MQ 化”的设计，而是先挑了一个典型高频、适合拆出去的链路做异步解耦。

这反而是一个比较务实的实现方式。

---

### 面试官问：你这里怎么考虑消息可靠性和幂等？

你可以这样答：

当前这块代码里，消费者拿到消息后会手动 `ack`，并且在保存点赞通知时会先查是否已经存在对应通知记录，避免重复落库。

所以幂等更多是落在“通知记录去重”这一层。

如果继续增强，我会重点补：

1. 发送失败重试
2. 消费异常补偿
3. 更清晰的死信处理

因为当前实现能跑通链路，但还不是那种特别完善的 MQ 治理体系。

---

### 面试官问：这块你怎么考虑的？

可以这样答：

我这里的核心考虑其实很简单：

1. 先把主流程做轻
2. 先把一个高频后置动作拆出去
3. 不为了上 MQ 而把所有链路都 MQ 化

所以 RabbitMQ 在这个项目里，更像是“**对点赞通知这条链路做异步解耦试点**”。

---

### 一段话直接背

> 我在这个项目里对 RabbitMQ 的使用比较克制，当前主要是把点赞通知这条链路做了异步解耦。用户点赞后，主流程先完成用户足迹落库；如果状态确实发生变化，再把点赞消息投递到 RabbitMQ，由消费者异步落通知记录。这样做的核心目的是减少主流程阻塞、降低点赞逻辑和通知逻辑的耦合。当前实现是自定义连接池加手动 publish/consume，不是 Spring 标准注解监听模式，所以我一般会把它定义成“针对点赞通知的异步解耦实践”，不会说成整个系统都已经全面 MQ 化。

## 六、最重要的提醒

这几个点你面试里一定要收着讲：

1. **Redis**
   不要说“我做了热点文章 Redis 缓存”，更准确是“统计计数和榜单优化”。

2. **Elasticsearch**
   不要把“标签组合查询”讲成已完全落地，当前更像明确扩展点。

3. **RabbitMQ**
   不要讲成“系统异步流程全面 MQ 化”，当前主要是点赞通知链路。

4. **AOP + MDC**
   这块是可以放心讲的，代码支撑比较足，而且讲起来比较完整。
