# 1. 第一章 并发基础
``` kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    launch {
        println("A1")
        delay(500) // 执行到这里时第一个协程挂起，执行下面的
        println("A2")
    }

    launch {
        println("B")
    }
}
```
执行结果：A1, B, A2。
如果换成Thread.sleep，那么就是A1, A2, B。因为 sleep 会阻塞当前线程

- `runBlocking` 自己会阻塞调用它的线程，直到它管理的任务完成。
- `suspend` 只是表示函数可以挂起，并不意味着每次调用都会挂起，更不意味着函数体里的阻塞操作自动变成非阻塞操作。
![[runBlocking执行过程.png]]

## 1.1 一些疑问
### 1.1.1 runBlocking 是否只能像示例代码那样使用？只能放在main后面？何时使用？

不是，runBlocking 本质上就是个可以调用的函数，例如可以这样写：
```kotlin
fun main() {
    runBlocking {
        delay(1000)
        println("Hello")
    }
}
```

在普通函数中调用：
```kotlin
fun getUser(): String {
    return runBlocking {
        delay(1000)
        "Alice"
    }
}
```

正确替代方法：

如果本身就是挂起函数
```kotlin
suspend fun getUser(): User {
    return userService.fetchUser()
}
```
<mark style="background-color: #FF5582A6;">直接调用即可。</mark> 这里指的是语法上的直接调用，并不是说直接执行协程

如果需要在挂起函数内创建并发子任务：<mark style="background-color: #FFB86CA6;">(扩展内容，暂时看不太懂)</mark>
```kotlin
suspend fun getUser(): User = coroutineScope {
    async {
        userService.fetchUser()
    }.await()
}
```
这里的 `async` 只是演示用法。只有一个任务而且立即 `await()`，实际上没有并发收益，直接调用 `fetchUser()` 更简单。

runBlocking 主要用于普通同步代码必须调用挂起函数，而调用入口又不能改成 `suspend` 的场景，例如某些测试或同步 API 的兼容代码。例子如下：

假设你接入了一个第三方 Java 库，它规定你必须实现下面这个接口：
```kotlin
interface ReportProvider {
    fun generate(): String
}
```
你无法修改这个接口，也不能把它的 `generate()` 改成 `suspend fun`。
但你的业务逻辑已经使用了协程：
```kotlin
suspend fun fetchReport(): String {
    delay(1000)
    return "报告内容"
}
```
直接这样写会编译失败：

```kotlin
class MyReportProvider : ReportProvider {
    override fun generate(): String {
        return fetchReport() // 编译错误
    }
}
```
原因是<mark style="background-color: #FF5582A6;">普通函数不能直接调用挂起函数。</mark>
这时可以使用 `runBlocking`：

```kotlin
class MyReportProvider : ReportProvider {
    override fun generate(): String {
        return runBlocking {
            fetchReport()
        }
    }
}
```
这个例子的重点是：**第三方接口要求同步返回结果，所以必须等。**
==`suspend` 提供挂起能力，`async` 用于启动并发任务，`await` 用于等待并获取结果。==

### 1.1.2 如何在 SpringBoot 中使用协程呢？
**Spring 本身就支持挂起函数，因此通常不用自己调用 `runBlocking` 或手动创建协程作用域来处理 HTTP 请求。**

Spring MVC 和 Spring WebFlux 都支持 `suspend` Controller。区别在于底层请求处理模型。只是提一嘴 WebFlux，这里不展开。

**一个实际的 Spring Boot 场景** ^058e78

假设你的后端需要提供这个接口：
```http
GET http://localhost:8080/summary
```
后端会同时调用两个 HTTP 接口：
- `/mock/user`，模拟获取用户资料，耗时约 1 秒。
- `/mock/orders`，模拟获取订单，耗时约 1 秒。
最后把两个结果合并。

先模拟两个慢接口
```kotlin
import kotlinx.coroutines.delay
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.RestController

@RestController
class MockController {

    @GetMapping("/mock/user")
    suspend fun user(): String {
        delay(1000)
        return "Alice"
    }

    @GetMapping("/mock/orders")
    suspend fun orders(): String {
        delay(1000)
        return "Order-1, Order-2"
    }
}
```

编写发送 HTTP 请求的 Service
```kotlin
import kotlinx.coroutines.future.await
import org.springframework.stereotype.Service
import java.net.URI
import java.net.http.HttpClient
import java.net.http.HttpRequest
import java.net.http.HttpResponse

@Service
class DemoService {

    private val client = HttpClient.newHttpClient() // JDK中的API

    suspend fun get(path: String): String {
        val request = HttpRequest.newBuilder()
            .uri(URI.create("http://localhost:8080$path"))
            .GET()
            .build()

		// sendAsync是JDK提供的异步HTTP请求API，调用后得到CompletableFuture，代表将来可以获得的结果
        val future = client.sendAsync(
            request,
            HttpResponse.BodyHandlers.ofString()
        )

        val response = future.await() // kotlin提供的扩展函数，当Future尚未完成时，await()可以挂起当前协程，而不是阻塞线程等待

        check(response.statusCode() == 200)
        return response.body()
    }
}
```

最后编写Controller
```kotlin
import kotlinx.coroutines.async
import kotlinx.coroutines.coroutineScope
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.RestController

data class Summary(
    val user: String,
    val orders: String
)

@RestController
class SummaryController(
    private val service: DemoService
) {

    @GetMapping("/summary")
    // 这个语法糖叫 单表达式函数体 + 尾随 lambda
    suspend fun summary(): Summary = coroutineScope {

        val user = async {
            service.get("/mock/user")
        }

        val orders = async {
            service.get("/mock/orders")
        }

        Summary(
            user = user.await(),
            orders = orders.await()
        )
    }
}
```

启动项目后，请求 `/summary`，正常情况下大约 1 秒多一点就能拿到：
```json
{
  "user": "Alice",
  "orders": "Order-1, Order-2"
}
```

如果去掉两个 `async`，改成：
```kotlin
val user = service.get("/mock/user")
val orders = service.get("/mock/orders")
```
两个调用就会顺序等待，总耗时接近 2 秒。

这里并发执行的是两个 HTTP 请求。即使只有一个协程执行线程，也可以通过非阻塞等待让两个 HTTP 请求同时处于进行中。



<mark style="background-color: #FF5582A6;">注意事项：</mark>
<mark style="background-color: #FF5582A6;">Mybatis-plus/Mybatis 底层均使用 JDBC，而JDBC为阻塞式查询</mark>，而针对独立的阻塞操作，可以考虑：
```kotlin
suspend fun getUser(id: Long): User? =
    withContext(Dispatchers.IO) {
        userMapper.selectById(id)
    }
```
把阻塞任务安排到更适合阻塞I/O的线程池中执行

<mark style="background-color: #FF5582A6;">另外，Spring 的传统 JDBC 事务上下文通常和线程绑定。在 `@Transactional` 管理的事务内部，不能随意切换到 `Dispatchers.IO`，否则可能导致事务上下文不能正确传递。</mark>

来看下面的一个例子：
```kotlin
suspend fun getUser(): User? =
    withContext(Dispatchers.IO) {
        userMapper.selectById(1)
    }
```

在发生调度切换的典型情况下：
1. 原来的协程挂起，等待 `withContext` 的结果。
2. `Dispatchers.IO` 将数据库查询安排到适合阻塞 I/O 的工作线程。
3. 工作线程执行 JDBC 查询，并被阻塞约 1 秒。
4. 查询完成后，协程取得返回值，继续执行。
第2点按我的理解，这里不就是换了个更“合适”的线程阻塞吗？那换到IO有什么意义？
假设一个传统的 Spring MVC 服务，请求处理线程池里有 10 个线程。
有 10 个请求同时进来，每个请求都需要等待一次阻塞式数据库查询。
![[切换到IO DIspatcher的意义.png]]
<mark style="background-color: #FFF3A3A6;">这里的收益是让一类线程免于被阻塞操作长期占用，特别是有其他任务需要使用这些线程时。</mark>
但必须注意：
- JDBC 线程依然被占用。
- 数据库连接依然被占用。
- 假如数据库连接池只有 10 个连接，也不会因为用了协程就能同时执行 100 个数据库查询。
- 如果业务本来就是传统的同步 MVC + MyBatis-Plus，额外切换线程可能带来开销，性能未必更好。
所以，不能把 `withContext(Dispatchers.IO)` 当成<mark style="background-color: #FF5582A6;">数据库查询的通用性能优化手段。</mark>
如果所有的请求都主要是在执行阻塞式 JDBC，那么简单地把阻塞从一组线程转移到另一组线程，通常不能从根本上改善系统吞吐量。

相反，上一节的 [[#^058e78]] 才真正实现了 HTTP 等待期间不阻塞协程的执行线程。

另有一点注意事项：`withContext(Dispatchers.IO)` 不保证切换到另一个物理线程。例如，从 `Dispatchers.Default` 切换到 IO 时，两者有可能共用同一个线程。它真正改变的是协程使用的调度上下文。<mark style="background-color: #FFB86CA6;">(先仅作了解)</mark>

## 1.2 先了解一下线程池
**线程池一般是由程序中的库或框架管理的，线程本身则由操作系统调度。**

例如 Java 的 `ThreadPoolExecutor`、Spring 的 `ThreadPoolTaskExecutor` 都可以管理线程池。

Kotlin 协程使用的 `Dispatchers.IO` 和 `Dispatchers.Default` 则是协程库提供的调度器，它们在 JVM 上使用共享的工作线程池。

### 2.1 先理解线程池

假设有三个任务需要执行：
```kotlin
taskA()
taskB()
taskC()
```

最简单的做法是每个任务创建一个新线程：
```kotlin
Thread { taskA() }.start()
Thread { taskB() }.start()
Thread { taskC() }.start()
```
但是频繁创建、销毁线程有成本。

线程池采用另一种方式：创建或维护一批工作线程，让它们反复执行提交进来的任务。
![[线程池示例.png]]
这样可以重复使用线程，避免为每个小任务都创建新的线程。

不过有个问题：如果工作线程执行到 `Thread.sleep()` 或阻塞式 JDBC 查询，它在等待期间就不能继续处理其他任务。

也就是说<mark style="background-color: #FF5582A6;">不能把「使用线程池」等同于「非阻塞」。</mark>

### 2.2 Dispatchers.IO 和线程池是什么关系？

```kotlin
withContext(Dispatchers.IO) {
    userMapper.selectById(1)
}
```
这里各部分的职责是：

|部分|作用|
|---|---|
|`withContext`|在指定的协程上下文中执行代码，并等待其结果|
|`Dispatchers.IO`|提供适合执行阻塞 I/O 的调度环境|
|工作线程池|提供实际运行代码的线程|
|`selectById()`|执行 JDBC 查询，期间可能阻塞工作线程|

`Dispatchers.IO` 会按需使用共享工作线程，默认阻塞 I/O 并行度限制为 <mark style="background-color: #FFF3A3A6;">64</mark> 或<mark style="background-color: #FFF3A3A6;"> CPU 核心数</mark>，取两者较大值，且可以配置。它和 `Dispatchers.Default` 也共享底层线程资源。

### 2.3 Dispatchers.Default
- Default：用于计算密集型任务，例如计算复杂数据
- IO：主要用于可能阻塞线程的IO任务，例如传统JDBC查询，阻塞式文件读取


# 2. 第二节 Kotlin 协程的挂起与恢复机制

## 2.1 第一节 Continuation、挂起点与恢复执行

目的：弄明白协程运行到 `delay(1000)` 时，究竟发生了什么？为什么 1 秒后还能从原来的位置继续执行？

### 2.1.1 先从一段简单的代码开始
```kotlin
suspend fun getUser(): String {
    println("1. 开始查询")

    delay(1000)

    println("2. 查询完成")
    return "Alice"
}
```
假设某个协程调用了 `getUser()`。执行到 `delay(1000)` 时，它不能直接往下执行，因为还没到指定时间。如果像普通线程那样用 `Thread.sleep(1000)` 等待，就需要阻塞线程。但 `delay()` 的设计是挂起当前协程，等待计时结束后恢复执行。这就产生了两个问题：
- **问题 A**： 协程暂停后，怎么知道下次该从哪行代码继续？
- **问题 B**： 谁负责在 1 秒后通知它继续执行？
它们分别涉及 `Continuation` 和负责计时、调度恢复的机制。

### 2.1.2 Continuation 到底是什么？
Kotlin 官方定义：
```kotlin
interface Continuation<in T> {
    val context: CoroutineContext
    fun resumeWith(result: Result<T>)
}
```
关于 `in` 的解释，见[[协程学习#2.1.2.1 扩展 - in]]

先来看看这两个成员：

| **成员**             | **作用**               |
| ------------------ | -------------------- |
| context            | 提供关联协程的上下文，例如调度器，Job |
| resumeWith(result) | 使用成功结果或异常，恢复对应协程执行   |
> [!warning]
> `Continuation` 不是线程，也不是线程池，更不是一个用来记录协程是否完成的布尔变量。**它表示一段被暂停的计算该如何执行**

如果 `getUser()` 中途挂起，那么恢复时需要知道已经执行到了 `delay()`，而不是再次从第一行开始执行。在 Kotlin/JVM 中，编译器会生成相应的状态机及 Continuation 实现，保存恢复所需的状态。
![[协程挂起与恢复的概念图.png]]
这里需要强调，`Continuation` 接口本身<mark style="background-color: #FF5582A6;">只规定如何接收结果并恢复执行</mark>。<mark style="background-color: #FFB86CA6;">真正保存局部变量、执行状态等信息的，是编译器生成的具体实现及其相关对象。</mark>

#### 2.1.2.1 扩展 - in
in 表示**逆变(Contravariance)**。控制的是不同泛型类型之间的赋值关系，而不是能否传入子类对象。例如：
```kotlin
val anyContinuation: Continuation<Any> = ...
// 合法，因为 Continuation 的 T 使用了 in
val stringContinuation: Continuation<String> = anyContinuation
```

反过来则不行：
```kotlin
val stringContinuation: Continuation<String> = ...
// 编译错误
val anyContinuation: Continuation<Any> = stringContinuation
```

### 2.1.3 用 suspendCoroutine 手动实现挂起与恢复

Kotlin 标准库提供了一个函数：
```kotlin
suspendCoroutine { continuation ->
    // 可以在这里安排异步操作
}
```
它提供当前挂起点对应的 `Continuation`。通过这个对象，就可以在外部操作完成时恢复协程。

#### 2.1.3.1 为什么 suspendCoroutine 能拿到 Continuation？我知道API 就是这样定义的，但是为什么它能获得 Continuation？为什么它能成为挂起点？

先看普通函数：
```kotlin
fun getUser(): String {
    return "Alice"
}
```
编译后，它本质上还是一个普通函数。调用之后直接返回字符串。而挂起函数不同：
```kotlin
suspend fun getUser(): String {
    return "Alice"
}
```
在 JVM 上，Kotlin 编译器会把挂起函数转换成一种特殊的调用形式。为了理解，可以想象成：
```kotlin
fun getUser(
    continuation: Continuation<String> // 这里
): Any? {
    return "Alice"
}
```
编译器会给挂起函数增加一个 Continuation 参数。为什么返回类型变成 `Any?`？因为挂起函数执行后可能产生两种结果：
- 正常完成，直接返回结果，例如 `"Alice"`。
- 发生挂起，返回特殊标记 `COROUTINE_SUSPENDED`。
这套转换方式叫 CPS（Continuation-Passing Style，续体传递风格）。

那么 suspendCoroutine 是怎么拿到 continuation 的？先看函数签名：
```kotlin
// TODO inline 是什么？
inline suspend fun <T> suspendCoroutine(
    crossinline block: (Continuation<T>) -> Unit
): T
```
它自己也是一个挂起函数。它的底层通过编译器支持的特殊函数 `suspendCoroutineUninterceptedOrReturn` 获取当前 Continuation，再经过包装，传入你写的 Lambda。即
```kotlin
suspendCoroutine { continuation -> 操作}
```
中的continuation

<mark style="background-color: #FF5582A6;">区分两个术语</mark>：
- 潜在挂起点
- 实际挂起
如：
```kotlin
suspend fun hello(): String =
    suspendCoroutine { continuation ->
        continuation.resume("Alice")
    }
```
这里调用了 `suspendCoroutine`，所以是一个潜在挂起点，但`resume`立刻提供了结果，因此不会实际发生挂起


#### 2.1.3.2 先看个例子：
```kotlin

import kotlinx.coroutines.*
import kotlin.coroutines.resume
import kotlin.coroutines.suspendCoroutine
import java.util.concurrent.Executors
import java.util.concurrent.ScheduledExecutorService
import java.util.concurrent.TimeUnit

suspend fun fetchUser(
    scheduler: ScheduledExecutorService
): String = suspendCoroutine { continuation ->
	// 先执行这个，第二个
    println("A：开始等待")
	
	// 这里是创建了一个未来执行的定时任务，该任务本身并不会马上执行，只是创建任务的代码会马上执行，到这里，整段 lambda就算执行完了，但函数还不算执行完，因为这个任务本身还没做，而这里本身也会挂起，于是执行下一个launch，即执行其他任务的那个
	// 等到这个任务真的完成后，这段函数才算完成
    scheduler.schedule({
        println("C：异步操作完成")
        continuation.resume("Alice")
    }, 500, TimeUnit.MILLISECONDS)
}

fun main() {
    val scheduler = Executors.newSingleThreadScheduledExecutor()

    try {
        runBlocking {
            launch {
	            // 第一个执行
                println("1：调用 fetchUser")
                // 进入 fetchUser
                val user = fetchUser(scheduler)
                // 最后，等上面的定时任务完成，整个函数执行完成后，这里才会打印
                println("3：拿到用户 $user")
            }

            launch {
	            // 第三个
                println("2：执行其他任务")
            }
        }
    } finally {
        scheduler.shutdown()
    }
}
```


### 2.1.4 suspendCancellableCoroutine
```kotlin
suspendCoroutine { continuation ->
    // ...
}
```
这个没有自动提供与协程Job 取消机制的集成。例如一个用户发起 HTTP 请求，随后取消了请求，我们通常不希望对应的业务协程还在无意义地等待。因此就有了：
```kotlin
suspendCancellableCoroutine { continuation ->
    // ...
}
```
与上面普通的 `suspendCoroutine` 不同，它提供的是 `CancellableContinuation`，可以响应协程取消，并注册取消时的清理操作。把之前的代码改成：
```kotlin
suspend fun fetchUser(
    scheduler: ScheduledExecutorService
): String = suspendCancellableCoroutine { continuation ->

    val task = scheduler.schedule({
        continuation.resume("Alice")
    }, 500, TimeUnit.MILLISECONDS)
    
	// 表示协程取消时，尝试取消还未执行的定时任务
	// 不一定能停止已经开始的任务
    continuation.invokeOnCancellation {
        task.cancel(false) // false表示明确不尝试中断正在执行该任务的线程
    }
}
```

### 2.1.5 状态机
先看之前的例子：
```kotlin
suspend fun getUser(): String {
    val name = "Alice"

    delay(1000)

    return name
}
```
可以把他想象成如下简化的状态机：(伪代码)
```kotlin
class GetUserState {
    var label = 0 // 表示当前执行到哪个状态
    var name: String? = null // 保存需要跨越挂起点继续使用的局部变量(GPT 原话依旧难懂)
    // 我的理解就是比如上面 val name = "Alice" 执行了，到下面 delay 挂起了，那就算是个挂起点，然后下次因为要执行 return name，就是越过了那个点，也就是delay那一行，name就是用来保存delay前面的那些信息的，不过因为这里只有一个name需要保存，所以就只生成了这一个

    fun execute(result: Any?): Any? {
        when (label) {
            0 -> {
                name = "Alice"

                label = 1

                val r = delayWithContinuation(this)

                if (r == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED
                }
            }

            1 -> {
                // 从 delay 之后恢复
                // 检查恢复结果是否包含异常
            }
        }

        return name
    }
}
```

| 概念                    | 准确含义                              |
| --------------------- | --------------------------------- |
| `suspend`             | 允许函数具有挂起点                         |
| `suspendCoroutine`    | 获取当前 Continuation，支持将异步完成结果接入挂起函数 |
| `Continuation`        | 表示挂起计算的后续执行，并接收恢复结果               |
| `resume(value)`       | 提供完成结果，必要时触发协程恢复                  |
| `COROUTINE_SUSPENDED` | 告诉调用方当前挂起函数没有立即完成                 |
| 状态机 `label`           | 记录恢复时应该进入哪个执行状态                   |
| 状态机中的局部变量字段           | 保存跨挂起点需要的数据                       |
| 调度器                   | 决定协程代码安排在哪些线程执行                   |

## 2.2 第二节：状态机

依旧先看示例代码：
```kotlin
import kotlinx.coroutines.*

suspend fun calculate(input: Int): Int {
    var n = input * 2
    println("A: $n")

    delay(500) // 挂起点 1

    n += 3
    println("B: $n")

    delay(500) // 挂起点 2

    println("C: $n")
    return n
}

fun main() = runBlocking {
    println(calculate(5))
}
```
输出：
```txt
10
13
13
```
正常情况下，`calculate()` 会经历两次实际挂起。编译器需要保证第一次恢复后执行 `n += 3`，第二次恢复后执行 `println("C: $n")`。

先忽略其他的，看 label 和局部变量：
状态0：首次执行时 lable = 0
```kotlin
n = input * 2
println("A: $n")
delay(500)
```
在可能挂起之前设置 label = 1，并保存需要跨挂起点使用的 n
							↓
状态1：第一次恢复时 label = 1
```kotlin
n += 3
println("B: $n")
delay(500)
```
在第二次可能挂起之前设置 label = 2，并保存更新后的 n。
							↓
状态2：第二次恢复时 label = 2
```kotlin
println("C: $n")
return n
```
函数完成，返回13

有两个细节值得注意：
- label 必须在可能发生挂起的调用之前更新
- 恢复时不需要重新调用已经完成的 delay

# 3. 第三章：协程的创建与执行

## 3.1 第一节 launch，async 和 coroutineScope

### 3.1.1 launch
```kotlin
fun main() = runBlocking {
    launch {
        delay(1000)
        println("Hello")
    }
}
```
launch 是一个<mark style="background-color: #FFB86CA6;">协程构建器(Coroutine Builder)</mark>，负责启动一个新的协程，返回值是 Job。

Job 可以理解为一个<mark style="background-color: #FFB86CA6;">代表协程任务生命周期的对象</mark>，可以通过它等待任务完成、请求取消任务、检查任务状态等。看下面的一个例子：
```kotlin
fun main() = runBlocking {
    println("1")

    val job = launch {
        delay(1000)
        println("3")
    }

    println("2")

	// join，挂起函数，如果 job 已经完成，直接返回，如果未完成，则挂起等待，完成后再继续
	// join 不会获取子协程的任务返回值，只负责等待对应的 Job 完成
	// join 挂起的是调用它的父协程，这里也就是 runBlocking 创建的协程
    job.join()

    println("4")
}
```
输出：
```txt
1
2
3
4
```
<mark style="background-color: #FFB8EBA6;">小知识：runBlocking 有两个特殊行为：即一方面创建协程，一方面阻塞调用它的线程，直到整个作用域完成，默认情况下，runBlocking 会在这个线程上运行事件循环(Event loop)。因此，即使 runBlocking 本身创建的父协程挂起，main 线程仍然可以在事件循环中运行子协程</mark>

<mark style="background-color: #FF5582A6;">疑问：这里的join看起来跟 Thread.sleep() 没什么区别啊，看起来都像是阻塞式的。</mark>
答：问出这个问题，你可能需要去放松一下了。join 表示的是挂起，而不是占用当前线程死等，也就是说挂起时线程可以去干别的，至于如果是真实的情况下，要等待的任务不是单纯的 delay，而是真的需要资源才能完成，这种时候协程的价值则更多的体现在任务组织、取消、生命周期管理，以及与其他挂起操作的配合上，而并非降低计算本身的资源消耗，<mark style="background-color: #FFB86CA6;">join 节省的是等待者对线程的占用，不是被等待任务的执行成本</mark>，也就是说，在CPU密集型任务上，协程并没有什么很大的优势。

### 3.1.2 launch 和 async 有什么区别？

它们都能启动新协程，但返回值不同：
```kotlin
val job: Job = launch {
    delay(1000)
    println("Hello")
}

val deferred: Deferred<String> = async {
    delay(1000)
    "Alice"
}
```
async 返回 `Deferred<T>`，也是一种 Job，但额外提供了获取任务结果的能力。
对比一下：

| |`launch`|`async`|
|---|---|---|
|启动协程|是|是|
|返回类型|`Job`|`Deferred<T>`|
|等待完成|`join()`|`await()`|
|获得业务结果|不直接提供|`await()` 返回 T|
|常见用途|执行不需要返回值的任务|并发计算、查询并获取结果|
例如：
```kotlin
fun main() = runBlocking {

    val deferred = async {
        delay(1000)
        10 + 20
    }

    println("等待结果")

    val result = deferred.await()

    println(result)
}
```
输出为：
```txt
等待结果
30
```

### 3.1.3 coroutineScope 又是什么？
这个很容易和大写的 `CoroutineScope` 搞混。大写的是接口，小写的是函数

#### 3.1.3.1 协程作用域
协程作用域可以理解成管理协程的一种上下文环境，比如：
```kotlin
fun main() = runBlocking {

    launch {
        println("协程 A")
    }

    launch {
        println("协程 B")
    }
}
```
这里的两个 launch 都是在 runBlocking 提供的 CorountineScope 中启动的。他们通常会成为 runBlocking 对应 Job 的子任务。
![[协程作用域示例.png]]
这是一种父子关系，后面结构化并发时会提到。

#### 3.1.3.2 为什么需要 coroutineScope 函数？

假设有一个挂起函数，想在里面启动两个子任务，并确保两个子任务都完成后才能返回：
```kotlin
suspend fun loadData() = coroutineScope {

    launch {
        delay(1000)
        println("用户查询完成")
    }

    launch {
        delay(500)
        println("订单查询完成")
    }
}

// 调用
fun main() = runBlocking {
    println("开始")

    loadData()

    println("全部完成")
}
```
输出：
```txt
开始
订单查询完成
用户查询完成
全部完成
```
可以看到，loadData 并未在理论上应该挂起的位置(即两个 delay 处)挂起，而是正常执行了两个任务，这就是因为 `coroutineScope` 会等待它内部的启动的子协程全部完成，才正常返回，<mark style="background-color: #FFF3A3A6;">它把这些子任务组织在一个作用域内，并保证作用域正常完成时，内部的子任务也已经完成。</mark>这也是 Kotlin 结构化并发的重要基础。

#### 3.1.3.3 coroutineScope 和 runBlocking 的区别

|                | `runBlocking`                                             | `coroutineScope`                                              |
| -------------- | --------------------------------------------------------- | ------------------------------------------------------------- |
| 自身是什么          | <mark style="background-color: #BBFABBA6;">普通函数</mark>    | 挂起函数                                                          |
| 能否在普通 main 中调用 | 可以                                                        | <mark style="background-color: #ABF7F7A6;">不能直接调用</mark>      |
| 等待子协程完成        | <mark style="background-color: #FF5582A6;">是</mark>       | <mark style="background-color: #FF5582A6;">是</mark>           |
| 等待期间的行为        | <mark style="background-color: #ADCCFFA6;">阻塞调用线程</mark>  | <mark style="background-color: #CACFD9A6;">可以挂起当前协程</mark>    |
| 常见用途           | <mark style="background-color: #BBFABBA6;">同步入口、测试</mark> | <mark style="background-color: #FFB8EBA6;">挂起函数内部组织子任务</mark> |

### 3.1.4 一个容易忽视的细节
```kotlin
fun main() = runBlocking {

    launch {
        delay(1000)
        println("A")
    }

    println("B")
}
```
这里并没有调用 join，但程序依然会等待子协程完成之后才退出 runBlocking，原因是 runBlocking 本身就会等待他的子协程完成。也就是说 <mark style="background-color: #FF5582A6;">join 不是为了不让程序提前结束必须写的东西，而是为了能够在代码的某个具体位置明确等待指定任务完成。(这里确实最好用不是...而是)</mark>，如果后续代码必须等待某个任务完成才能执行，那么 join 就有意义

## 3.2 第二节：CoroutineScope、Job 与父子协程
<mark style="background-color: #ADCCFFA6;">重点：结构化并发</mark>
<mark style="background-color: #ABF7F7A6;">三个问题：协程之间怎么建立父子关系、父协程为什么要等待子协程、CorountineScope 到底负责什么</mark>

### 3.2.1 CoroutineScope 和 Job
|概念|职责|
|---|---|
|`CoroutineScope`|提供创建协程所需的上下文，限定一组协程的管理范围|
|`Job`|表示任务的生命周期，支持等待、取消及父子关系|
|`launch`|在指定作用域中启动新协程，并返回该协程的 Job|
```kotlin
fun main() = runBlocking {   // 创建协程 R

    val jobA = launch {      // 创建子协程 A
        delay(1000)
    }

    val jobB = launch {      // 创建子协程 B
        delay(500)
    }
}
```
![[协程父子关系.png]]
这里的 `jobA`、`jobB` 就分别是两个 `launch` 返回的 Job。<mark style="background-color: #FFF3A3A6;">父子关系建立在 Job 之间，而不是线程之间。</mark>

### 3.2.2 父协程为什么要等待子协程
```kotlin
fun main() = runBlocking {
    println("1")

    launch {
        delay(1000)
        println("3")
    }

    println("2")
}

```
输出1，2，3。没有写 join，但程序仍等待子协程执行完成才退出，因为<mark style="background-color: #FFB86CA6;">父 Job 不能在子 Job 尚未完成时进入最终完成状态。</mark>但是要注意，<mark style="background-color: #FFB8EBA6;">父协程执行完自己的代码 != 父 Job 已经完成。</mark>例如上面 runBlocking 的协程执行完之后，即打印2之后，已经执行完了自己的代码块，但他还有一个没有完成的子 Job。为什么要这么设计？因为如果父协程不等待子协程，那么父协程执行完之后这个子协程就没人管了

### 3.2.3 ## coroutineScope() 到底有什么作用？
```kotlin
fun main() = runBlocking {
    // 协程 R
    println("R: 开始") // 1

    coroutineScope {
        // 创建作用域 S

        launch {
            delay(200)
            println("A: 完成") // 4
        }

        launch {
            delay(100)
            println("B: 完成") // 3
        }

        println("S: 已启动两个任务") // 2
    }

    println("R: 继续") // 5
}

```
输出：
```txt
R: 开始
S: 已启动两个任务
B: 完成
A: 完成
R: 继续
```
- `runBlocking` 创建了协程 R。
- `coroutineScope` 创建了新的作用域 S 以及关联的 Job，但它不像 `launch` 那样启动一个额外的并发执行协程。
- 两个 `launch` 分别创建了协程 A、B，它们的 Job 都是作用域 S 对应 Job 的子 Job。

这里会有个疑问：为什么 `S: 已启动两个任务` 后不是直接输出的 `R: 继续` 呢？因为`coroutineScope` 是挂起函数，他必须等待自己代码块以及内部启动的子协程全部完成，才能正常返回，当A、B还没有完成时，<mark style="background-color: #FF5582A6;">调用`coroutineScope` 的协程 R 可以挂起等待。</mark>注意是R，不是别的。与 join 其实是类似的，只不过 join 是管理单个 Job，而`coroutineScope`是管理整个作用域

### 3.2.4 既然父协程本来就会等待子协程[[协程学习#3.2.1 CoroutineScope 和 Job]]，为什么还需要 coroutineScope？
假设一个 Spring Boot Service，需要同时查询用户信息和订单：
```kotlin
suspend fun getSummary(): Summary = coroutineScope {

    val user = async {
        getUser()
    }

    val orders = async {
        getOrders()
    }

    Summary(
        user = user.await(),
        orders = orders.await()
    )
}
```
三个作用：
- ==在普通的 `suspend fun getSummary()` 中，并没有天然可用的 `CoroutineScope` 接收者。(解释见下方)==`coroutineScope` 正好提供一个，让我们可以在其中调用 `launch` 或 `async`。
- `getSummary()` 不会在两个子任务仍未完成时正常返回结果。这意味着调用者不用担心某个任务还没有结束，就已经退出了整个业务操作。
- 例如正常的结构化并发关系下，如果一个子协程发生未处理的普通异常，作用域会取消其他子任务，并将异常传播出去。如果调用方取消了当前操作，作用域里的子协程也会收到取消请求。
---
`launch` 并不是一个可以在任何地方直接调用的普通函数。它的定义可以简化为：
```kotlin
// CoroutineScope.launch 表明这是一个扩展函数，也就是说，要调用 launch，必须有一个 CoroutineScope 对象作为接收者。
fun CoroutineScope.launch(
    block: suspend CoroutineScope.() -> Unit
): Job
```
那为什么 runBlocking 里面可以直接调用呢？因为这是因为 `runBlocking` 接收的 Lambda 有一个隐式的 `CoroutineScope` 接收者。在这个 Lambda 中：
```kotlin
runBlocking {
    launch {
        println("Hello")
    }
}
```
可以写成：
```kotlin
runBlocking {
    this.launch {
        println("Hello")
    }
}
```
这里的 `this` 就是 `runBlocking` 提供的 `CoroutineScope`。
