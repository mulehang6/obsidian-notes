# 1. 第一节
``` kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    launch {
        println("A1")
        delay(500) // 执行到这里时第一个协程挂起，执行下面的
        println("A2")
    }

    launch {
        println("B")
    }
}
```
执行结果：A1, B, A2。
如果换成Thread.sleep，那么就是A1, A2, B。因为 sleep 会阻塞当前线程

- `runBlocking` 自己会阻塞调用它的线程，直到它管理的任务完成。
- `suspend` 只是表示函数可以挂起，并不意味着每次调用都会挂起，更不意味着函数体里的阻塞操作自动变成非阻塞操作。

## 1.1 一些疑问
### 1.1.1 runBlocking 是否只能像示例代码那样使用？只能放在main后面？何时使用？

不是，runBlocking 本质上就是个可以调用的函数，例如可以这样写：
```kotlin
fun main() {
    runBlocking {
        delay(1000)
        println("Hello")
    }
}
```

在普通函数中调用：
```kotlin
fun getUser(): String {
    return runBlocking {
        delay(1000)
        "Alice"
    }
}
```

正确替代方法：

如果本身就是挂起函数
```kotlin
suspend fun getUser(): User {
    return userService.fetchUser()
}
```
<mark style="background-color: #FF5582A6;">直接调用即可。</mark> 这里指的是语法上的直接调用，并不是说直接执行协程

如果需要在挂起函数内创建并发子任务：<mark style="background-color: #FFB86CA6;">(扩展内容，暂时看不太懂)</mark>
```kotlin
suspend fun getUser(): User = coroutineScope {
    async {
        userService.fetchUser()
    }.await()
}
```
这里的 `async` 只是演示用法。只有一个任务而且立即 `await()`，实际上没有并发收益，直接调用 `fetchUser()` 更简单。

runBlocking 主要用于普通同步代码必须调用挂起函数，而调用入口又不能改成 `suspend` 的场景，例如某些测试或同步 API 的兼容代码。例子如下：

假设你接入了一个第三方 Java 库，它规定你必须实现下面这个接口：
```kotlin
interface ReportProvider {
    fun generate(): String
}
```
你无法修改这个接口，也不能把它的 `generate()` 改成 `suspend fun`。
但你的业务逻辑已经使用了协程：
```kotlin
suspend fun fetchReport(): String {
    delay(1000)
    return "报告内容"
}
```
直接这样写会编译失败：

```kotlin
class MyReportProvider : ReportProvider {
    override fun generate(): String {
        return fetchReport() // 编译错误
    }
}
```
原因是<mark style="background-color: #FF5582A6;">普通函数不能直接调用挂起函数。</mark>
这时可以使用 `runBlocking`：

```kotlin
class MyReportProvider : ReportProvider {
    override fun generate(): String {
        return runBlocking {
            fetchReport()
        }
    }
}
```
这个例子的重点是：**第三方接口要求同步返回结果，所以必须等。**
==`suspend` 提供挂起能力，`async` 用于启动并发任务，`await` 用于等待并获取结果。==

### 1.1.2 如何在 SpringBoot 中使用协程呢？
**Spring 本身就支持挂起函数，因此通常不用自己调用 `runBlocking` 或手动创建协程作用域来处理 HTTP 请求。**

Spring MVC 和 Spring WebFlux 都支持 `suspend` Controller。区别在于底层请求处理模型。只是提一嘴 WebFlux，这里不展开。

**一个实际的 Spring Boot 场景** ^058e78

假设你的后端需要提供这个接口：
```http
GET http://localhost:8080/summary
```
后端会同时调用两个 HTTP 接口：
- `/mock/user`，模拟获取用户资料，耗时约 1 秒。
- `/mock/orders`，模拟获取订单，耗时约 1 秒。
最后把两个结果合并。

先模拟两个慢接口
```kotlin
import kotlinx.coroutines.delay
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.RestController

@RestController
class MockController {

    @GetMapping("/mock/user")
    suspend fun user(): String {
        delay(1000)
        return "Alice"
    }

    @GetMapping("/mock/orders")
    suspend fun orders(): String {
        delay(1000)
        return "Order-1, Order-2"
    }
}
```

编写发送 HTTP 请求的 Service
```kotlin
import kotlinx.coroutines.future.await
import org.springframework.stereotype.Service
import java.net.URI
import java.net.http.HttpClient
import java.net.http.HttpRequest
import java.net.http.HttpResponse

@Service
class DemoService {

    private val client = HttpClient.newHttpClient() // JDK中的API

    suspend fun get(path: String): String {
        val request = HttpRequest.newBuilder()
            .uri(URI.create("http://localhost:8080$path"))
            .GET()
            .build()

		// sendAsync是JDK提供的异步HTTP请求API，调用后得到CompletableFuture，代表将来可以获得的结果
        val future = client.sendAsync(
            request,
            HttpResponse.BodyHandlers.ofString()
        )

        val response = future.await() // kotlin提供的扩展函数，当Future尚未完成时，await()可以挂起当前协程，而不是阻塞线程等待

        check(response.statusCode() == 200)
        return response.body()
    }
}
```

最后编写Controller
```kotlin
import kotlinx.coroutines.async
import kotlinx.coroutines.coroutineScope
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.RestController

data class Summary(
    val user: String,
    val orders: String
)

@RestController
class SummaryController(
    private val service: DemoService
) {

    @GetMapping("/summary")
    // 这个语法糖叫 单表达式函数体 + 尾随 lambda
    suspend fun summary(): Summary = coroutineScope {

        val user = async {
            service.get("/mock/user")
        }

        val orders = async {
            service.get("/mock/orders")
        }

        Summary(
            user = user.await(),
            orders = orders.await()
        )
    }
}
```

启动项目后，请求 `/summary`，正常情况下大约 1 秒多一点就能拿到：
```json
{
  "user": "Alice",
  "orders": "Order-1, Order-2"
}
```

如果去掉两个 `async`，改成：
```kotlin
val user = service.get("/mock/user")
val orders = service.get("/mock/orders")
```
两个调用就会顺序等待，总耗时接近 2 秒。

这里并发执行的是两个 HTTP 请求。即使只有一个协程执行线程，也可以通过非阻塞等待让两个 HTTP 请求同时处于进行中。



<mark style="background-color: #FF5582A6;">注意事项：</mark>
<mark style="background-color: #FF5582A6;">Mybatis-plus/Mybatis 底层均使用 JDBC，而JDBC为阻塞式查询</mark>，而针对独立的阻塞操作，可以考虑：
```kotlin
suspend fun getUser(id: Long): User? =
    withContext(Dispatchers.IO) {
        userMapper.selectById(id)
    }
```
把阻塞任务安排到更适合阻塞I/O的线程池中执行

<mark style="background-color: #FF5582A6;">另外，Spring 的传统 JDBC 事务上下文通常和线程绑定。在 `@Transactional` 管理的事务内部，不能随意切换到 `Dispatchers.IO`，否则可能导致事务上下文不能正确传递。</mark>

来看下面的一个例子：
```kotlin
suspend fun getUser(): User? =
    withContext(Dispatchers.IO) {
        userMapper.selectById(1)
    }
```

在发生调度切换的典型情况下：
1. 原来的协程挂起，等待 `withContext` 的结果。
2. `Dispatchers.IO` 将数据库查询安排到适合阻塞 I/O 的工作线程。
3. 工作线程执行 JDBC 查询，并被阻塞约 1 秒。
4. 查询完成后，协程取得返回值，继续执行。
第2点按我的理解，这里不就是换了个更“合适”的线程阻塞吗？那换到IO有什么意义？
假设一个传统的 Spring MVC 服务，请求处理线程池里有 10 个线程。
有 10 个请求同时进来，每个请求都需要等待一次阻塞式数据库查询。
![[切换到IO DIspatcher的意义.png]]
<mark style="background-color: #FFF3A3A6;">这里的收益是让一类线程免于被阻塞操作长期占用，特别是有其他任务需要使用这些线程时。</mark>
但必须注意：
- JDBC 线程依然被占用。
- 数据库连接依然被占用。
- 假如数据库连接池只有 10 个连接，也不会因为用了协程就能同时执行 100 个数据库查询。
- 如果业务本来就是传统的同步 MVC + MyBatis-Plus，额外切换线程可能带来开销，性能未必更好。
所以，不能把 `withContext(Dispatchers.IO)` 当成<mark style="background-color: #FF5582A6;">数据库查询的通用性能优化手段。</mark>
如果所有的请求都主要是在执行阻塞式 JDBC，那么简单地把阻塞从一组线程转移到另一组线程，通常不能从根本上改善系统吞吐量。

相反，上一节的 [[#^058e78]] 才真正实现了 HTTP 等待期间不阻塞协程的执行线程。

另有一点注意事项：`withContext(Dispatchers.IO)` 不保证切换到另一个物理线程。例如，从 `Dispatchers.Default` 切换到 IO 时，两者有可能共用同一个线程。它真正改变的是协程使用的调度上下文。<mark style="background-color: #FFB86CA6;">(先仅作了解)</mark>

## 2. 先了解一下线程池
**线程池一般是由程序中的库或框架管理的，线程本身则由操作系统调度。**

例如 Java 的 `ThreadPoolExecutor`、Spring 的 `ThreadPoolTaskExecutor` 都可以管理线程池。

Kotlin 协程使用的 `Dispatchers.IO` 和 `Dispatchers.Default` 则是协程库提供的调度器，它们在 JVM 上使用共享的工作线程池。

### 2.1 先理解线程池

假设有三个任务需要执行：
```kotlin
taskA()
taskB()
taskC()
```

最简单的做法是每个任务创建一个新线程：
```kotlin
Thread { taskA() }.start()
Thread { taskB() }.start()
Thread { taskC() }.start()
```
但是频繁创建、销毁线程有成本。

线程池采用另一种方式：创建或维护一批工作线程，让它们反复执行提交进来的任务。
![[线程池示例.png]]
这样可以重复使用线程，避免为每个小任务都创建新的线程。

不过有个问题：如果工作线程执行到 `Thread.sleep()` 或阻塞式 JDBC 查询，它在等待期间就不能继续处理其他任务。

也就是说<mark style="background-color: #FF5582A6;">不能把「使用线程池」等同于「非阻塞」。</mark>

### 2.2 Dispatchers.IO 和线程池是什么关系？

```kotlin
withContext(Dispatchers.IO) {
    userMapper.selectById(1)
}
```
这里各部分的职责是：

|部分|作用|
|---|---|
|`withContext`|在指定的协程上下文中执行代码，并等待其结果|
|`Dispatchers.IO`|提供适合执行阻塞 I/O 的调度环境|
|工作线程池|提供实际运行代码的线程|
|`selectById()`|执行 JDBC 查询，期间可能阻塞工作线程|

`Dispatchers.IO` 会按需使用共享工作线程，默认阻塞 I/O 并行度限制为 <mark style="background-color: #FFF3A3A6;">64</mark> 或<mark style="background-color: #FFF3A3A6;"> CPU 核心数</mark>，取两者较大值，且可以配置。它和 `Dispatchers.Default` 也共享底层线程资源。

### 2.3 Dispatchers.Default
- Default：用于计算密集型任务，例如计算复杂数据
- IO：主要用于可能阻塞线程的IO任务，例如传统JDBC查询，阻塞式文件读取
