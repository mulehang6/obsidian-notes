# Jewel 安全迁移

## 分阶段执行

1. 在改动前运行最小相关编译和测试，记录通过结果或完整失败堆栈、Gradle/JDK 版本与依赖树。
2. 按 `version-safety.md` 建立版本矩阵，逐版筛选旧版至目标版的 Release Notes。只在目标为已发布构件时继续。
3. 原子更新版本矩阵与同发布线的 Jewel 构件；先处理 Compose/Kotlin/JDK/IntelliJ Platform 的二进制兼容性，再处理 Kotlin 编译错误。
4. 将每一处修复归入：坐标/模块、导入/签名、主题初始化、运行时行为或视觉行为。使用目标版本 source JAR、签名或官方示例确认替换方式。
5. 为受影响交互补充聚焦测试，并在可运行环境中检查主题、焦点、窗口、弹窗、滚动、缩放、图标与 Markdown（如有）。

## API 修复准则

- 不要用全局搜索替换批量改包名或函数名。一个符号的迁移可能同时改变参数语义、主题归属和运行时前提。
- API 被移除或重命名时，先确认它在目标版本的正式替代项；没有替代项时保留兼容层、降低目标版本或向用户报告阻塞，不要臆造功能相近的组件。
- 在升级多个发布线时，按发布说明建立逐条映射表，而不是只解决当前编译器显示的第一个错误。
- 将直接使用实验 API 的调用集中起来，避免其破坏性变更扩散到业务 UI。

## 验收

迁移完成至少需要同时满足：

- 依赖树无旧新 Jewel 发布线混用，也无 standalone 与 plugin/bridge 混用。
- 最小相关编译、测试和打包任务通过。
- 受影响 UI 在主题、键盘/焦点、缩放和窗口交互中无已知回归。
- 交付说明包含版本矩阵、审阅的 Release Notes 范围、API 映射、验证结果与尚存风险。
